## What this is and why it matters

**Dynamic Workflows** is a feature of *this runtime* — not of the Microsoft
Agent Framework (MAF). It lets an agent's tools declare themselves
`@workflow_tool`-safe (deterministic, idempotent) so that, at request time, an
LLM tool call can hand a small DAG of those tools to a durable orchestrator
instead of running them as ordinary in-turn tool calls. The runtime discovers
these tools, wires a real Azure Durable Functions orchestrator/activity
pipeline for them at app-registration time, and exposes exactly five control
tools (`start_workflow`, `get_workflow_status`, `list_workflows`,
`cancel_workflow`, `terminate_workflow`) to the agent's reasoning loop. MAF
never sees a "workflow" — it sees five ordinary async tool callables. The
orchestration itself is entirely an Azure Functions Host + Durable Functions
concern, established by the original design in
[0004-dynamic-workflows.md](0004-dynamic-workflows.md).

This matters for ACA because FRD 0008's ACA Sandbox model relocates the
*whole* harness — MAF's reasoning loop, tools, skills, MCP clients, memory —
into one isolated Azure Container Apps sandbox per session, and turns the
Azure Functions app into a thin, authenticated **controller** in front of it
(0008, §goals; [0008.1](0008.1-execution-backend-and-controller.md)). The
sandbox is *not* a Functions Host. Under 0008.6's Model-1 packaging (parent
Decision 69) its generic image is a stdlib-only bootstrap plus base OS that
bakes in *no* MAF; the runtime that actually speaks the controller protocol,
re-runs discovery/translation, and drives a MAF `Agent` arrives as the
customer's captured `.python_packages`, delivered over the transport. Either
way, the stack that executes is a fixed entry point over MAF — never a
Functions Host. Dynamic Workflows' entire mechanism — promoting a tool
call into a Durable Functions orchestrator run — depends on exactly the
Functions Host machinery the sandbox deliberately does not carry. That is the
tension this FRD analyzes.

The headline finding, substantiated below, is more precise than "the
orchestrator doesn't exist under ACA": **it does exist** — the controller
(still an ordinary Functions app) registers a fully wired Durable
orchestrator for any project with `workflows.enabled: true`, *regardless* of
which execution backend is chosen for the chat turn itself. What's missing
under ACA is only the bridge from the sandboxed MAF Agent's tool-call
boundary to that already-running controller-side orchestrator. This
reframing matters because it changes the shape of the compatibility problem
from "build a workflow engine that runs inside a locked-down sandbox" (hard,
likely wrong) to "give the sandbox a controller-mediated path to invoke five
specific control tools" (bounded, and analyzed in
[Candidate compatibility designs](#candidate-compatibility-designs) below).

## Precise mechanics of Dynamic Workflows today

Everything below is cited against
`src/azure_functions_agents/workflows/*` and its touchpoints in
`_function_tool.py`, `discovery/tools.py`, `registration/capabilities.py`,
`registration/endpoints.py`, `runner.py`, and `app.py`, as they exist on
`main` today. Nothing here is MAF code; MAF is handed ordinary async
callables and never learns that a "workflow" concept exists.

### 1. Two decoupled tool inventories, from discovery onward

`discovery/tools.py` scans `tools/*.py` and, via the `@workflow_tool`
decorator in `_function_tool.py`, attaches `WorkflowToolMetadata` to marked
callables — a `setattr`, not a MAF tool registration. This produces a
**second, separate inventory** from the normal `@tool`-discovered MAF
FunctionTools: workflow-safe tools live in
`azure_functions_agents.workflows.registry`'s module-level registry (name →
handler), addressable only from inside a running Durable orchestration, never
directly callable by the LLM. A function marked `@workflow_tool` explicitly
does **not** become a normal MAF tool (FRD 0004, Decision 7) — the two
inventories are disjoint by design.

### 2. Capability negotiation decides *whether* the bridge exists

`registration/capabilities.py::build_capabilities` computes
`filtered_workflow_tools` only when `resolved.is_main and
_workflows_enabled(resolved)` (lines 84–91), where `_workflows_enabled` reads
`resolved.workflows["enabled"] is True` from the agent's front matter (line
44–46) — a pure front-matter check, with **no dependency on execution
backend/provider at all**. This is the exact hook 0008.7's Decision 36
fail-closed gate extends: it makes the same `_workflows_enabled` check also
fail startup when the resolved provider is `aca_sandbox`.

### 3. Registration wires a real Durable Functions app — on the controller

`app.py`'s composition pass makes the whole `FunctionApp` object itself
Durable-aware: `app = df.DFApp(...) if workflows_requested else
func.FunctionApp(...)` (lines 154–158), where `workflows_requested` is
computed purely from front matter across all resolved agents (lines
150–153) — again, no backend/provider check. For each main agent,
`build_workflow_integration(app, resolved.metadata,
workflow_tools=capabilities.filtered_workflow_tools)` is called
unconditionally (`app.py` lines 206–211); it returns a non-`None`
`workflow_system_addendum` only if workflow tools survived filtering, and
that flag (`workflows_enabled`) is threaded into
`register_builtin_endpoints` (lines 244–253).

Inside `build_workflow_integration` (`workflows/integration.py`, line 268),
`register_workflows(app)` (`workflows/engine.py`, line 98) builds an
`azure.durable_functions.Blueprint()` and declares:

- `agents_workflow_run_tool` — an **activity trigger**
  (`@bp.activity_trigger(input_name="task")`, line 107) that dispatches a
  single DAG node to the matching handler in the workflow registry.
- `agents_workflow_orchestrator` — an **orchestration trigger**
  (`@bp.orchestration_trigger(context_name="context")`, line 135), a
  wave-based DAG scheduler using `context.call_activity(...)` per ready node,
  `context.create_timer(...)` for `wait` tasks, and
  `context.task_any`/`context.task_all` for fan-in — the deterministic-replay
  semantics that Durable Task Framework provides and that
  `workflows/schema.py`'s templating (`${node_id.result...}`, resolved
  against JSON-normalized prior outputs) depends on.

`app.register_blueprint(bp)` (line 286) hands both triggers to the Functions
Host's own trigger-dispatch loop. Separately, `registration/endpoints.py`
wraps the built-in chat HTTP (line 331) and stream (line 393) handlers with
`app.durable_client_input(client_name="client")` — an Azure Functions
**input binding**, resolved only by the Functions Host at invocation time,
that injects a live `DurableOrchestrationClient` — and does so only
`if workflows_enabled` (else plain handlers with no client are registered).
Durable's storage backend (Azure Storage vs. Durable Task Scheduler) and task
hub name are selected entirely by `host.json`, never by front matter
(`workflows/integration.py` lines 39–44, 123, 158–164) — one more piece of
state that lives with the Functions Host/deployment, not with the harness.

**This registration is unconditional on `resolved.is_main` and front-matter
`workflows.enabled` — it does not check which execution backend a given
agent uses.** Concretely: a project with `provider: aca_sandbox` and
`workflows.enabled: true` on `main.agent.md` makes the *controller's own*
Functions app a `DFApp` with a live orchestrator/activity Blueprint,
*today*, unchanged by ACA. The orchestrator is not a missing subsystem; it is
running right next to the sandbox, on the controller.

### 4. Execution is a fire-and-forget handoff into that same host

`runner.py::_build_role_agent` (lines 352–361) builds the five agent-facing
tools via `build_workflow_tools(durable_client=workflow_durable_client)` and
attaches them to the MAF `Agent`'s tool list — but only for the **main**
agent. `_build_delegated_agent` (lines 395–416) explicitly passes
`workflow_enabled=False, workflow_durable_client=None` — delegated/specialist
agents never receive workflow tools, mirroring 0008.13's precedent that only
the top-level harness instance gets host-adjacent capabilities.

Each tool body in `workflows/tools.py` (lines 303–472) is an ordinary async
MAF `FunctionTool` handler that reads `session.durable_client` off the
`WorkflowSessionContext` (`workflows/context.py`, line 66–71) built at
request time from the bound `durable_client` object (line 82–94). If that
object is `None` — i.e., no Functions Host resolved the
`durable_client_input` binding for this invocation — every handler
short-circuits to a static `_NO_CLIENT_MESSAGE` (line 259; checked at lines
308, 375, 406, 424, 449) rather than raising at startup. `start_workflow`'s
happy path is `await session.durable_client.start_new(ORCHESTRATOR_NAME,
instance_id=..., client_input={...})` (line 346) — it **enqueues and returns
immediately**. The actual DAG execution happens later, out-of-band, driven
entirely by the Functions Host's Durable Task Framework listener invoking
`agents_workflow_orchestrator`, independent of the chat turn that called
`start_workflow`. Instance IDs are prefixed with
`sha256(session_id)[:12]` (`context.py` line 46) — an anti-probing measure,
explicitly not an ACL.

**Summary of the two Functions-Host dependencies this bakes in:**

| Dependency | What it needs | Where it lives |
| --- | --- | --- |
| Trigger dispatch | Functions Host worker-dispatch loop + Durable extension bundle + task-hub backend from `host.json` | Controller's Functions app process |
| Binding injection | `durable_client_input` resolved per-invocation by the Host | Controller's Functions app process |

Neither dependency is satisfiable by the ACA sandbox: per 0008.6's Model-1
packaging (parent Decision 69) its generic image is a stdlib-only bootstrap
that loads the customer's captured MAF runtime (`.python_packages`) and runs a
fixed entry point over it — nothing in that stack is a Functions Host, carries
the Durable extension bundle, or can resolve a `durable_client_input` binding.

## Why this is incompatible with the ACA single-sandbox model in v1

### 1. No Functions Host process inside the sandbox

FRD 0008's own **Non-goals** state the project will not be "Modifying the
Azure Functions Host or Python worker protocol," and its master Decisions
log records **Decision 13 — Direct Functions Host integration is
deferred**, chosen over building it in parallel, "until the runtime-level
contract is proven and host-team investment is justified"
([0008.1](0008.1-execution-backend-and-controller.md), Decision 13, identical
framing: "The Python-level controller is enough to prove the product; wiring
this deeper into the Functions Host is postponed"). 0008.1's own
execution-backend contract (`AgentExecutionBackend.start_run`/`get_run`/
`read_events`/`cancel_run`) carries only typed requests and events — never a
live `ResolvedAgent`, Python tool objects, or a `DurableOrchestrationClient`
— across the controller/sandbox boundary. Mapped onto the runtime pipeline
(discover → translate → register → execute), 0008.1 states plainly:
"the seam lives in **execute**, while **registration** stays the only
Azure-aware stage that chooses and wires the backend." Registration —
including `register_workflows(app)` and the `durable_client_input` binding —
is a controller-side, registration-stage concern by construction. It has no
analog inside the sandbox, because the sandbox never runs the registration
stage; per 0008.6 it "unpacks it into `/app`, **re-runs the normal
discovery/translation pipeline locally, and runs the requested agent**" —
translate and execute, not register.

### 2. No Durable orchestrator substrate inside the sandbox to promote into

Because there is no Functions Host process inside the sandbox, there is
nothing for `context.call_activity`/`context.create_timer` to run against
locally, and no `durable_client_input` binding to inject a client into the
sandboxed `WorkflowSessionContext`. Per the mechanics above, the
`build_workflow_tools()` call inside the sandbox's copy of `_build_role_agent`
would receive `durable_client=None` — every workflow tool call would hit the
soft-fail `_NO_CLIENT_MESSAGE` path rather than erroring at startup. This
silent-ish degradation (a working tool that always politely refuses) is
exactly the class of surprise 0008.7's Decision 36 exists to prevent by
failing closed at startup instead: "a silent fallback would quietly drop
tools, workflows, schema validation, or event fidelity a user is relying
on."

### 3. Default-deny egress leaves no path to a Durable backend even if reachable

Even setting aside (1)–(2): 0008.9's **Decision 10 — Egress posture** puts a
full-inspection, **default-deny** policy active "before the harness
executes," rejecting both "allow then tighten" and "deny only after
bootstrap," because packaging requires no internet install at create time
(0008.6) — "there is no bootstrap window to protect." A sandbox attempting to
reach a Durable Task Scheduler endpoint or Azure Storage task-hub backend
directly would need an explicit, reviewable egress allowlist entry baked in
at sandbox creation — itself a nontrivial trust decision, since it would hand
the sandbox network reachability to (and, for DTS or Storage, credentials
for) an orchestration substrate, not just an anti-probing instance ID. This
is a secondary, reinforcing constraint: even a hypothetical
sandbox-resident Durable client would need a deliberate hole punched in a
posture designed to have no holes by default.

### 4. No nested execution substrate — one harness, one substrate, by design

0008.13 (subagent delegation) establishes the load-bearing precedent that
**the whole harness runs in one sandbox, in one process**: "One session =
one sandbox = one coordinator + its in-process specialists" (Decision 42),
and a harness that cannot run a specialist in-process must **fail closed at
startup**, "never silently drop delegation" (Decision 45) — the same
fail-closed pattern 0008.7 Decision 36 applies to Dynamic Workflows and
nested Dynamic Sessions. Dynamic Workflows needs something categorically
different from delegation, though: not a second *specialist agent* inside
the same substrate, but a second *execution substrate* (Durable's
orchestrator/activity engine) layered underneath the harness. Nothing in
FRD 0008 provisions a second substrate inside the sandbox — the sandbox is
sized and packaged (0008.6) around "harness + fixed entry point" only.

### 5. The controller↔sandbox transport has no ingress for a callback

0008.5 fixes the controller↔sandbox transport to a small, transport-agnostic
verb set — `submit`, `get_status`, `read_events`, `get_result`, `cancel`,
`ensure_ready` — implemented today as an authenticated file/exec journal, and
states plainly: "**anonymous ingress is never an allowed fallback**." 0008.5
also records that a live bidirectional channel was considered *and rejected*
as an alternative to journal polling for the *existing* streaming/cancel
problem, specifically because "it reintroduces the two things the journal
deliberately avoids — a sandbox **ingress path**" among them. Any
compatibility design in which the *controller* calls back into a specific,
already-running sandbox mid-orchestration (to execute a DAG step, say) would
need to either reopen that already-rejected ingress question, or route the
callback through the existing sandbox→controller direction only — a
constraint the candidate designs below take seriously.

### 6. A natural question: "why can't a sandbox tool just start a Durable run itself?"

A reasonable objection to (1)–(2): Dynamic Workflows already starts a Durable
orchestration that goes on to trigger independent activity-function instances
"as it sees fit," so — the intuition goes — why can't a sandbox-resident
workflow tool simply *trigger a new run* the same way, since spawning function
instances is evidently something the system already does at will? This
subsection answers that directly, because the answer is what forces every
candidate below to route through the controller rather than act locally.

**Starting a run is not the missing piece — the runtime that starts and runs
it is.** `start_workflow` today *is* exactly "trigger a new function run":

```python
# workflows/tools.py  (start_workflow)
returned_id = await session.durable_client.start_new(ORCHESTRATOR_NAME, ...)
```

and the orchestrator it starts fans out to independent activity instances via
host-dispatched triggers registered on the app:

```python
# workflows/engine.py  (register_workflows)
@bp.activity_trigger(input_name="task")
@bp.orchestration_trigger(context_name="context")
```

So the concept is fine. The blocker is the object that call hangs off:
`session.durable_client`. That client is **not something the harness
constructs** — it is a *Functions Host binding*, injected into the chat handler
by the host at invocation time:

```python
# registration/endpoints.py  (chat handler wiring, workflows enabled)
decorated = app.durable_client_input(client_name="client")(decorated)
```

and `workflows/context.py` documents it as exactly that: "the Durable Functions
`client` the Functions host injected into the chat handler via
`durable_client_input`." The whole app must be a `df.DFApp` for that binding to
exist at all (`app.py`). Inside the sandbox there is no Functions Host
(subsection 1), so there is no binding to inject, and `build_workflow_tools()`
receives `durable_client=None` (subsection 2) — every workflow tool politely
refuses.

**Even a hand-built client would not close the gap.** Suppose the sandbox
bypassed the binding and constructed a `DurableOrchestrationClient` pointed
straight at a task hub. Two things still fail:

- It would need **task-hub credentials and network egress** (Azure Storage or
  DTS) smuggled into the sandbox — precisely the hole 0008.9's default-deny
  posture (subsection 3) is designed not to have.
- More fundamentally, `start_new` only **enqueues a start message**. Something
  still has to *run* the orchestrator replay and *dispatch* its activity
  functions — and that "something" is the Functions Host + Durable extension,
  which by design exists **only on the controller** (subsections 1 and 4). The
  sandbox would have moved the *button* (initiation) inside its walls, at real
  security cost, while the *machine the button drives* (execution) stayed on the
  controller anyway — a strictly worse position than simply asking the
  controller to press start on its behalf.

**Consequence — and why v1 stays fail-closed.** This is the crux the candidate
designs below turn on: the controller already runs the entire Durable engine
today, unconditionally (see the mechanics section above); the sandbox has none
of it and cannot usefully acquire it. So a compatibility fix is necessarily
*delegation* (the sandbox asks the controller to start/poll/cancel on its
behalf — candidate (a)), never *local execution* inside the sandbox. Designing,
sizing, and signing off that delegation bridge — including the versioned
reverse-RPC transport capability 0008.5 has already ruled it requires (see
[Honest critique](#honest-critique) and the
[Decisions-log-style note](#decisions-log-style-note-non-binding)) — is
**deferred to a future implementation FRD**. Until such an FRD lands and ships,
the v1 posture is unchanged and deliberate: **an ACA-sandbox-backed agent with
`workflows.enabled` is simply not allowed — the runtime fails closed at startup**
per [0008.7](0008.7-harness-compatibility-and-conformance.md) Decision 36. This
document analyzes the future fix; it does not enable the combination.

## Candidate compatibility designs

None of these are decided here. They are ordered from most to least
architecturally aligned with the constraints in the previous section, per
this document's own (non-binding) assessment.

### (a) Controller-side orchestration, sandbox-side proxy tools — *leading candidate*

Keep `register_workflows(app)`, the Blueprint, and the
`durable_client_input` binding exactly as they are today, on the
**controller**. That registration already happens unconditionally, so the
controller already has a fully functional orchestrator/activity engine and
workflow-tool registry for the same agent project, independent of ACA — the
mechanics section above shows this is true *today*, with zero new code.

What's new: for ACA-backed agents only, `workflows/tools.py`'s five handlers
are replaced with thin proxies. Instead of reading a local
`session.durable_client`, a proxy ships a "run this control-plane tool on my
behalf" request to the controller over the *existing*
sandbox→controller direction of the 0008.5 transport, and the controller
executes it against its own, already-registered `durable_client`
(`start_new`, `get_status`, `raise_event`, `terminate`, …), returning the
result into the sandbox's normal tool-result channel.

- **Security / trust domain.** Strongest fit of the four: the sandbox never
  holds a `durable_client`, never gets Storage/DTS credentials, never needs
  new egress. The trust boundary for "who can start an orchestration under
  this app's identity" stays exactly where it is today — the controller's
  managed identity — consistent with 0008.9's OBO/managed-identity model.
- **Latency.** One extra controller round trip per *control-plane* call
  (`start_workflow`, `get_workflow_status`, …), not per DAG step — DAG
  execution stays entirely controller-side at Durable speed, unaffected.
  Dynamic Workflows' own API surface is already coarse-grained
  (start/poll/cancel, not step-by-step), so this cost lands where it hurts
  least.
- **Checkpoint / resume.** Strong: the orchestration instance lives entirely
  on the controller, checkpointed by Durable Task Framework exactly as
  today, wholly decoupled from sandbox suspend/resume (0008.8). A sandbox
  resume only needs to know a `workflow_id` was issued for this
  `session_id` — already naturally supported by the session-id-derived
  instance-ID scheme (`context.py` line 46).
- **Failure modes.** If the transport is degraded when a control-plane tool
  is called, that call fails retryably — the same failure class as any other
  controller RPC, not a new one. If the sandbox crashes/recycles mid-DAG,
  the orchestrator is unaffected and can be polled by a new sandbox instance
  for the same session after resume.
- **New surface required.** Real, but smaller than it first looks — see the
  deep dive immediately below: both directions this needs (a
  controller→sandbox file write, a sandbox→controller journal read) are
  already proven by Decision 26's live spike; what's new is a convention
  layered on them, not an unproven transport mechanism.

#### Deep dive: a concrete protocol sketch for the bridge

*(This subsection is this document's own synthesis, grounded in 0008.5's
already-resolved transport design. It is a sketch offered for evaluation —
not a claim that 0008.5 has already designed this, and not a decision.)*

0008.5's controller↔sandbox protocol already gives the controller
**authenticated read *and* write access to the sandbox's filesystem** via
the ADC data plane, and both directions a bridge would need are already
proven, not hypothetical:

- **Controller→sandbox write** is already live today: the controller writes
  the request envelope to `inbox/{run_id}.json` before every run, over the
  same ADC file-write primitive a bridge would reuse. Decision 26's spike
  measured this path directly (1 MiB round trip: 0.518 s write / 0.632 s
  read).
- **Sandbox→controller-visible write** is already live today: the sandbox
  journals `status.json` / `events.jsonl` / `result.json` as it runs, and
  the controller's `read_events(run_id, since=Last-Event-ID)` polls that
  journal for every run, today, to stream progress back to the caller
  (~1.14 s p95 event visibility, per the same spike).

A workflow-tool-call bridge does not need a new mechanism on top of these —
it needs a new **convention** layered on them, exercised while the calling
chat turn's own run is active and already being polled:

1. A proxy tool (per (a) above) appends a new *typed* record to its own
   `events.jsonl` — e.g. `{"type": "workflow_tool_call_requested",
   "request_id": …, "tool_name": "start_workflow", "args": {…}}`. This is
   not a novel idea at the protocol level: `events.jsonl` already carries a
   typed control record distinct from ordinary content events
   (`snapshot-restart`, used for replay-window recovery), so a second typed
   record kind for a different purpose is additive, not a new mechanism.
2. The controller's *existing* `read_events` poll loop — the same one
   already streaming progress for that turn — recognizes the new type and
   executes the requested call against its own live `durable_client`.
3. The controller writes the result back using the *same* proven
   controller→sandbox write direction `inbox/{run_id}.json` already uses,
   to a new path — e.g. `runs/{run_id}/workflow_calls/{request_id}.json`.
4. The proxy tool's `await` resolves by polling that one local file on the
   sandbox's own disk — a local filesystem read, not a network call, so
   0008.9's default-deny egress is untouched by this step.

**Why this doesn't reopen 0008.5's rejected gRPC-style alternative.** 0008.5
considered and rejected a persistent bidirectional channel specifically
because it "reintroduces … a sandbox **ingress path** (an anonymous port …
or a heavyweight private tunnel) and a **connection-bound, stateful** run
that dies with its controller instance." This sketch has neither problem:
no port is opened on the sandbox — the controller still only *calls out*
through the ADC data plane, exactly as it does for `inbox/{run_id}.json`
today — and nothing is connection-bound: step 4 is a stateless poll of a
file, so it inherits the transport's existing connectionless,
instance-death-survivable character rather than working around it.

**Reattach composes for free.** If the controller instance that would have
handled step 2 recycles first, 0008.5's existing reattach model already
covers it: any later controller instance resumes `read_events` from
`Last-Event-ID`, sees the still-unresolved `workflow_tool_call_requested`
record (no result file yet exists for that `request_id`), and can service
it — the same "any instance can reattach and continue driving the journal"
property 0008.5 relies on generally. The Durable-side call this triggers
should itself be idempotent per `request_id` (mirroring the deterministic,
session-derived instance-ID pattern `workflows/context.py` already uses for
workflow instance IDs), so a duplicate service attempt after a recycle is
safe rather than a new failure mode to invent.

**Sandbox-side blocking is a local, not a lifecycle, concern.** Step 4 has
the sandbox's own run process waiting on a local file. That process is, by
definition, already "blocking" for the duration of that tool call from the
calling agent's perspective — a `start_workflow` call is conceptually
synchronous to the reasoning loop either way. It does not interact with the
*controller* instance's own lifecycle: the sandbox process is what is
executing the turn regardless of which controller instance happens to be
polling it, so a controller recycle during the wait changes *who* services
the request, not *whether* the sandbox can keep waiting for the answer.

**What this reduces the earlier "new surface" concern to.** The concrete
ask is narrower than an unproven new transport mechanism: one new typed
journal record (sandbox→controller, no new verb — it rides inside the
existing `read_events` path) plus one narrowly-scoped controller→sandbox
write target (mechanically identical to what `submit` already does for
`inbox/{run_id}.json`, just addressed at a sub-path of an *existing* run
instead of a new one). Whether 0008.5's owner wants to formalize the write
side as a seventh transport verb (e.g. `deliver_async_result(run_id,
request_id, payload) -> ok`) or as an unversioned convention inside the
existing file layout is exactly the scoping question this document poses to
0008.5 in [Open questions](#open-questions--iterate-here) below — either
shape reuses mechanism that is already spiked and measured, not mechanism
that still needs proving.

**Latency, more precisely.** Using Decision 26's measured numbers instead of
a rough estimate: a control-plane tool call through this bridge costs
roughly one `read_events` poll cycle's visibility latency (~1.14 s p95,
measured) plus one small file write/read round trip (~0.5–0.6 s for a 1 MiB
file; these payloads will typically be far smaller), on top of the actual
Durable operation's own latency (sub-second for `start_new` / `get_status` /
`raise_event` / `terminate`). Call it on the order of **1–3 seconds per
control-plane call**, rather than the earlier, vaguer "one extra controller
round trip" — a more specific, citable number, and one that still lands on
Dynamic Workflows' already coarse-grained API surface (start/poll/cancel),
not a per-DAG-step cost.

### (b) Sandbox→controller callback bridge for workflow *step* execution

A more ambitious variant: keep the orchestrator on the controller (as in
(a)), but let individual DAG nodes' `@workflow_tool` bodies execute *inside*
the sandbox — e.g., because they depend on per-session sandbox state — by
having each `context.call_activity(...)` invocation call back into that
session's sandbox mid-orchestration, wait for a result over the transport,
and return it to the orchestrator.

- **Security / trust domain.** Weaker than (a): the controller must now
  target a *specific, already-running* sandbox instance mid-orchestration.
  Durable's replay model can invoke an activity more than once for the same
  logical step on retry/replay — this requires the sandbox-side callback
  handler to be strictly idempotent, or a new de-duplication layer.
- **Latency / availability coupling.** Materially worse than (a): if the
  sandbox is suspended (0008.8) or has been reaped since `start_workflow`
  was called, every DAG step — not just the initial call — now depends on
  sandbox liveness/resume latency. This reintroduces exactly the concurrency
  question 0008.5 flagged and set aside when it rejected a live
  bidirectional channel: the callback needs an ingress path into a specific
  sandbox, which is the thing the transport was deliberately designed
  without.
- **Run-liveness window mismatch (sharpens the point above).** The deep dive
  under (a) shows *why* (a)'s bridge fits cleanly: `start_workflow`'s
  calling run is, by construction, still active and being polled via
  `read_events` for the entire duration of the request/response pair it
  needs. (b) does not have this property. `start_workflow` returns
  immediately and the calling run typically reaches a terminal state — its
  journal no longer being actively polled — long before a later DAG step is
  scheduled, since DAG execution is deliberately decoupled from the
  initiating chat turn (mechanics section, point 4). So (b) cannot simply
  reuse "write into the currently-open run's journal": it would need to
  either keep a sandbox run open for the workflow's entire duration
  (defeating the point of `start_workflow` being fire-and-forget) or invent
  a separate mechanism to wake a specific sandbox and inject a
  step-execution request outside any active run's lifecycle — a materially
  bigger, unproven lift than the request/response pair (a) needs inside an
  already-live run.
- **Checkpoint / resume.** Weak: an in-flight DAG becomes unable to
  complete if its sandbox has been torn down, a failure mode (a) does not
  have, since (a) never depends on sandbox liveness after the initial
  `start_workflow` call.
- **Failure modes.** Worse than (a) for the reasons above; also raises an
  open question this document does not resolve — whether workflow tool
  *node* execution truly needs sandbox-local state at all. (Per the
  mechanics section, the controller *already* independently discovers and
  registers the same `@workflow_tool` functions from the same code —
  under 0008.6's capture-from-disk packaging model (Decision 68), the
  controller captures its own `/app` from its script root and delivers it
  to the sandbox over the transport, so both run byte-identical code —
  meaning in the common case the controller can run workflow *nodes*
  itself, exactly as `in_process` does today, without any callback at all.
  (b) is only motivated if some workflow tool genuinely needs live
  sandbox-resident state, which this document has not found a concrete
  example of.)
- **Verdict.** Not recommended as a starting point; revisit only if a
  concrete use case requires workflow-node execution to observe sandbox
  state that the controller's independent copy of the same tools cannot
  reconstruct.

### (c) Sandbox-local shim / MCP bridge

Give the sandbox a local, in-process DAG runner that fakes the five
control-tool interfaces without any Durable orchestration — or, as a
network-reachable variant, an MCP server exposing the same five operations.

- **Security / trust domain.** The in-process variant needs no new egress
  and no controller round trip at all — but see below. The MCP variant
  needs either a controller-hosted MCP endpoint (functionally a slower,
  extra-hop version of (a)) or a new externally-reachable endpoint, which
  would need an explicit, reviewable egress-allowlist exception to 0008.9's
  default-deny-from-creation posture — undercutting "no bootstrap window to
  protect" for a workflow-shaped bootstrap window instead.
- **Latency.** Best of the four for the in-process variant (no round trip);
  worst for the MCP-external variant (network hop plus whatever the remote
  endpoint's own latency is).
- **Checkpoint / resume.** Weakest of the four for the in-process variant:
  FRD 0004's own Decision 1 already considered and rejected "in-process
  scheduler" as the workflow execution backend, choosing Durable Functions
  specifically for its durability/checkpointing semantics. An in-sandbox
  shim would either reinvent Durable Task Framework's replay/checkpoint
  model from scratch (a large, easy-to-get-wrong undertaking) or lose
  in-flight DAG state on every sandbox suspend (0008.8) — a durability
  regression versus what `in_process` deployments already get today.
- **Failure modes / behavioral parity.** A shim creates two divergent
  execution semantics for the same `workflows.enabled: true` front-matter
  flag depending on backend (`in_process` gets real Durable guarantees;
  `aca_sandbox` gets a shim's weaker ones) — in tension with 0008.7's own
  rationale for fail-closed gates generally: a quiet downgrade in semantics
  is the kind of surprise Decision 36 exists to prevent, even where it
  isn't literally a silent *feature* drop.
- **Verdict.** Not recommended: it reopens a design point FRD 0004 already
  closed, and weakens durability guarantees relative to the existing
  `in_process` backend for a feature whose entire premise is durability.

### (d) Explicitly out of scope for ACA v1 (and possibly v2)

Keep 0008.7's Decision 36 exactly as it stands, indefinitely, until product
demand justifies (a). This is the status quo, not a new design.

- **Security.** Strongest possible — zero new surface.
- **Latency / checkpoint / failure modes.** Not applicable; the feature
  combination simply does not exist for ACA-backed agents.
- **Cost.** A real, acknowledged feature gap. 0008.7 itself notes: "the
  Workflows/Dynamic-Sessions rejection is a real feature gap. Users
  combining ACA sessions with Dynamic Workflows … simply can't in v1;
  whether that combination is commonly wanted is an open product question."
  This document has not attempted to answer that product question.

### Leading candidate

**(a), controller-side orchestration with sandbox-side proxy tools**, is the
candidate this document would recommend investigating first, for three
reasons converging on the same conclusion: it needs no new sandbox egress,
it needs no new sandbox-resident credentials, and — per the mechanics
section — it needs no new *orchestrator*, only a bridge for exactly five
already-well-defined control-plane tool names. This is offered as a
recommendation for human review, not a decision; see
[Decisions-log-style note](#decisions-log-style-note-non-binding) below.

## Alternatives considered & why they were set aside before reaching the candidate list

- **Run the Durable Functions extension directly inside the ACA sandbox.**
  Rejected before being listed as a headline candidate: it directly
  contradicts 0008.1 Decision 13 and the parent's Non-goal against modifying
  Functions Host/worker protocol, requires a second execution substrate
  inside a sandbox sized for "harness + fixed entry point" only (0008.6),
  and would need new egress to a task-hub backend that 0008.9's Decision 10
  has no room for by default. Effectively "make the sandbox a Functions
  Host," which the parent FRD's whole premise is to avoid.
- **Mandate Durable Task Scheduler reachability via a universal egress
  allowlist entry as a precondition for `workflows.enabled` under ACA.**
  Considered as a way to make candidate (b) tractable by giving every
  workflow-enabled sandbox direct DTS access. Set aside rather than promoted
  to a standalone candidate: it only removes one of (b)'s several problems
  (no controller round trip) while leaving the harder ones (replay-time
  idempotency, sandbox-liveness coupling, ingress-path re-litigation) intact,
  and it still needs a new hole in default-deny egress that (a) does not.
  Its useful half (egress-for-DTS) is really a variant of (b)'s trade-offs,
  not an independent design.
- **Treat workflow control calls as "just another MCP tool call."** This
  collapses into candidate (c)'s MCP-bridge variant once the "server" in
  question is asked where it actually executes the Durable operations — it
  is not a genuinely distinct design, only a different transport skin over
  either (a) or (c).

## Honest critique

**Strengths.**

- The core finding — that the controller-side orchestrator already exists
  and is already wired, unconditionally on front matter, regardless of
  execution backend — is grounded directly in `app.py`'s composition pass,
  not inferred. It meaningfully changes the shape of "what a fix needs" from
  "build a new system" to "bridge an existing one," which should make any
  future FRD's scope smaller and more bounded than a first read of Decision
  36 might suggest.
- Every incompatibility claim in this document traces to a specific decision
  or quoted passage in a sibling/parent FRD (0008.1 Decision 13, parent
  Non-goals, 0008.6's packaging description, 0008.9 Decision 10, 0008.5's
  verb set and its own rejection of a bidirectional channel, 0008.13's
  co-location precedent) rather than to this document's own assumptions —
  the "why" is substantiated, as requested, not restated.
- The candidate ranking follows directly from constraints those sibling FRDs
  already established (no new sandbox ingress, no new sandbox credentials,
  no second execution substrate), rather than from a fresh set of
  preferences invented here.

**Risks / assumptions.**

- ~~This analysis assumes 0008.5's transport can be *extended*…~~ **Resolved
  by 0008.5's owner** (their commit `3c4b804`, in response to this
  document's routed question): the carrier mechanism is confirmed sound —
  it reuses proven file primitives and correctly avoids the previously
  rejected gRPC-style channel (stateless, connectionless, no ingress) — but
  it is ruled **not** an acceptable unversioned convention. It must be a
  formal, versioned protocol capability, gated by `protocol_version` /
  `ensure_ready`, because an unrecognized request would silently hang the
  proxy tool forever rather than failing safely, and because it is the
  first *sandbox-initiated* interaction in a transport whose six existing
  verbs are all controller-initiated — a materially different reliability
  surface (idempotency, cancellation-while-pending, reattach-after-recycle)
  that 0008.5 judged needs explicit sign-off, not silent convention. 0008.5
  recommends shaping it as a **generic reverse-RPC verb pair** — e.g.
  `request_host_call(run_id, request_id, op, args)` /
  `deliver_host_call_result(run_id, request_id, payload)` — with the five
  workflow control-plane operations as `op` values, rather than a
  workflow-specific mechanism, so other future brokered controller calls can
  reuse the same reverse channel. This does not change v1 scope: no seventh
  verb is added now, since Dynamic Workflows is not sandbox-resident in v1;
  0008.5 has recorded this as a forward-looking constraint in their own
  dependency ledger and offered to help shape the verb pair when a real
  implementation FRD picks this up.
- Candidate (a) assumes the five control-plane tools are the *only* thing
  that needs a bridge — i.e., that no `@workflow_tool` DAG node genuinely
  needs live sandbox-resident state. This document found no concrete
  counterexample in the current tool set, but it is an assumption about
  future authoring patterns, not a proof.
- This document has not investigated the observability/telemetry
  implications of a workflow's orchestration instance living entirely on the
  controller while the session's other spans live in the sandbox (0008.13
  flags an analogous "telemetry nests in-sandbox" correlation problem for
  delegation) — likely a real gap in candidate (a) that a follow-on FRD
  would need to close.
- The soft-fail behavior in `workflows/tools.py` (`_NO_CLIENT_MESSAGE` when
  `durable_client` is `None`) was read as reinforcing evidence for why
  0008.7 chose a hard startup-time gate over relying on the tool's own
  runtime degradation — but this document did not interview 0008.7's
  authors to confirm that was in fact their reasoning; it is this document's
  inference from the code, not a confirmed fact about their decision
  process.

**Reconsider triggers.**

- If product feedback shows ACA-sandbox users routinely want Dynamic
  Workflows, the cost/benefit of building candidate (a) changes from
  "nice bounded idea" to "should be scheduled" — 0008.7 itself frames this
  as the open product question this document does not answer.
- If 0008.5's transport is redesigned (e.g., the "gRPC option" it mentions as
  a future alternative to the file/exec journal) before any workflow
  compatibility FRD starts, candidate (a)'s "extend the existing verb set"
  premise should be re-evaluated against whatever the new transport
  natively supports — a live bidirectional channel might make (a) *and* (b)
  both easier, which would be worth revisiting at that time.
- If a future `@workflow_tool` authoring pattern emerges that clearly needs
  sandbox-resident state mid-DAG, candidate (b) should be re-opened rather
  than dismissed — this document's rejection of (b) rests on not having
  found such a case yet, not on a structural impossibility.
