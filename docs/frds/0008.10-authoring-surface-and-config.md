> in plain language, one self-contained decision area from the reviewed parent.
> It re-decides no *parent* architectural decision. **Finalized 2026-07-23** (Human
> sign-off); the parent 0008 remains *In review*.
>
> **Note on decisions:** unlike its sibling sub-FRDs, this area owns *no*
> Decisions-log number of its own. The authoring surface is a *consequence* of
> other decisions — the opt-in backend (Decision 12, in 0008.1), MAF-only harness
> (Decision 34, in 0008.7), and fail-closed on unsupported features (Decision 36,
> in 0008.7). It is kept as a standalone sub-FRD because its **config shape** carries

## What this is and why it matters

Everything else in FRD 0008 is machinery; *this* is the part an app author
actually touches. It defines the small block of configuration that turns the ACA
Sandbox backend on and points it at the right resources. The design keeps this
surface deliberately tiny and **non-secret**: the author selects the backend and
supplies a single non-secret resource *identifier* (plus one optional app-level
retention override); all the sensitive and operational
settings (identities, storage/state access, and egress *enforcement*) stay in
*deployment* configuration, not in agent authoring files.

An **ACA Sandbox** is an isolated Azure Container Apps container that runs the
agent; a **harness** is the engine that runs the agent loop inside it (v1 supports
only **MAF**, the Microsoft Agent Framework). This sub-FRD is where those choices
become a line of YAML.

## The authoring surface

The backend is an **app-level** choice in `agents.config.yaml`; v1 does *not* allow
per-agent sandbox-group overrides:

```yaml
session_runtime:
  provider: aca_sandbox       # in_process (default) | aca_sandbox
  harness: maf                # only supported v1 value
  aca_sandbox:
    sandbox_group_resource_id: $ACA_SANDBOX_GROUP_RESOURCE_ID
  retention:                  # OPTIONAL app-level override of the group lifecycle defaults
    auto_suspend_idle: 5m     # idle → suspend; ACA-supported: 1m/2m/5m/10m/30m/1h
    reclaim_idle: 24h         # idle → delete; also caps how long a terminal async result stays fetchable
```

There is **no run-duration field in this block**. Run duration reuses the agent's
existing authored `timeout` (see the rules below and the iteration log); v1 keeps a
single duration knob to avoid two names for one thing (0008.1). The optional
`retention` block is the **one app-level** (not per-agent) override of the deployment
lifecycle defaults (idle-suspend / idle-reclaim) — see the rules below. There are
also **no packaging fields** here: the sandbox **disk** and the agent **content** are
not authored. The **disk** is a runtime-provided generic harness image (pinned by
digest in customer IaC, 0008.4); the **content** is **captured by the controller from
its own script root at session start** and delivered over the transport (0008.6
Decision 68) — there is no IaC-pinned Run-From-Package artifact for the sandbox to read.

Rules that define this surface:

- `provider` defaults to **`in_process`** (today's behavior); `aca_sandbox` is the
  opt-in.
- `harness` defaults to **`maf`**; unknown or not-yet-supported values **fail
  startup** (this is the authoring-side face of Decision 34/36 in 0008.7).
- `sandbox_group_resource_id` is the **one non-secret deployment identifier** that
  selects the Sandbox Group (0008.4); its **region is derived** from the resolved
  group (the group's ARM `location`), not authored. Environment substitution follows
  existing config behavior.
- **No packaging fields on the authoring surface.** The sandbox **disk** and the
  agent **content** are *not* authored here. The **disk** is a runtime-provided generic
  harness image referenced by pinned digest in the **deployment/IaC plane** (0008.6;
  0008.4 residency). The **content** is **captured by the controller from its own
  script root at session start** and delivered over the transport — **not** an
  IaC-pinned Run-From-Package zip or per-plan Blob artifact (0008.6 Decision 68). A
  v1 custom disk image (an IaC-plane escape hatch, not an authoring field) must still
  be **MAF-conformant** — v1 is **MAF-only** (parent §221; 0008.7); a **non-MAF /
  bring-your-own harness image is deferred** to a separate FRD.
- Run duration is governed by the **existing authored `timeout`** on the agent
  (today's `ResolvedAgent.timeout` / `runner.run_agent(timeout=)`), **not** a new
  `session_runtime` field — v1 keeps one run-duration knob (0008.1). For a session
  sandbox the **entry (coordinator) agent's `timeout`** is the single run-level
  budget; co-located subagents never extend it (bounded by `min(subagent timeout,
  coordinator remaining)`, per FRD 0007 / 0008.13). It yields two derived bounds:
  the sandbox **watchdog** = `timeout` (0008.8), and the sync-wait cap =
  `min(timeout, 180s)` (0008.11, Decision 19). `in_process` keeps today's behavior
  (no 180 s cap, Decision 12). Auto-suspend is disabled only while a run is active.
- **Egress is derived, not a new authoring field (v1).** The controller computes the
  sandbox's deny-by-default allowlist as the **union of existing capability config**
  (MCP server URLs, `web_request` `allowed_hosts`, the model endpoint); the egress
  proxy enforces it (0008.9). No new `session_runtime` egress field is needed — see
  *Credentials & egress* below.
- Identities and storage/state access remain **deployment configuration**, never
  copied into agent frontmatter (0008.3, 0008.8, 0008.12). Lifecycle/retention
  **defaults** likewise live in deployment (the Sandbox-Group lifecycle policy, IaC),
  with the one optional app-level override below.
- **Retention override (app-level, optional).** `retention.auto_suspend_idle` and
  `retention.reclaim_idle` are the *only* retention knobs on this surface and are
  **app-scoped, not per-agent** (never `.agent.md` front matter, so the per-agent
  authoring rule is intact). If omitted, the Sandbox-Group lifecycle policy applies
  (0008.12 owns the defaults, ~5 min / ~24 h). If set, the value **takes precedence**
  and the runtime applies it **per-sandbox at create** (0008.12; feasible on the ADC
  data plane). `auto_suspend_idle` must be an ACA-supported value
  (1m/2m/5m/10m/30m/1h); `reclaim_idle` is a positive duration that must exceed
  `auto_suspend_idle`, and also bounds how long a terminal async result stays
  fetchable (0008.11/0008.12). Retention applies only to the `aca_sandbox` provider.
- **App runtime prerequisite (v1).** The `aca_sandbox` backend requires the Functions
  app to be **Linux, x86_64, Python 3.13/3.14** — the generic harness image's ABI,
  inherited from the Functions Python base image (0008.7/0008.6). In practice this
  means **Flex Consumption** (or Premium/Dedicated Linux), since Linux Consumption
  tops out at Python 3.12. Revised Path-1 imports the app's captured content (incl.
  vendored `.python_packages`) without rebuilding, so a mismatched OS/arch/Python minor
  **fails fast** (validation-matrix row 12); there is no in-sandbox fallback.
- The legacy `runtime:` frontmatter key stays **ignored** and is not reused.
- Per-agent harness selection is **deferred** until the app-level model
  proves insufficient.
- Non-HTTP triggers always use `in_process` in v1; translation rejects opting a
  trigger into persistent sandbox execution (reserved for FRD 0009).
- `workflows.enabled` and nested Dynamic Sessions code-interpreter config are
  **rejected** with the ACA backend until their compatibility designs land (0008.7).
- Production deployment additionally supplies the dedicated **state-storage**
  account (the `AzureFunctionsAgentsStateStorage` app setting — 0008.3 Decision 31;
  Table + container, Shared Key disabled, scoped RBAC) as *identity-based app
  settings* — these trust resources are **not** agent authoring fields (they belong
  to 0008.3, finalized; Key Vault signing was dropped in Decisions 32-R/39-R).

The parent is explicit that **exact field names remain subject to the ACA SDK
spike and schema review**; what this FRD fixes is the *semantic boundary* —
global backend selection plus a non-secret resource identifier — not the final
key name.

### Credentials & egress (authored vs. provisioned)

*Consequence of 0008.9 (egress/credentials) — cross-referenced, not restated.*

**Egress allowlist.** Authors don't hand-write a separate sandbox allowlist. Egress
intent is expressed through the **existing `web_request` `allowed_hosts` + per-host
`auth` model (FRD 0005)** — an allowlist plus optional typed secret-refs in `auth`
headers (`env` today; `managed_identity` / `key_vault_ref` forward-compatible),
extended across the other capabilities. The controller compiles the deny-by-default
policy as the **union** of that `web_request` allowlist, MCP server URLs (`mcp.json`),
the model endpoint, telemetry, and the (future) broker; the out-of-sandbox **egress
proxy** enforces it at the sandbox boundary. Consistent with **one app = one trust
domain** (FRD 0005/0007), that authored union *is* the allowlist; a deploy-time
operator **ceiling** the author can't exceed is a *possible future hardening*, **not**
a v1 guarantee. **Ownership:** the authoring *shape* is this sub-FRD's + FRD 0005;
**compile-to-egress-policy, ordering lint, and `auth`-profile → proxy-`Transform`
mapping are 0008.9's**. On the sandbox backend an `env` static-secret ref can't
resolve in-workload, so it maps to a `key_vault_ref` or managed-identity `Transform`
(the class (b)/(c) split below). No new `session_runtime` egress field is introduced
in v1.

**Credentials fall into three classes**, each with a fixed home:

1. **Controller trust resources** — the dedicated state-storage endpoints (Table +
   container, Shared Key disabled + scoped RBAC). Consumed by the *controller*
   (Function App) as app-settings; **never authoring** (0008.3). *(Key Vault signing
   was removed in 0008.3 Decisions 32-R/39-R.)*
2. **Tool / MCP credentials** — authored via the MCP `header_provider`; resolution
   differs by backend:
   - **Local backend (`in_process`):** unchanged — `$ENV` / static-secret references
     and in-worker `DefaultAzureCredential` both resolve **in-process**.
   - **Sandbox backend (identity-less):** the sandbox holds **no managed identity** and
     no AAD token — in-sandbox `DefaultAzureCredential` / IMDS find nothing, so the
     harness must **not** rely on it. Outbound auth for allowed destinations
     (**including MCP servers**) is **brokered externally by the egress proxy via
     credential injection** — a proxy-side MI `Transform` (primary), else a Key Vault
     reference / static secret from the **Sandbox Group Secrets store**. (Parent
     Decision 66, which supersedes 0008.9 #56/#57; carrying the app's assigned MI into
     the sandbox — the earlier #56/#57 mechanism — is **deferred**.) Still MI, *not*
     user OBO.
3. **Egress-destination auth (sandbox backend)** — **proxy-injected**, never an
   authoring field: prefer a managed-identity `Transform` (no secret ever enters the
   workload); fall back to a static secret the operator mirrors into the
   **sandbox-group Secrets store** (0008.9). Closest precedents: APIM/Envoy
   egress-gateway credential injection, and this repo's in-process MCP
   `header_provider` — the sandbox backend moves that same injection *out of the
   workload* into the egress proxy.

The one remaining authoring identifier (`sandbox_group_resource_id`) is
non-secret, so env-substitution here carries no secret-smuggling risk.

## Startup validation matrix (fail-closed)

The backend is **fail-closed** (0008.7 Decision 36): unsupported or inconsistent
config **stops startup** with a specific error rather than degrading silently. Two
planes are validated — the **authoring plane** (this block's shape) and the
**two-plane / trust** checks that cross-check the deployment trust resources
(0008.3). For the trust rows the **config/surface placement is owned here; the
runtime assertion is 0008.3's** — and 0008.3 (finalized 2026-07-22) makes this
preflight **required for v1**.

- **Absence of a `session_runtime` block is not an error** — it selects the default
  `in_process` backend (Decision 12); none of the rows above apply.
- Rows **6–8** are the concrete content of the two-plane preflight (see the open
  question). After 0008.3's finalization they are *required*, and **no Key Vault
  signing key** is checked (dropped in 0008.3 Decisions 32-R/39-R).
- Rows **9–11** validate the optional `retention` override; 0008.12 owns the applied
  defaults and the per-sandbox-at-create application.
- Row **12** is a **platform ABI** cross-check: revised Path-1 (0008.6) imports the
  app's captured content — including vendored `.python_packages` — into the generic
  harness image **without rebuilding**, so the app runtime must match the image
  (Linux, x86_64, Python 3.13/3.14 — in practice Flex Consumption, since Linux
  Consumption caps at 3.12). 0008.7 owns the ABI definition; there is no in-sandbox
  fallback, so it fails fast at deploy/config time.
- Row **13** is a **lifecycle** cross-check protecting the **authored-retention
  promise** — *not* v1 core correctness (no live session is ever deleted, and the
  reaper reclaims first by design). `reclaim_idle` is author-owned (raised without
  IaC) while the Sandbox Group **`auto_delete`** backstop is operator IaC, so an author
  could ask for more retention than the backstop honors. Terms (0008.12-owned,
  **seconds**): **`cadence`** = the configured reaper interval (**v1 ~1 h** default,
  operator-tunable — *not* the v2 ~1-min mirror SLO); **`grace`** = a fixed 0008.12
  safety buffer (~5 min / 300 s). The comparison is inclusive `≤`, so it **fails iff
  strictly `>`**. When the group `auto_delete` is **readable** at config time this is a
  **hard fail**; when **not readable** it **warns** (non-blocking) and the runtime
  reaper **clamps** to `min(reclaim_idle, auto_delete − cadence − grace)` (logged), so
  the degraded path is well-defined (0008.12 commit 80a4905). **0008.12 owns the
  inequality + terms; 0008.10 enforces at config/registration.**
- Message strings are **illustrative**, pending the Pydantic `config/schema.py`
  implementation and the ACA SDK spike.

## Alternatives considered & why the choice won

This area owns no Decisions-log entry, so there is no formal alternative table to
restate. The shape above is the authoring-surface *expression* of decisions made
elsewhere, and it embeds two implicit design stances worth naming:

- **App-level, not per-agent.** A single global `session_runtime` block (rather
  than per-`.agent.md` overrides) — deferring per-agent selection until proven
  necessary. This follows the parent's "keep the surface minimal" posture and the
  one-Sandbox-Group-per-app residency in 0008.4.
- **Non-secret identifiers only.** Trust/operational config (egress *enforcement*,
  identities, storage/state access) lives in deployment settings, keeping authoring
  files safe to commit and share.

Where these lean on formal decisions, they are cited to their owning sub-FRD
(0008.1 #12, 0008.7 #34/#36, 0008.4 #30) rather than duplicated here.

## Honest critique

**Strengths.** A tiny, non-secret, app-level block is the right authoring surface:
it keeps secrets out of source control, makes the opt-in explicit, and fails
startup loudly on unsupported values instead of degrading silently. Reusing
existing env-substitution behavior means no new authoring concept for users to
learn.

**Risks / assumptions.**
- **Value format (not the key name) is the residual.** The authored key
  `sandbox_group_resource_id` is **locked** (see the iteration log); only its accepted
  **value format** (full ARM resource ID vs. an SDK handle) + Pydantic validation
  remain pending the SDK spike. *(Run-duration, `disk`, `content_package`, and `region`
  are settled — see the iteration log.)*
- **App-level-only may be too coarse.** A project with several agents of very
  different risk/resource profiles can't give one agent a different sandbox-group in
  v1; if that need is common, the deferral bites.
- **Config/behavior coupling is easy to get wrong.** Several fields *fail startup*
  in combination (`harness` ≠ maf, `workflows.enabled` + aca, non-HTTP trigger +
  aca, missing group). The validation matrix is broad and must be
  precise, or authors get confusing startup errors.
- **Two config planes to reconcile.** Authors set the `session_runtime` block, but
  operators set the *matching* trust resources (the dedicated state storage) as app
  settings; a mismatch between the two planes is a likely support issue.

**Reconsider triggers.** Revisit if: the SDK spike forces a change to the accepted
`sandbox_group_resource_id` **value format** (the key name is locked); real
multi-agent projects need per-agent sandbox-group selection; or the fail-startup
validation matrix proves too confusing and needs consolidation into clearer
diagnostics.
