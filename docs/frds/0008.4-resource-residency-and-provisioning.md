# FRD 0008.4 — Resource residency & provisioning boundary

> Sub-FRD of [FRD 0008](0008-aca-sandbox-session-runtime.md). It re-expresses,
> in plain language, one self-contained decision area from the reviewed parent.
> The core decision (Decision 30) is **unchanged** from the parent; this sub-FRD
> additionally resolved its five open questions as *scope refinements* (Human,
> 2026-07-22) without altering that decision. **Status: Finalized** — human sign-off
> recorded 2026-07-22 (see [Status & sign-off](#status--sign-off)).

## What this is and why it matters

Running an agent inside an **ACA Sandbox** (an isolated Azure Container Apps
container) needs some Azure infrastructure to exist first: a **Sandbox Group** (the
parent resource that sandboxes are created under), a disk image, identities, an
egress/network policy, storage, and role assignments. Someone has to own,
provision, and pay for all of that.

This area draws the line between *who creates the standing infrastructure* and
*what the runtime creates at request time*. The decision: all standing resources
live in **the customer's own Azure subscription** (the application owner's
subscription — not Microsoft's, not the end user's), with **one Sandbox Group per
Function App/environment**. The customer's deployment tooling (Infrastructure as
Code) creates the durable resources and role assignments; the running product
creates only *individual session sandboxes* through the ACA data plane. This
mirrors how the existing ACA Dynamic Sessions feature already works: sample IaC
creates the pool, and the runtime only consumes its endpoint.

## Decisions this sub-FRD owns

- **Decision 30 — Sandbox resource residency & provisioning split.** One Sandbox
  Group per Function App/environment, in the *customer's* subscription. A
  Microsoft-owned central multi-tenant Sandbox Group is rejected. Customer IaC
  creates ARM resources + RBAC; the runtime creates only individual sandboxes.

### The provisioning boundary (parent §4.2)

Two roles, two responsibilities:

| Actor | Creates | How |
| --- | --- | --- |
| **Customer deployment tooling** (runs *as the customer*) | The Sandbox Group **and its group-level lifecycle policy** (autosuspend idle-timeout + auto-delete idle-retention window; the default/fallback — the runtime may override lifecycle per-sandbox at create via the data plane); a **reference to the runtime-published generic bootstrap image** (a stdlib-only boot/base disk that bakes **no MAF or agent runtime**; pins its digest/version — it does *not* author the image contents); the dedicated state account; identities; egress policy; and *scoped* role assignments. | ARM / IaC, once per app/environment. |
| **The runtime** (the controller) | Only individual per-session sandboxes (create / resume / delete). | ACA data plane, using **SandboxGroup Data Owner** scoped to that *single* group. |

The runtime *never* creates or updates ARM resources. This keeps a clean privilege
split: the powerful "create infrastructure" rights belong to a deployment identity
the runtime never uses, while the runtime holds only the narrower data-plane right
to manage sandboxes inside one pre-created group.

The **Sandbox Group lifecycle policy** (session autosuspend idle-timeout and
auto-delete idle-retention window) illustrates this split cleanly, and it has **two
tiers** that fall on opposite sides of the Decision 30 line:

- **Group-level lifecycle policy (ARM / control plane) → customer IaC.** This is a
  configuration *of* the customer-owned Sandbox Group, so customer IaC sets it **at
  deploy time** and the runtime **never reconfigures the group** at runtime. It is the
  default/fallback applied to sandboxes that specify no override.
- **Per-sandbox lifecycle override at create (data plane) → runtime.** Under the
  hybrid retention model (0008.12), the runtime **may set a sandbox's own auto-suspend /
  auto-delete lifecycle when it creates that sandbox**, using the *effective* retention
  value resolved from the config hierarchy below — a per-sandbox **data-plane** write on
  a resource the runtime itself created, squarely within its existing "per-session
  create/resume/delete" scope (**SandboxGroup Data Owner**). This adds **no new
  privilege**: 0008.8 (Decision 27) already performs per-sandbox lifecycle writes
  (disabling auto-suspend during an active run). It lets retention be
  runtime/app-controllable *without* the customer editing the group IaC, while the
  group-level ARM policy — and the residency of the group — stay customer-owned.

Ownership of the *values* follows an idle-based **three-tier hierarchy** (master-log
Decision 64; [0008.10](0008.10-authoring-surface-and-config.md)), most-specific wins:

1. **Group-level default (ARM)** — the customer-owned Sandbox Group lifecycle policy set
   by customer IaC at deploy; the fallback when nothing more specific is set. 0008.4 owns
   *where* this lives (the customer-owned group);
   [0008.12](0008.12-lifecycle-failure-and-reconciler.md) owns its defaults.
2. **App-level `session_runtime.retention` (live in v1)** — an app-scoped authoring field
   owned by [0008.10](0008.10-authoring-surface-and-config.md); overrides the group
   default for the whole app.
3. **Per-agent `.agent.md` override (deferred to v2)** — a future per-agent field that
   would override the app-level value; not part of v1.

The runtime resolves the effective value from this hierarchy and applies it as the
per-sandbox override at create (the runtime-tier bullet above). So retention **is**
expressed via `session_runtime.retention` in v1 — 0008.4 retains only ownership of the
**group-level default's residency** (that it lives on the customer-owned group), not the
authoring surface. This mirrors how egress policy appears in the row above: listed here as
customer-provisioned standing infrastructure, with its design/authoring owned by the
relevant sibling.

**Who controls the sandbox image?** The runtime project does — but under Model-1
(master-log Decision 69) the image is deliberately **minimal**. The generic sandbox
disk is a **stdlib-only bootstrap/base image**: it boots the sandbox and starts the
entry point, but it bakes **no MAF and no agent runtime**. It is **authored, built, and
published by the runtime project** (see
[0008.6](0008.6-sandbox-packaging-image-and-content.md), Decisions 8/17) and is
*generic*: byte-identical for every customer and every agent. The code that actually
**speaks the controller↔sandbox protocol and drives the MAF harness** does **not** live
in the image — it rides in the customer's **captured `.python_packages`** (the runtime
library vendored into the app's script root), which the controller captures and delivers
into the sandbox at create over the 0008.5 transport (Decisions 68/69). Customer IaC
does **not** build the image; it *references a published, digest-pinned image*
and provisions a copy into the customer's Sandbox Group — much like referencing a
base container image. The customer controls *where* it runs (their subscription,
their region) and *which version they pin*, never its contents. The per-app authored
bits (`.agent.md`, `tools/`, `skills/`, `mcp.json`) — and the runtime library
itself — never enter the image; instead the
**controller captures them from its own local script root** (app code + vendored
`.python_packages`) and delivers them into the
sandbox over the **0008.5 file transport**. The **sandbox is identity-less and has no
storage access** — it never reads the deployment artifact itself. Integrity is a
**SHA-256 content digest** carried on the controller-written authoritative session row
and verified against the live sandbox manifest (0008.6 Path 1; 0008.3) — no per-artifact
signature, consistent with 0008.3's finalized trust model (Decisions 32-R/39-R). So
editing an agent re-emits the content the controller delivers and never rebuilds the
image. (The deferred Path 2 committed disk image uses the same integrity model, with
digest = the immutable committed-image disk-id.) A
customer who
needs native dependencies can build a **custom image**, but that is
0008.6's explicit escape hatch — not the default path. In **v1 that custom image must
still be MAF-conformant** (it has to pass the golden-trace conformance gate;
MAF-only v1, see [0008.7](0008.7-harness-compatibility-and-conformance.md)); a
**non-MAF / bring-your-own harness is deferred to a separate FRD**,
not a v1 escape hatch. Either way, the escape hatch does not move any
trust boundary defined by Decision 30.

**Interaction with the content-artifact model (0008.6 Decision 17-R, revised
round-2).** 0008.6 resolved (Human, 2026-07-22) that the per-app *content* layer
reuses the existing Functions deployment artifact as the Path 1 baseline, with an
optional deploy-time **committed disk image** as Path 2. **v1 scope: Path 1 only —
Path 2 is deferred.** A round-2 revision (Human, 2026-07-24, master-log Decision 66 —
identity-less sandbox; Decision 68 — controller-captured content) then changed *how*
Path 1 content reaches the sandbox — see below. Two consequences for this
boundary — both **consistent with Decision 30** (no residency or split change); the
first is v1-active, the second is deferred with Path 2:

- **[v1-active] Content stays customer-owned; sandbox is identity-less — no read grant
  needed.** *Round-2 correction (Decisions 66/68):* the earlier close (a scoped *read*
  for the Sandbox Group runtime identity on the deployment storage container) is
  **withdrawn**. Per **Decision 66** the sandbox has **no identity and no storage
  access**; per **Decision 68** the **controller captures the app content from its own
  local script root** and delivers it over the 0008.5 file
  transport. Net effect is **less** runtime data-plane footprint (one fewer role
  assignment, no sandbox-side storage reach), which *strengthens* the least-privilege
  posture behind Decision 30 rather than straining it.
- **[deferred with Path 2] Image *building* is a deploy-identity capability, never the
  runtime's.** Path 2
  runs at **deploy time as the deploy identity**, which needs sandbox
  create/exec/**commit** rights. The runtime keeps only per-session
  create/resume/delete via **SandboxGroup Data Owner** and never gains the
  commit/image-build right — so this *reinforces* the least-privilege split rather than
  blurring it. The per-deploy committed images accumulate inside the customer Sandbox
  Group (still customer-side; residency unchanged), which feeds the capacity and
  cleanup notes below.

## Alternatives considered & why the choice won

- **Sandbox resource residency (Decision 30).** Considered three models:
  1. **Customer subscription** (one Sandbox Group per app/env) — chosen.
  2. **A Microsoft-owned central multi-tenant subscription** — rejected. It would
     centralize customer content and billing, share subscription quotas and blast
     radius across tenants, complicate customer VNet/private-resource access, and
     require cross-tenant identity/OBO plus a new always-on service that this
     open-source runtime does not operate.
  3. **Delegated customer deployment** (automation still deploys *into* the
     customer subscription) — kept as the long-term DX direction, *not* a change
     of trust boundary.

  Chosen by *Agent reviewers*. The deciding principle: keep the trust boundary in
  the customer's tenant. The long-term goal is better *automation* of customer-side
  deployment, never moving customer compute/billing into a Microsoft-run plane.

## Honest critique

**Strengths.** Residency-in-customer-subscription is the only model consistent with
an open-source runtime that has no always-on operator, and it inherits the proven
Dynamic Sessions precedent. The IaC-vs-data-plane privilege split is clean and
directly enables the least-privilege RBAC in sibling 0008.3. "One group per
app/environment" gives a natural blast-radius and quota boundary.

**Risks / assumptions.**
- **Adoption friction.** The customer must stand up a Sandbox Group, disk image,
  identities, egress policy, storage, and role assignments *before*
  trying the feature. For an experimental backend that's a steep on-ramp, and this
  sub-FRD owns the resource *residency* decision but not the IaC samples that make
  it bearable (those are a docs/samples deliverable in the parent).
- **"One group per app/environment" scaling.** The pilot target is 100 concurrent
  active runs per group (see 0008.5). If a single app needs more, the model has no
  stated story for multiple groups per app — it's one-to-one by decision.
- **Preview quota reality.** ACA Sandboxes is a preview service; per-subscription
  quotas, supported regions, and group limits can change and may not accommodate
  the one-group-per-environment pattern at scale.
- **Delegated-automation ambiguity → now resolved in shape.** Previously the
  "long-term delegated automation" path was named but undefined, risking quiet drift
  toward the rejected central plane. It is now defined (see Open questions): a
  customer-run Bicep/ARM module executed under the customer's own credentials, checked
  against Decision 30's trust boundary. Residual risk is only in implementation detail
  (distribution/versioning, parameter surface), not in the trust model.

**Reconsider triggers.** Revisit if: preview quotas or region availability make
one-group-per-app impractical; a single app provably needs more than one Sandbox
Group (interacts with 0008.5's concurrency target); or the delegated-automation
module moves from shape to detailed design — its distribution, parameter surface, and
identity model must each be re-checked against Decision 30's trust boundary before
shipping.

## Open questions / iterate here

All five open questions here were **resolved on 2026-07-22 (Human)**. The
resolutions below refine — but do **not** alter — Decision 30; they clarify its
scope. The master Decisions log lives in the parent
[FRD 0008](0008-aca-sandbox-session-runtime.md); a cross-reference on the Decision 30
row is suggested there (this sub-FRD does not edit the parent).

**Resolved**

- **Group capacity vs preview quota — resolved: use defaults.** v1 relies on the ACA
  Sandboxes preview default quotas for a single group; the residency model does not
  special-case, pre-request, or design around raised quotas. Whether one group
  sustains the 100-concurrent target (Decision 29) is answered by the live-spike
  acceptance gate in [0008.5](0008.5-controller-sandbox-transport-and-protocol.md),
  not by changing residency. If the default quota proves insufficient, that surfaces
  as a 0008.5 finding — it does not reopen Decision 30. *Additional consumer (deferred
  with Path 2):* 0008.6's optional committed disk images (Decision 17-R) would also
  occupy Sandbox Group storage/quota alongside concurrent session sandboxes, so once
  Path 2 ships, 0008.5's capacity gate and any image-retention policy should account for
  them, not just live sandboxes. This does not apply to the Path-1-only v1.
- **Multiple groups per app — resolved: hard 1:1 for v1.** One Sandbox Group per
  Function App/environment is a firm v1 invariant; sharding a single app across
  multiple groups is explicitly out of scope for v1 and may be revisited later.
  *Cross-cutting note:* permitting >1 group later would require the state binding in
  [0008.3](0008.3-state-store-and-tamper-evident-trust.md) to record which group owns
  a session — no change is needed now.
- **Region strategy — resolved: customer-chosen, runtime co-locates.** The customer
  picks the Sandbox Group's region in their IaC; the runtime creates every session
  sandbox in that same region. Single region per app/environment for v1; multi-region
  and DR are a customer IaC concern and out of scope here. *Cross-cutting note:* the
  dedicated state account in [0008.3](0008.3-state-store-and-tamper-evident-trust.md)
  should be provisioned co-regional with the Sandbox Group to avoid cross-region
  latency and residency drift. This co-region invariant must also hold under DR — a
  geo-failover of the state account must not relocate it to a different region than the
  Sandbox Group. 0008.3 has since resolved multi-region/DR as **deferred (a v1
  non-goal)**, explicitly preserving this co-region invariant (no failover drift); it
  owns the DR handling if/when it lands.
- **Cleanup ownership — resolved: customer owns standing-IaC teardown.** Symmetric
  with creation — whoever's IaC created the Sandbox Group and standing resources
  deletes them, exactly as customers already manage the lifecycle of their Function
  Apps. The runtime only deletes the individual sandboxes it created via the data
  plane; it never tears down the group or any other ARM resource. *Cross-cutting
  note:* per-session / per-sandbox reclamation (idle GC, terminal-state cleanup) is
  owned by lifecycle [0008.12](0008.12-lifecycle-failure-and-reconciler.md);
  group-level teardown is outside that timer's scope. *Committed images (deferred with
  Path 2):* the following applies only once 0008.6's Path 2 ships — it is not part of
  the Path-1-only v1. Per-deploy committed disk images (0008.6 Decision 17-R) are
  standing-style artifacts created by the **deploy identity**, so pruning old image
  versions follows the same "creator owns teardown" principle — a deploy/customer-side
  concern, **not** the runtime reaper's job (0008.12 reaps only per-session
  sandboxes/snapshots, never committed images or the group). The decisive reason is
  least-privilege, not just symmetry: making committed-image GC the reaper's job would
  require granting the runtime **image
  delete/manage rights** on the Sandbox Group, re-broadening the per-session-only
  data-plane footprint that Decision 30 and the Decision 17-R note deliberately keep
  narrow. The reaper still contributes *indirectly*: by reclaiming idle/terminal
  session sandboxes it drains the references that pin a superseded image. Because the
  platform enforces the delete order (an image cannot be deleted while any sandbox
  still references it), deploy-side pruning is **best-effort and self-sequencing** — it
  simply succeeds once the reaper has drained the pinning sandboxes, so there is **no
  reaper→deploy "eligibility signal" contract to build** (a label/disk-id query, which
  0008.6 guarantees is available, is only an optional optimization to skip futile delete
  attempts). The reaper therefore emits no image-specific signal and needs no image
  rights; the reference-safe delete (child-before-parent: dependent sandboxes → child
  committed images → base image) is executed deploy/customer-side by the same deploy
  identity that built the images. Flipping this
  to runtime-owned reference-counted GC would be a **Decision 30 rights change** (the
  runtime would gain image-management rights), to be decided explicitly rather than
  absorbed silently.

- **Delegated automation — resolved: customer-run Bicep/ARM module; v1 ships
  composable sample IaC, the one-command composite module is the post-v1 target.** The
  long-term on-ramp fix is a distributable **Bicep/ARM module the customer runs via
  `az deployment` under their own credentials** (interactive `az login`, or their own
  CI/CD federated identity / service principal) — so every ARM resource, identity, and
  role assignment is created *as the customer, in the customer's subscription*. No
  Microsoft-operated identity, nothing cross-tenant, and no always-on provisioning
  service — which is exactly what keeps delegated automation on the customer side of
  Decision 30's trust boundary, and mirrors the ACA Dynamic Sessions sample-IaC
  precedent. The end-state shape is **one composite "quickstart" deployment** that
  stands up the whole standing set end-to-end — Sandbox Group, a digest-pinned
  reference to the runtime-published generic bootstrap image (0008.6), the dedicated state
  account (owned by 0008.3 — note its finalized trust redesign, Decisions 32-R/39-R,
  dropped the per-binding Key Vault signing key and the WORM binding-log, so there is
  no Key Vault resource to compose), identities, egress policy, and *scoped*
  RBAC — by **internally composing the sibling modules** (it *references* 0008.3's
  state module rather than re-authoring it) while staying decomposable for
  advanced users. **v1 scope:** ship documented, composable **sample IaC** (the module
  structure), consistent with the experimental / opt-in, preview-dependent posture; the
  polished one-command composite quickstart module is the **committed post-v1 DX
  target**, not a v1 deliverable. **Prerequisite / caveat:** because the module creates
  *scoped* role assignments, the deploying identity needs `Owner` or `User Access
  Administrator` on the target scope. *Cross-cutting notes:* (a) 0008.3's state
  resources should expose a composable module interface so the quickstart can
  reference them; (b) the module pins the bootstrap image digest, tying to 0008.6's image
  versioning; (c) the parent's on-ramp / samples narrative and master Decisions log may
  want to record this v1-vs-post-v1 split.

**Remaining implementation detail** (the decision is made; these specifics defer
downstream): the module's distribution channel and versioning (repo sample vs Bicep
public registry vs ACR), its exact parameter surface, and whether v1 docs bless a
CI/CD federated identity in addition to interactive `az login`.
