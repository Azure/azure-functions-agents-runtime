# FRD 0008.8 — Snapshot, auto-suspend & state durability

> Sub-FRD of [FRD 0008](0008-aca-sandbox-session-runtime.md). It re-expresses,
> in plain language, one self-contained decision area from the reviewed parent.
> It now also carries a **Human-decided v1 re-scope (2026-07-22)**: v1 relies on
> ACA auto-suspend/resume for durability and defers the external mirror to v2.
> **Status: Finalized** (Human sign-off, 2026-07-22). The parent master-log rows
> 9/18/27/28 and the sibling ripples (0008.3 / 0008.5 / 0008.12) still need
> matching parent/sibling-owner updates (see
> [Cross-references & boundary notes](#cross-references--boundary-notes)).

## What this is and why it matters

Keeping one **ACA Sandbox** (an isolated Azure Container Apps container) alive per
session across many turns would be expensive if it sat idle between messages. ACA
offers **auto-suspend** — freezing an idle sandbox's memory so it can resume warm
later, optionally as a **memory snapshot**. That warm resume is what makes a
persistent session affordable.

**v1 leans on the platform.** In v1 the sandbox itself — its on-disk session
directory, preserved across idle by ACA auto-suspend/resume — is the session's
durability boundary. There is **no external mirror in v1**; if the sandbox and its
snapshot are both lost, that session is lost. This is an explicit, accepted v1
limitation (best-effort durability) in exchange for dropping a large amount of
machinery. *(Decided by Human, 2026-07-22.)*

Two correctness rules still hold in v1, because they are cheap and guard against
*guaranteed* — not rare — events:

- **Resume is not "as-is".** Even if ACA restores process memory perfectly, after
  any idle window that crosses a token lifetime or a peer's idle-timeout, cached
  tokens are *expired* and peer sockets are *closed server-side*. So network
  clients, token providers, MCP connections, and leases are **recreated after
  resume**, never assumed live, and a **resume-readiness handshake** runs before
  the controller submits work.
- **No sleeping mid-thought.** **Auto-suspend is disabled while a run is actively
  executing** and a **watchdog** bounds run time — because ACA's idle reclamation
  cannot tell a busy run from an idle one (see below).

**v2 restores the stronger boundary.** The original principle — *the snapshot is
only an optimization; an owner-scoped external checkpoint is the true correctness
record* — is retained as the **v2 target**, not discarded. v2 adds the external
mirror so losing a sandbox no longer loses the session.

## Decisions this sub-FRD owns

> **v1/v2 split (Human, 2026-07-22).** v1 relies on ACA auto-suspend/resume as the
> session's best-effort durability boundary and **defers the external mirror to
> v2**. The four owned decisions are re-scoped accordingly below; the parent
> master-log rows 9/18/27/28 need a matching parent-owner update (see

- **Decision 9 — Snapshot role.** *v1:* the sandbox + its auto-suspend/resume
  **state** (the preserved on-disk session directory — *not* a separate snapshot
  resource; see the durability section) **is** the v1 durability boundary —
  best-effort. *v2:* revert to the stronger rule — a snapshot is only an optimization
  and an external checkpoint is the correctness record.
- **Decision 18 — Conversation durability.** **Deferred to v2.** v1 keeps the
  transcript only in the sandbox (the disk, preserved across idle by
  auto-suspend/resume); no owner-scoped Blob mirror and no bounded recovery checkpoint.
  v2 mirrors each completed transcript delta + a bounded checkpoint to owner-scoped
  customer Blob Storage.
- **Decision 27 — Active-run lifecycle.** *Kept in v1.* Disable auto-suspend before
  accepting a run and keep the session non-idle while it runs; a sandbox watchdog
  bounds the authored `timeout` (0008.1/0008.10 — the single authored knob; there is no
  parallel `max_run_seconds`). After a terminal state idle-suspend is restored — by the
  controller for a sync/attached run, or, for a **detached async** run where no
  controller is present at terminal, by the **v1 periodic reconciler's idle-policy
  repair** (0008.12, confirmed — see the detached-async note) — **except an *async*
  terminal keeps the session reap-protected** (auto-suspend allowed, destroy/reap
  deferred) so the sandbox-only result stays fetchable for **max(the remaining
  idle-retention window, a ~5-min floor from terminal)**; a **fetch reverts
  the session to normal idle-retention** (not an
  immediate reap). 0008.12 committed v1 retention as *idle-based, clock starting at
  terminal* (Decision 22/24), under which the full-from-terminal window already exceeds
  the floor — so the floor **never binds** and is kept only as strictly-safe insurance
  against a future retention-model change. The watchdog covers active runs only, not
  post-terminal. The reconciler's role shrinks
  (see boundary notes).
- **Decision 28 — Resume readiness.** *Kept in v1.* Treat the file/exec *operation
  result* as authoritative, recreate live clients/tokens/leases, and verify the
  protocol/session manifest after resume, because sandbox state reads can lag the
  data plane.

### How durability actually works (v1)

In v1, warm resume via ACA auto-suspend is how session state persists across idle:

- the harness checkpoints conversation + tool state to its **session directory on
  disk** inside the sandbox using a **whole-turn atomic commit**. A single turn writes
  *multiple* files (conversation history + tool working files), so per-file
  write-temp→fsync→rename is **not** sufficient — N independent renames can be caught
  half-applied by a crash *between* them. Instead the turn is committed as one
  all-or-nothing set:
  1. write turn N's **entire file set** into a staging location (e.g. `turns/N/` or a
     tmp dir), then **fsync the files *and* the directory**;
  2. **commit with one atomic operation** — a single `rename()` that advances a
     `current` pointer/manifest to name turn N as committed; that lone rename is the
     all-or-nothing commit of the whole set. The commit then **fsyncs the replacement
     pointer *and* its parent directory** (so the rename itself is durable across a
     crash/power loss) **before acking** the turn as committed;
  3. **on resume**, read `current` and **discard any incomplete staging** (e.g. a
     partial `turns/N+1/`) — i.e. roll back to the last cleanly-committed turn.

  **Soundness — three isolation requirements (rubber-duck):** the pointer-commit is
  atomic only if turn N's writes are isolated, so v1 requires all three:
  (a) **prior committed turn trees are immutable** — a committed `turns/<k<N>/` is never
  mutated in place, so the commit of N cannot corrupt an already-committed turn;
  (b) **every tool/working write during turn N is routed into that turn's private
  staging/overlay**, never in-place into the live files — an in-place tool write would
  escape the atomic set and be visible before (or survive without) the pointer flip;
  (c) **the commit fsyncs the replacement pointer and its parent directory after the
  rename, then acks** (as in step 2) — otherwise the rename could be lost on power loss
  even though the staged files were durable.

  So a silent harness crash at any point can never leave a half-applied multi-file turn:
  either the pointer advanced (turn N fully committed) or it didn't (turn N-1 stands).
  ACA auto-suspend/resume preserves that directory (and process memory) across idle
  windows;
- there is **no external mirror in v1** — the transcript and any recovery state live
  only in the sandbox. **Control-plane records stay durable**: the Azure Table
  session/run rows (status, pointer, generation — 0008.3 Decision 20, unchanged;
  authoritative per 32-R) are *separate* from the deferred Blob archive, so a
  completed run's terminal **status** survives even a lost sandbox — only the
  transcript/checkpoint **content** is non-durable in v1;
- **two failure modes, deliberately distinguished (master-log row 67):**
  - **(a) sandbox/snapshot LOST** — no recoverable disk (sandbox reaped, deleted, or
    idle-reclaimed past cooldown). The replayable content is unrecoverable in v1, so
    the session is **tombstoned**: subsequent use is **410 Gone**, any in-flight run
    **abandoned** (status mechanics 0008.12/0008.11), and **there is no resume**. The
    rebuild path that would survive this — an owner-scoped external mirror — is **v2**
    (Decisions 53/54, with 18). An accepted v1 limitation, not a defect.
  - **(b) harness CRASH with sandbox/disk INTACT** — a process fault, not a lost
    sandbox (the common case). The session **resumes on the *same* sandbox** from the
    last cleanly-committed turn: the whole-turn atomic-commit guarantee above discards
    any uncommitted staging, and the D28 / `ensure_ready` handshake verifies before new work. The
    crashed *run* is marked **abandoned** to release the one-active-run slot, but the
    *session* is **not** tombstoned — its committed disk state is intact. (So a mid-run
    crash Abandons the **run** but must **not** reclaim the **session/sandbox** — see
    the 0008.12 boundary note flagging this.) This is the case v1's in-sandbox
    durability exists to cover;
- **what preserves the disk in v1 (rubber-duck clarification):** v1 relies on **ACA
  auto-suspend/resume preserving the on-disk session directory (and process memory)**
  across idle — it does **not** provision separate, explicitly-managed ACA *snapshot
  resources*. ACA documents auto-suspend (a state of the still-existing sandbox) and
  explicit snapshot artifacts as **distinct** mechanisms; v1 uses only
  auto-suspend/resume, which is exactly why a *lost* sandbox (case a) also loses its
  co-located suspended state and is unrecoverable. An independently-stored artifact
  that outlives the sandbox is the **v2** durability work (Decisions 53/54), not v1.
  (An image/content/protocol change is handled by **drain-on-deploy (Decision 70)**,
  *not* as a snapshot-compatibility question: a redeploy is a new epoch, so a
  digest-mismatched session is intentionally **drained** — grace → abandon → tombstone
  → 410 — and the client starts a fresh session on the new epoch; see 0008.6. The only
  genuinely open item is whether ACA auto-suspend reliably preserves the disk *within a
  single epoch*.)
- on resume, network clients, token providers, MCP connections, and leases are
  **recreated** (never assumed live) — expired tokens and server-closed sockets are
  the norm after any non-trivial idle window;
- **generation identifies the sandbox backing; in v1 it is effectively fixed at
  creation.** Suspend/resume and a harness crash-with-disk-intact (case b) both resume
  the *same* backing (instance + disk), so `sandbox_generation` is **unchanged**. Per
  0008.3's definitive model (commit **7c66c07**, refining 95f5caf): a **generation
  advance is V2-ONLY** — it is a state-preserving rebind to a *different* backing
  (instance + disk), which requires the external mirror to reconstruct state, and the
  mirror is v2; so **v1 never advances the generation**. The two v1 outcomes are
  therefore only: **same backing ⇒ SAME generation** (suspend/resume, crash-restart on
  the intact disk), or **backing lost ⇒ TOMBSTONE → 410** (state unrecoverable, a new
  session — never a generation advance). So in v1: same-generation resume = the normal
  case; loss = tombstone; **a generation advance cannot occur (v2-only)**.

**Canonical loss-recovery model (v1/v2), stated as durability owner** — the reference
0008.5 / 0008.12 / parent align to. The governing **invariant** is: **tombstone ⇔ state
truly unrecoverable; generation advance ⇔ state preserved across a backing change** (and
a generation advance is v2-only — see below). From that:

- **v1 (no external mirror).** The generation is **effectively fixed at creation** — a
  **generation advance is v2-only** (it needs the mirror to rebind state onto different
  backing). So the only two v1 outcomes are: **same backing ⇒ SAME generation**
  (suspend/resume, crash-with-disk-intact — case b); or a sandbox/snapshot **LOSS ⇒
  tombstone** — a `410`, a new session must be started, **never** a generation advance
  (there is no surviving copy to rebind to).
- **v2 (external mirror).** After a **sandbox-instance loss** the session **MAY be
  rebuilt from the mirror onto a new instance** — that is a **state-preserving rebind =
  a generation advance** (per 0008.3), **not** a tombstone. A **true loss** (the mirror
  is *also* lost or unusable) still **tombstones**. Exact v2 rebuild semantics (rebuild
  trigger, transcript watermark, partial-turn handling) are **deferred to v2**.

So the v1→v2 change is precisely which events fall on each side of the invariant: v1 has
no mirror, so the generation is fixed at creation and every backing loss is a true loss
(tombstone); v2's mirror converts the *recoverable* subset of backing losses into
state-preserving generation advances, leaving only mirror-inclusive losses as tombstones.

**Active-run rule:** the controller disables auto-suspend and keeps the session
**non-idle** *before* it accepts a run, then restores idle-suspend after the terminal
state. This matters because ACA's idle reclamation is a **cooldown** (documented
range **300–3600 s**) that fires on *no requests* and then **destroys** the session
— it is idle-based, not execution-bounded, so it can neither stop a runaway *active*
run nor be trusted to leave a long async turn alone. A dedicated **sandbox
watchdog** kills runs exceeding the authored `timeout`.

**Who re-arms auto-suspend at a *detached* async terminal** *(resolved with 0008.12;
spike inputs from 0008.5/0008.6; 0008.12's v1-reconciler reinstatement is human-signed-off
2026-07-24).* For a detached async run the controller has already
returned `202` and released its lease, so it is *not* present when the run finishes —
yet auto-suspend must be re-armed, or a zero-poll fire-and-forget run would leave its
sandbox awake (and, since the group `auto_delete` backstop only touches *suspended*
sandboxes, never even reach reclaim). Auto-suspend is **request-idle-based, not
CPU-based** (that is precisely why D27 must disable it — a busy-but-quiet run is
otherwise napped), so it does **not** re-arm on its own once disabled; an explicit
restorer is required. **Heartbeat keep-alive is ruled out** (needs a live external
pinger the controller can't sustain across a long detached run).

**A *periodic* controller-side reconciler is the irreducible restorer**, because every
alternative fails the crash case — a harness that **crashes at/near terminal** never
writes its terminal journal and can't self-request or call back; only a periodic sweep
detects it (via a **stale liveness signal** — the OS-lock/journal heartbeat, 0008.2/0008.5)
and re-arms + reclaims. So the sweep is mandatory and everything else is a latency
optimization on top. The v1 realization (0008.12's minimal periodic reconciler,
reinstated and human-signed-off 2026-07-24; a timer trigger, **not** Durable
Functions — Decision 4 unaffected; **cadence configurable, ~1 h default, operator-tunable
up to several hours, auto-tightening to ~1 min in v2**):

- **Pull re-arm = v1 default (chosen).** The reconciler reads the terminal journal
  **from outside via the controller's ACA data-plane exec/file channel** (*not* sandbox
  egress) and re-arms auto-suspend to the session's normal/override interval. Its named
  repair condition (confirmed by 0008.12): *"a terminal or crashed sandbox still in the
  D27 run-disabled auto-suspend state → re-arm."* Needs **no new creds, no egress, no
  platform dependency** — least-privilege by construction, and 0008.6 landed on the same
  design independently.
- **My firm constraint (D9/27/28 × 0008.1/0008.9):** the untrusted, credential-less
  sandbox must never make a **control-plane** lifecycle write — this permanently rules
  out a harness policy self-rewrite (0008.12's option (a) as a control-plane op).
- **Harness data-plane self-*request* ("you may nap me") — future only.** It would be
  acceptable to my constraint (no creds, not escalation), but 0008.5's spike found **no
  in-sandbox data-plane suspend verb** (only the control-plane `set_lifecycle_policy`,
  which is out), so it is **not available in v1**; recorded as a future promptness
  optimization if such a verb ever ships.
- **Completion callback (push) — considered, not adopted.** More prompt, but needs a
  deny-by-default **egress** hole + callback auth (a spoofed "done" could prematurely
  re-arm/reclaim) and — decisively — **cannot cover the crash case** (a dead harness
  can't POST). Optimization at best, never the guarantee.
- **TTL/bounded disable (option (c)) — not viable.** 0008.5/0008.6 confirmed ACA has
  **no** auto-reverting disable (max interval 3600 s); a 3600 s interval would revert
  mid-run for any run quiet >1 h — the exact D27 failure — so it can't be the keepalive
  (at most an optional coarse ≤1 h bounded-leak backstop).

Either way the awake-after-terminal window is **bounded** (reconciler cadence + the
idle-suspend timeout) rather than indefinite — so there is no zero-poll always-awake
*leak*. Honest cost: a **zero-poll fire-and-forget** detached run can stay awake up to
**one reconciler cadence** after terminal before the sweep re-arms auto-suspend (then +
the ~5-min idle nap) — so ~1 h at the default, but as much as **several hours** if an
operator relaxes the cadence (the warmth-vs-spend knob cuts both ways). **Any** poll
(`get_status`/`get_result`) re-arms far sooner, so only the truly abandoned, never-polled
case pays the full cadence tail; operators who care about spend can tighten it, and v2
auto-tightens to ~1 min. 0008.12's minimal v1 reconciler (reinstated, human-signed-off
2026-07-24 — walking back its earlier "no v1 timer" sub-refinement toward the parent's
Decision 22)
carries this idle-policy repair alongside crash-detection and reclaim, all driven by the
same stale-liveness detection. **My D27 mechanism is unchanged** — this only refines the
earlier "controller restores after terminal" phrasing, which held solely for the
sync/attached case; the detached-async path is the reconciler's.

**Post-terminal result retention (async, v1).** Because a completed async run's
*result content* is sandbox-only in v1, reaping the sandbox before the client fetches
would lose it. So at an async terminal the controller keeps the session
**reap-protected**: **auto-suspend is allowed** — a snapshot preserves `result.json`,
so a later fetch warm-resumes (via `ensure_ready`) and reads it, with no need to burn
warm CPU — but **destroy/reap is deferred**. The result is retrievable for **max(the
remaining idle-retention window, a ~5-min floor from terminal)**. Two *complementary*
elements from 0008.12 (Decision 22/24) make this stable — they are not competing
choices: (1) the **retention model** is committed as *idle-based with the idle clock
starting at the terminal transition* (matching the persistent/reused-across-turns
design and ACA's own idle-cooldown model, *not* an absolute TTL from creation) — and
since auto-suspend is disabled *during* the run (D27), the clock provably starts at
terminal, so the window is measured from terminal with no truncation; (2) the **~5-min
floor** is kept as strictly-safe insurance (`max(...)` can only *extend*
retrievability) — under the committed idle-based model it **never binds** (the
full-from-terminal window already exceeds it), so it is inert belt-and-suspenders that
would only matter if retention ever gained an absolute-TTL component. A **fetch
releases the result-hold** and the session reverts to **normal idle-retention** (kept
for reuse, reaped on idle timeout) — it is *not* reaped merely because the result was
read; immediate-reap-after-fetch is a separate explicit opt-in for genuine one-shot
jobs, never the default. Once the session is actually reaped, `get_result` returns
**410** while `get_status` still resolves terminal status from the Tables control
record. The watchdog does *not* apply here (no active run to bound). Result content is
addressed per `run_id` (satisfied by 0008.5's `runs/{run_id}/` layout) so a subsequent
run cannot clobber an unretrieved earlier result; and this rides on the same
*auto-suspend-persists-across-idle* / sole-deleter assumption persistent sessions
already depend on (see the snapshot-durability open question) — it adds no new
durability risk. In v2 the mirror makes the result survive reaping, so retrieval becomes
a latency nicety, not a durability guard. (Sync runs are unaffected — the result returns
inline before any suspend.)

**Resume readiness:** lifecycle state reads are *hints, not proofs*. After every
resume the controller performs a real data-plane readiness operation and verifies
protocol, content digest, last-run journal, and the manifest's owner/app/session +
Sandbox Group + sandbox ID + generation binding — cross-checked against the
authoritative Table-row pointer (generation, ETag-guarded, per 0008.3's 32-R/39-R) —
before submitting more work. Sibling **0008.5** names this handshake `ensure_ready(sandbox)`
and hard-depends on it (cancel-during-resume and instance-death reattach both run
behind it). (This is the direct consequence of the spike finding in sibling 0008.5
that `get().state` can lag the file/exec plane.)

A "verified resume" means the manifest digest, the authoritative Table-row pointer
(matching generation, ETag-guarded, per 0008.3's 32-R/39-R), owner/app/session
identity, generation, deployment/content digest, and last-run journal *all*
validate; partial validation is never silently accepted. (The transcript-watermark
check against an external mirror is a v2 addition, landing with Decision 18.)

## Alternatives considered & why the choice won

- **v1 durability scope (Human, 2026-07-22).** Considered: ship the full
  owner-scoped external mirror in v1; or lean on ACA auto-suspend/resume for v1 and
  add the external mirror in v2. Chosen: **platform-only durability for v1**, mirror
  deferred to v2. The external-mirror machinery (per-turn Blob writes, reconciler
  mirror job, rebuild-from-checkpoint) is large and guards against a *rare* event
  (sandbox + snapshot both lost); auto-suspend/resume already gives warm continuity
  for the common case, and best-effort v1 durability is an acceptable trade for the
  simplification.
- **Snapshot role (Decision 9).** Considered: snapshot as sole session state; cache
  only; or no snapshots. *v1 choice:* the sandbox + auto-suspend/resume snapshot is
  the best-effort durability boundary. *v2 choice (retained target):* snapshot is
  only an optimization and an external checkpoint is the correctness record —
  because live sockets/tokens/leases can be stale after resume and a snapshot can be
  lost, trusting it as *permanent* truth is unsafe. *Human (v1 re-scope) / Agent.*
- **Conversation durability (Decision 18).** Considered: sandbox disk only; sandbox
  snapshot only; or an owner-scoped external mirror. *v1 choice:* sandbox disk +
  snapshot only (no external mirror). *v2 choice:* mirror each completed transcript
  delta + bounded checkpoint to owner-scoped customer Blob Storage — so losing a
  sandbox never loses the session. *Human (v1 defer) / Agent reviewer.*
- **Active-run lifecycle (Decision 27).** Considered: rely on idle timeout/cooldown;
  heartbeat; or disable auto-suspend while active. Chosen (v1): disable auto-suspend
  before accepting a run, keep the session non-idle, bound execution with a
  watchdog, restore policy after terminal — ACA's idle **cooldown** destroys idle
  sessions and cannot bound an active run, and a heartbeat is racy. *Agent.*
- **Resume readiness (Decision 28).** Considered: trust `get().state`; retry
  operations only; or an operation + manifest handshake. Chosen (v1): operation
  result is authoritative + recreate clients + verify the manifest, because the
  spike proved state reads can lag the data plane. *Agent.*

## Honest critique

**Strengths.** The v1 cut is honest and well-scoped: it keeps the *cheap,
always-needed* correctness rules (recreate clients on resume; don't let an idle
reclamation kill an active run; verify before submitting work) and defers only the
*expensive, rare-failure* machinery (the external mirror). Keeping "an external
checkpoint is the true boundary" as the explicit v2 target means the good mental
model isn't lost — just staged.

**Risks / assumptions.**
- **Best-effort v1 durability.** With no external mirror, a lost sandbox+snapshot —
  or an idle session reclaimed past its cooldown — means the session is gone. This
  is now a *primary* v1 behavior, not an edge case, and must be documented for
  callers.
- **Reliance on a preview capability.** Warm resume with intact process/disk state
  depends on the **ACA Sandbox auto-suspend/resume** feature, which is *preview*
  with no stated durability SLA for the memory snapshot. If the platform drops a
  snapshot, v1 has no fallback.
- **Redeploy drains sessions by design (Decision 70), not a snapshot-compat risk.** An
  image/content/protocol change is a **redeploy = new epoch**, so a digest-mismatched
  session is **intentionally drained** (grace → abandon → tombstone → 410; the client
  starts a new session on the new epoch — 0008.6). This is deliberate lifecycle, not a
  "warm snapshot invalidated → silent session loss" failure. The only residual risk is
  narrower: whether ACA auto-suspend reliably preserves the disk *within a single
  epoch* (no redeploy) — the tracked preview-durability question.
- **Idle-vs-active reclamation.** ACA cooldown fires on *no requests* and destroys
  the session; the controller must actively keep a long-running async turn's session
  non-idle, or it can be reclaimed mid-run. The watchdog bounds the opposite failure
  (a run that never ends).

**Reconsider triggers.** Pull the v2 external mirror forward if: best-effort
durability proves unacceptable for a real workload; the preview snapshot proves
unreliable or lacks a durability SLA within a single epoch; or the drain-on-deploy
(Decision 70) cadence is high enough that losing in-epoch sessions on every redeploy
hurts (v2's mirror would let a redeploy *rebind* surviving state onto the new epoch
instead of draining). Deferred v2 design questions (bounded-checkpoint contents;
per-turn mirror cost; async recovery gap) reopen at that point, in coordination with
0008.3, 0008.11, and 0008.12.

### Cross-reference: future handoff state (Decision 46, owned by 0008.13)

The checkpoint model above is what a *future* multi-agent **handoff** feature will
lean on. Today's subagent delegation (see sibling **0008.13**) is synchronous and
carries no shared session state, so it needs nothing durable here. But the
committed handoff fast-follow transfers control between participants *across
turns* with a shared broadcast context — i.e. "which participant is active" and
"what context is shared" become **durable session state** that would have to live
in this checkpoint/manifest schema and survive suspend/resume. Decision 46
(owned by 0008.13, **Finalized 2026-07-23**) **explicitly punts handoff durable state
to v2** (Human call): the checkpoint/manifest schema **reservation stands** as its
future home, but concrete field layout, versioning, and suspend/resume behavior are
designed in v2, co-reviewed against the v2 Blob mirror between 0008.13 and this
sub-FRD.
Note: with v1 deferring *all* external durability, there is no durable store for
handoff state until the v2 mirror lands, so any handoff durable-state design is
**v2+ by construction**.

  **parent-owner update** to add the v1/v2 split — flagged, not edited here.
- **0008.12 (lifecycle & reconciler).** In v1 the reconciler's **mirror job** and
  **Decision 24** (two-minute p95 terminal-checkpoint mirror SLO) are **deferred to
  v2** along with Decision 18. The v1 reconciler keeps only sandbox/session reaping

  *SLO* is satisfied by that single ~1-min sweep, not a second timer. **Crash-vs-reclaim
  (row 67 case b) — flag to 0008.12:** a harness *process* crash with the sandbox/disk
  **intact** must mark the in-flight **run** abandoned (one-active-run slot release) but
  must **not** reclaim the **session/sandbox** — reclaim is gated on genuine loss or
  idle-retention expiry, so the session can resume on the same sandbox from the last
  committed turn (case b). 0008.12 to confirm its silent-death→abandoned crash path
  distinguishes *run*-abandoned from *session*-reclaim; I have not edited 0008.12.
- **0008.3 (state store & containers).** The **deletable history/checkpoint
  container** is *provisioned but not written in v1* (populated only in **v2**). Per
  0008.3's finalized redesign (**32-R / 39-R**, Human 2026-07-22) there is **no WORM
  binding-log and no bindings container** in v1: the session→sandbox pointer is the
  **authoritative Azure Table row** (controller managed identity is the sole writer
  via scoped RBAC, Shared Key disabled), rollback-barred by a **monotonic generation
  on the row itself** (ETag-guarded) and cross-checked against the **live sandbox
  manifest** — no Key Vault signature. *Decision 20 unchanged; Decision 39 → 39-R (no
  WORM log).*
- **0008.5 (transport & protocol).** The resume handshake here *is* 0008.5's named
  `ensure_ready(sandbox)` verb and is a **hard transport dependency**: it must be
  idempotent / safe to await concurrently (cancel-during-resume serializes behind
  it), and a "ready" verdict must guarantee the last-run journal is trustworthy and
  the rehydrated PID / `sandbox_generation` are confirmed (instance-death reattach
  reads the journal only after it returns).
- **0008.5 / 0008.3 — same-gen vs loss vs generation advance (aligned to 0008.3
  7c66c07).** `ensure_ready` in-flight *rehydration* is scoped to **same-generation**
  resume, which in v1 covers both suspend/resume and crash-with-disk-intact (case b) —
  state-preserving on the *same* backing. A genuine **LOSS (case a) is NOT a generation
  advance**: with no recoverable disk it is a **tombstone → 410**, no resume. A
  **generation advance** — a state-preserving rebind to a *different* backing (same
  `session_id`, new `sandbox_generation`) — is **v2-only** (it needs the external mirror
  to reconstruct state; the v1 sandbox has no such rebuild path), so **v1 never advances
  the generation**. In the v2 advance case, `ensure_ready` verification
  (manifest/protocol/owner/generation) runs on the new instance, committed state is
  preserved from the mirror, and only the in-flight *run* is abandoned (the process
  didn't survive the backing change) — the *session* is not lost. (This supersedes the
  earlier "gen-bump = state-losing → fails explicitly" wording; under 7c66c07 the
  state-losing/410 case is **loss**, and a generation advance is a v2-only
  state-preserving rebind. 0008.5's matching transport-boundary residual was routed for
  the same alignment by the parent.)
- **0008.2 (identity & ownership).** "Owner-scoped" here must accept an app-scoped
  `function_app` OwnerContext, **not Entra-only**. The manifest owner binding
  verified on resume must handle either identity type, and the (v2) checkpoint
  owner-match must be aware of `owner_hash_version` (no eager migration), since an
  older checkpoint may carry an older owner-hash version.

## Open questions / iterate here

**v1 (live now):**
- **Best-effort durability acceptance.** Is "sandbox/snapshot loss ⇒ session lost"
  acceptable for the target v1 workloads, and how is it surfaced to callers?
- **In-epoch snapshot durability (preview).** ACA Sandboxes is preview; does ACA
  auto-suspend reliably preserve the on-disk session directory *within a single epoch*
  (no redeploy)? (An image/content/protocol change is **not** in scope here — that's a
  redeploy → drain-on-deploy, Decision 70/0008.6, by design; see the honest critique.)
- **Keeping an active session non-idle.** Given ACA cooldown is idle-based (min
  300 s) and destroys the session, what exact mechanism keeps a long async turn's
  session alive while the watchdog bounds max run time? (Interacts with 0008.12.)
- **Detached-async auto-suspend re-arm (resolved with 0008.12; human-signed-off
  2026-07-24).** Auto-suspend is
  request-idle-based, so it doesn't re-arm once D27 disables it; no controller is present
  at a detached-async terminal. **Resolution:** the **v1 periodic reconciler** (0008.12,
  reinstated) re-arms via **pull** — reads the terminal journal over the controller's ACA
  data-plane exec/file channel (no sandbox egress, no new creds) and re-arms to the
  session's normal/override interval; named repair condition confirmed ("terminal/crashed
  sandbox still in D27 run-disabled state → re-arm"). A *periodic* sweep is irreducible
  because it's the only thing that catches a **harness crash before signaling** (via
  stale liveness). Ruled out: harness control-plane self-rewrite (creds); data-plane
  self-*request* (0008.5 found no such verb — future only); push callback (egress+auth,
  can't cover crash); TTL-disable (ACA has none; 3600 s reverts mid-run). Reconciler
  cadence configurable (~1 h default, operator-tunable up to several hours,
  auto-tightening to ~1 min in v2), so a zero-poll run's worst-case awake tail is one
  cadence (~1 h default; any poll re-arms sooner). My D27 behavior is unchanged.
- **Client-recreation completeness.** Which specific clients/leases must be rebuilt
  after resume, and is there a conformance check (0008.7) that a resumed MAF adapter
  actually rebuilt them?
- **Warm-session cost model (resolved with 0008.12).** Two idle clocks, both
  idle-based and starting at the terminal transition (reset by any request, incl.
  `get_result` — so a polling client keeps the session alive; there is no absolute
  creation-time TTL in v1): an **auto-suspend timeout** (*behavior mine* — D9/27/28;
  default ~5 min / 300 s is **0008.12's**), applied as a **per-sandbox lifecycle
  override written at create** from a global/app config (hybrid, ADC data plane —
  app-controllable without editing group IaC; config home **0008.4**, group policy the
  fallback default); and an **idle-reclaim window** (*0008.12's* — ~24 h default), which
  doubles as the async result-retention window and, **in v1, is a reaper data-plane
  delete** (not an ACA platform auto_delete). Warmth-vs-spend curve: **0–5 min idle =
  running**, **~5 min–24 h idle = suspended** (snapshot-cheap, warm-resumable via
  `ensure_ready`), **~24 h idle = reclaimed** (→ `get_result` 410). My D27
  disable/restore is unchanged, simply parameterized: after terminal it restores
  auto-suspend to the per-sandbox **override value** (not the group default), which
  0008.12 persists (denormalized onto the session control record at create) so it is
  readable at restore — else the first run would silently downgrade the session to the
  group fallback. **v1 keeps the reaper as the sole authoritative deleter** (0008.3
  generation-guarded single-writer): its reclaim clock *is* the
  idle-from-terminal / reset-on-request / through-suspend window locked above, so no
  platform TTL can violate the no-absolute-TTL or 24h→410 guarantees; the customer's
  group-level auto_delete is only a coarse far backstop — and even that backstop cannot
  race a *live* session, because **D27 disables auto-suspend during a run while any
  platform/group `auto_delete` only ever acts on *suspended* sandboxes**, so it
  physically cannot touch a running session; if the backstop does delete a suspended
  sandbox, the reaper reconciles the Tables control record to terminal afterward
  (ETag-CAS, 0008.3 single-writer; sandbox delete is idempotent, the record never
  double-written). Letting ACA's per-sandbox auto_delete become the happy-path deleter
  is a **future optimization gated on two acceptance contracts**: (1) it must be
  idle-based, reset-on-request, and run *through* suspend; (2) it must preserve a single
  authoritative deleter (reaper reconciles Tables status after any platform delete, no
  race on a live session). Until then deletion stays with the reaper and my suspend/410
  model is untouched. Residual (empirical): the per-hour suspended-vs-running $ profile.
  (empirical): the actual per-hour suspended-vs-running $ profile.
- **Async result retrieval (resolved with 0008.12).** Post-terminal reap-protection
  (auto-suspend allowed, reap deferred); result fetchable for **max(remaining
  idle-retention window, ~5-min floor from terminal)**. Two complementary elements
  (0008.12 Decision 22/24): retention committed as *idle-based, clock starting at
  terminal* (so the full-from-terminal window is the effective bound), and the **floor
  kept** as strictly-safe insurance that is inert under that model but survives a future
