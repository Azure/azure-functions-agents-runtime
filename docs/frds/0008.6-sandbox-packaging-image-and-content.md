## What this is and why it matters

Before an agent can run inside an **ACA Sandbox** (an isolated Azure Container Apps
container), two things must come together inside that sandbox: a generic **bootstrap
image** (the Azure Functions Python base + a **stdlib-only** entrypoint) and the
*captured app environment* — the author's `.agent.md` files, tools, skills, MCP config,
and **one pip-resolved dependency tree** that includes **both our runtime
(`azurefunctions-agents-runtime`) and the harness engine it pulls in (MAF)** plus the
customer's tool deps. In v1 the harness engine (MAF) is **not baked into the image**; it
arrives with the captured content. How those arrive determines both security and
developer experience.

The naive approach — have the sandbox `pip install`, `curl | bash`, or `git clone`
at session start — is rejected outright: it forces a startup window with permissive
network access before any lockdown, and re-fetches from the internet for every
session. So packaging keeps a **generic, immutable prebuilt bootstrap image** (Functions
Python base + a stdlib-only entrypoint) and layers the specific app environment on top.
The key refinement
(Decision **17-R**) is that this per-app layer is **not a bespoke new format and needs
no fetch by the sandbox**: the **controller captures the customer's already-deployed
app content from its own local script root** (the code plus the Functions-vendored
`.python_packages`), zips it, hashes it (SHA-256), and **delivers it into an
identity-less sandbox over the file transport** ([0008.5](0008.5-controller-sandbox-transport-and-protocol.md)).
**v1 ships this path (Path 1) only.** A pre-baked **ACA committed disk image** (Path 2)
is documented below as a **deferred future optimization** for low latency /
network-install dependencies, but is not built in v1. Either way the sandbox verifies
a content **digest** before use — computed over the controller-captured bytes, not a
new signing scheme.

## Decisions this sub-FRD owns

- **Decision 8 — Runtime packaging.** Use an **immutable prebuilt disk** with
  protocol + manifest verification. Installing/cloning at session start and mutable
  shared volumes are rejected. (Refined by Decision 17.)
- **Decision 17 — Artifact delivery (revises #8).** A *generic* immutable harness
  disk **plus** a per-app content layer (not baked into the disk) — so authoring a
  new agent does not require rebuilding the disk image.
- **Decision 17-R — Content-layer mechanics (refines #17; Human, 2026-07-22;
  recorded as *Decision 48* in the parent master log). Round 2 (2026-07-24, Human
  Tier-A — parent rows 66 + 68) revises the *delivery mechanism*.**
  **v1 = Path 1 only:** the **controller captures the customer's already-deployed app
  content from its own local script root** (`/home/site/wwwroot` or the Flex
  equivalent — code + the Functions-vendored `.python_packages`), zips it, computes a
  **SHA-256** digest, and **delivers it into an identity-less sandbox over the file
  transport (0008.5)**. The sandbox needs **no identity and no storage access**; there
  is no bespoke content-package format and no in-sandbox dependency resolution. (This
  replaces the Round-1 "sandbox reads the Run-From-Package zip from customer storage via
  managed identity" mechanic, which was not implementable across Functions plans and
  conflicts with the identity-less sandbox.) The routing digest is computed over the
  captured bytes (0008.3, `digest_kind=funcs_zip`). An **ACA *committed disk image*
  (Path 2)** produced by a deploy-time priming sandbox is **documented as a deferred
  future optimization** for low-latency / network-install / build-from-source cases,
  **not implemented in v1**.

### How packaging works

Packaging has two layers — a **generic harness image** and a **per-app content
layer** — but the content layer now **reuses what Azure Functions deployment already
produces** rather than a new bespoke format.

**The generic bootstrap image (stdlib-only; Round 3 states its ABI basis).** A
single immutable disk image carries only the **Azure Functions Python base plus a
stdlib-only bootstrap/entrypoint** — it **does not bake MAF or our runtime**. It is
authored, built, and published by the runtime project, is byte-identical for every
customer, and is referenced by pinned digest (see the residency split below and
[0008.4](0008.4-resource-residency-and-provisioning.md)). **It is built *FROM* the
Azure Functions Linux Python base image** (`mcr.microsoft.com/azure-functions/python:<ver>`)
— the same architecture, glibc, and CPython minor as the app's Functions worker — so the
`.python_packages` wheels captured from the app's disk **import ABI-identically by
construction** (Round 3 decision, larohra, 2026-07-24; pairs with 0008.7's
inherit-base-ABI statement). This is the *mechanism* behind the ABI requirement; it adds
no new ABI spec, and the customer-facing gate stays "Linux Python 3.13/3.14" (0008.10).

**The content layer.** v1 uses Path 1; Path 2 is a deferred future optimization (below).

*Path 1 — controller captures and delivers the app content (the v1 mechanism).* The
**sandbox is identity-less** and has **no storage access**; the **controller** puts the
content in. The Functions worker already runs the customer's app from its **local script
root** (`/home/site/wwwroot`, or the Flex equivalent) on every SKU, so the controller
**captures that same on-disk app content** — the code plus the vendored
`.python_packages` (dependencies resolved offline by the normal Functions deployment) —
**zips it, computes a SHA-256 digest, and delivers it into the sandbox over the file
transport** ([0008.5](0008.5-controller-sandbox-transport-and-protocol.md)). The sandbox
unpacks it into `/app`, **bootstraps the single captured environment** (below), re-runs
the normal discovery/translation pipeline locally, and runs the requested agent **from
the captured env**. This needs **no sandbox identity, no sandbox storage access,
and no per-plan artifact-location assumptions** — the controller reads content it already
has mounted, rather than the sandbox reaching a customer Blob (the earlier "sandbox reads
Run-From-Package via managed identity" mechanism wrongly assumed a Blob that only exists
in some Functions plans, and the identity-less sandbox forbids it anyway). Deployment
stays whatever `func` / `azd` already do; there is no bespoke package format.

*ABI compatibility (by construction).* Because the vendored wheels are **imported, not
rebuilt**, the sandbox runtime must match the app's — and it does **by construction**:
the harness image is built *FROM* the Azure Functions Linux Python base image
(`mcr.microsoft.com/azure-functions/python:<ver>`), so it inherits the **same
architecture, glibc, and CPython minor** as the app's worker, and the captured
`.python_packages` wheels (cp313/cp314 manylinux) import cleanly. **v1 requires the
Functions app to be Linux Python 3.13/3.14** so the base-image match holds. There is
**no in-sandbox dependency resolution** (no internet at create), so the ABI match is a
hard v1 requirement met by the shared base image, not a best-effort.

*Bootstrap (stdlib-only image → run from the captured env).* The image's entrypoint uses
**only the Python standard library**; it does not import MAF or our runtime (they aren't
in the image). At session start it unpacks the captured content to `/app` and adds the
captured `.python_packages` tree to the import path via **`site.addsitedir()`** (not a
raw `sys.path.insert`, which would **not** process `.pth` files), with **deliberate
ordering so `/app` does not shadow the standard library** (a real `inspect.py`-shadow
failure was observed and must be avoided). It then imports and runs the runtime's
sandbox-harness entrypoint **from the captured env**. Note: `.python_packages` is an
**already-installed tree** — the bootstrap **points `sys.path` at it; it does not
`pip install` from it** (it is not a wheelhouse, and there is no internet at create).
*Empirically validated:* a stdlib-only process imported `agent-framework-core` 1.3 +
`pydantic` 2.13 + `jmespath` and ran a trivial MAF agent fully offline from a
`pip install --target` tree (~2.2 s unpack + 0.35–0.70 s first MAF import).

*One pip-resolved environment (no harness-vs-customer conflict by construction).* The
image adds **no Python packages**, so the **sole Python environment is the captured
`.python_packages`** — a single tree the customer's Functions build already co-resolved.
Because `azurefunctions-agents-runtime` is a customer `requirements.txt` dependency that
pulls in **MAF transitively**, runtime + MAF + tool deps are **one pip-resolved env**, so
there is **no harness-vs-customer dependency version conflict** to reconcile — pip already
did. (This replaces the earlier "harness deps live outside `/app`" framing: there are no
separate harness deps to isolate.)

*Redeploy vs. live sessions (drain-on-deploy).* A new deployment changes the captured
**content digest**, which is a **new content identity**, so it applies to **new**
sessions; **live sessions are not silently re-pointed and do not keep serving under a
"latest" rule.** Per 0008.3 (row 70), a content-digest change **drains** the affected
live session — **grace period → abandon → tombstone → `410 Gone`** — rather than bumping
a generation or swapping content underneath a running session. (The generation tracks the
*backing* sandbox resource, never content; see the tamper-evident-routing note above.)

*Path 2 — committed disk image (deferred future optimization; not built in v1).* At
**deploy time**, a short-lived **priming sandbox** is booted from the generic harness
image **with controlled, deploy-time egress**, the deployment zip is extracted into
`/app`, and dependencies are installed normally — **including packages that need the
network at install time or must be built from source**. The primed filesystem is then
captured with **`aca sandbox commit`** into a **per-deploy committed disk image** that
lives in the customer Sandbox Group. Every *session* sandbox for that deployment boots
directly from that image (`--disk-id`) with **egress denied from the first second**.
Content *and* installed dependencies are already present, so session create does no
download, no unpack, and no install. The image is produced **only at deploy time** —
session create merely boots from an existing `--disk-id` and never commits — and it is
tagged with the same **app/owner/build labels** its session sandboxes carry, so "which
sessions still pin this image" is answerable as a label query (see the 0008.12 note on
reference-counted GC).

*Why Path 2 is deferred (not v1).* Path 1 already gives no-internet-at-create,
verifiable contents, and the fast authoring loop by reusing proven Functions plumbing —
so for an experimental v1 the committed-image path is not worth its extra cost: (1) a
**more privileged deploy step** (the deploy identity would need sandbox
create/exec/commit, not just blob write) plus minutes of extra deploy latency from the
prime+commit; (2) **committed-image lifecycle/GC** to build and operate (per-deploy
images accumulate and must be pruned); (3) **harness/protocol version coupling** — a
committed image is a child of a specific base, so a base bump forces a re-commit
fan-out and a fleet bump-orchestration policy (0008.7) that Path 1 simply does not
need; and (4) ACA committed-image immutability is a **preview-product property still to
be verified**. Path 2's wins (network-install / build-from-source deps, near-zero cold
start) are not required for the initial pilot — the **custom-image escape hatch**
covers the rare hard-dependency case. Path 2 is kept fully specified here so it can be
adopted later without re-deriving the design; the reconsider triggers below say when.

**What Path 1 preserves (and Path 2 would too).**

1. **No internet at session create.** Path 1 needs **no network from the sandbox at
   all** — the controller delivers the captured content over the file transport (0008.5)
   into an identity-less, storage-less sandbox, so there is no `pip install` /
   `curl | bash` / `git clone` and nothing for the sandbox to reach. Path 2 does all
   installation once, at deploy time, in a controlled window. Either way the
   deny-by-default egress in [0008.9](0008.9-network-egress-and-obo.md) holds from
   creation — and Path 1 makes it stronger: the sandbox has no egress need for content
   whatsoever.
2. **Tamper-evident routing.** The sandbox still verifies a content **digest** against
   the **authoritative session record** in
   [0008.3](0008.3-state-store-and-tamper-evident-trust.md)
   (`owner/app/agent/digest/session`), which 0008.3 cross-checks against the **live
   sandbox manifest**. (Per 0008.3's redesigned trust model — Decisions 32-R/39-R — the
   record is authoritative-by-construction: scoped RBAC + disabled Shared Key make the
   controller managed identity its only writer, so there is no per-binding signature or
   WORM log; the digest is written by the controller onto that row and verified against
   the live manifest.) That digest is the **SHA-256 over the controller-captured
   app-content zip** (Path 1) or the **committed image's create-only `--disk-id`**
   (Path 2, an immutable
   per-commit id — never a mutable label) — reusing an existing hash rather than a new
   signing scheme. Because the two paths live in different digest spaces, packaging
   emits a `digest_kind` discriminator (`funcs_zip` | `aca_image`) **paired with** the
   digest, and 0008.3 compares the pair `(digest_kind, digest)` — a `funcs_zip` digest
   can never match an `aca_image` one. The **generation** on the authoritative row tracks
   the session's **backing** (sandbox resource), **not** its content; a **content-digest
   change is not a generation bump** — it means a **different content identity**, handled
   as a **new session (drain-on-deploy, 0008.3 row 70)**, not a silent in-place swap. So
   at run time the sandbox's live content must match the digest recorded for *this*
   session. The declared algorithm is **SHA-256** in canonical
   `sha256:<hex>` form (agreed with 0008.3). The sandbox re-runs discovery against the
   verified contents; it does not trust controller-supplied Python objects.
3. **Markdown-first authoring.** Editing a `.agent.md` and redeploying makes the
   controller re-capture the new app content (Path 1) or re-prime and re-commit (Path 2).
   Neither rebuilds the **generic harness image**, so the fast authoring loop survives.
4. **All reachable agents.** Because the captured content is the whole app, the
   content layer naturally spans every agent a coordinator can delegate to (FRD 0007),
   with no per-specialist packaging.

A custom immutable image remains the **escape hatch**, not the default path — for
OS-level bits a stdlib bootstrap + captured env can't supply. **In v1 it must still be
MAF-conformant** (v1 is MAF-only — parent §221, 0008.7); a **non-MAF harness is out of
v1 scope and deferred to a separate FRD**, not enabled by the escape hatch.

**Where the two halves live (residency split, see [0008.4](0008.4-resource-residency-and-provisioning.md)).**
This packaging split is exactly what lets the runtime *control the image* while
*provisioning stays customer-owned*. The generic harness disk image is authored,
built, and published by the runtime project and is **byte-identical for every
customer**; customer infrastructure-as-code only references it by **pinned digest**
and places a copy into the customer's Sandbox Group. All per-app authored bits are
**captured from the customer's deployed app content by the controller and delivered into
the sandbox** (Path 1) — or, under deferred Path 2, baked into a per-deploy committed
image — **never baked into the generic image**, and the custom-image path remains the
escape hatch above. So "the runtime controls the
harness" and "the customer owns provisioning" are not in tension — Decisions 8/17
draw the line between them.

## Alternatives considered & why the choice won

- **Runtime packaging (Decision 8).** Considered: install/clone at session start;
  an immutable prebuilt disk; or a mutable shared volume. Chosen: immutable
  prebuilt disk with protocol + manifest verification. Install/clone means a
  permissive-egress bootstrap and per-session internet dependence; a mutable
  shared volume undermines the "known, verifiable contents" property. *Agent.*
- **Artifact delivery (Decision 17, revising 8).** Considered: bake the whole
  project into *every* disk; a generic disk + separate per-app content layer; or
  install/clone at session start. Chosen: generic disk + per-app content layer, so
  authoring never rebuilds the disk. Baking the project into the disk would force an
  image rebuild on every `.agent.md` edit, destroying the fast markdown authoring
  loop. *Agent reviewer.*
- **Content-layer mechanics (Decision 17-R, refining 17).** *Given* the generic-disk
  + content-layer split, how is the content layer actually built and delivered?
  Considered:
  - *(a) Bespoke signed content package + custom offline-dep resolver* — the original
    17 mechanic. Rejected as reinventing the wheel: it duplicates the app content +
    vendored dependencies the Functions deployment already produces, and adds a
    signing scheme that 0008.3's redesigned trust model (Decisions 32-R/39-R) no longer
    uses at all — routing trust there is authoritative-by-construction (scoped RBAC +
    live-manifest cross-check), not per-artifact signatures.
  - *(b) Reuse the deployed Functions app content (Path 1)* — **chosen as the v1
    mechanism.** Nearly zero new deploy machinery; offline deps come from the normal
    Functions-vendored `.python_packages`. *Round 2 (2026-07-24) corrected the
    **delivery**:* from "the sandbox reads a customer Blob via managed identity" (not
    implementable across Functions plans; conflicts with the identity-less sandbox) to
    **"the controller captures its own script-root content and delivers it over the
    file transport (0008.5)"**. The digest is computed over the captured bytes for
    0008.3.
  - *(c) ACA committed disk image via deploy-time priming (Path 2)* — **documented but
    deferred to post-v1.** Uniquely moves any network-install / build-from-source
    step into a *controlled, one-time deploy window*, then runs sessions with egress
    denied from creation; gives the best session-create latency (content and deps are
    pre-baked). Cost (the reason it is deferred): it re-couples content to the
    harness/protocol version (a base upgrade forces a re-commit), needs a heavier and
    more privileged deploy step (sandbox create/exec/commit, not just blob write), and
    adds committed-image lifecycle/GC.
  - *(d) Per-deploy Azure Files content mount* — a middle option (extract deps to a
    read-only share mounted across sessions). Noted, not chosen for v1: it still pays
    a mount + per-session setup cost at create and adds a share to manage.

  Chosen: **(b) Path 1 as the sole v1 mechanism; (c) Path 2 documented as a deferred
  future optimization, not built in v1** (see "Why Path 2 is deferred" above and the
  Honest-critique costs). *Human, 2026-07-22.*

## Honest critique

**Strengths (v1 / Path 1).** Reusing the Functions deployment artifact means v1 adds
**almost no new deploy surface** — no bespoke package format, signing key, or offline
resolver to build or secure, and no new privileged deploy rights. It keeps
no-internet-at-create, tamper-evident routing (0008.3), markdown-first authoring, and
whole-app / all-reachable-agents coverage (FRD 0007). Re-running discovery *inside* the
sandbox against verified contents is a strong defense-in-depth choice. The
committed-image path (Path 2, deferred) *would* additionally retire the "offline
dependency is a hard promise" problem (network-install / build-from-source handled once
at deploy) and cut cold start — which is why it is kept on the roadmap, not discarded.

**Why Path 2 is deferred — its costs (Path 1 v1 avoids all of these).**
- **Committed images couple baked content to a specific base + captured runtime.** A
  committed image bakes a specific generic base image **and** the session's captured
  runtime (which carries `protocol_version`, per the decouple below). So a **base-image
  (harness) upgrade** *or* a **captured-runtime/protocol change** requires **re-committing**
  the per-deploy image. Path 1 bakes no image, so it needs neither. Path 2
  trades that for latency. The re-commit is **redeploy-triggered** (the base is pinned
  by digest, so a bump is a redeploy), 0008.5's `ensure_ready` **rejects any stale
  image at submission** as a backstop, and the *fleet-wide bump-orchestration policy*
  is an open ownership item (likely 0008.7 — see cross-cutting notes).
- **Heavier, more privileged deploy step (Path 2).** The deploy identity must be able
  to create, exec in, and commit sandboxes — a broader grant than "write a blob"
  (interacts with the 0008.4 provisioning-rights split). Priming also adds deploy
  latency (the ACA commit pauses/resumes the sandbox and can take minutes).
- **Committed-image lifecycle / GC.** Every deploy spawns a new child image; stale
  images accumulate. Per 0008.4 "creator owns teardown," **deletion is deploy/
  customer-side** (the runtime reaper never deletes images); the platform's
  **child-before-parent** rule means an image can only be pruned after the 0008.12
  reaper has drained the session sandboxes that pin it. Still real operational weight:
  something must prune *superseded* images each deploy, not only at environment
  teardown — 0008.12 declined image GC, so 0008.6 owns that prune trigger/cadence
  (open question below).
- **Deploy-time vs session-create cost tradeoff.** Path 2 front-loads cost to
  *deploy*; Path 1 pays at *session create*. If sessions ≫ deploys (production),
  Path 2 wins; during active authoring (edit → deploy → run), Path 2's priming adds
  friction to every iteration.
- **Escape hatch still exists (MAF-conformant in v1).** OS-level needs that even a
  priming sandbox can't install still require a custom immutable image; the boundary
  is narrower than before (commit absorbs most native/network cases) but not gone. A v1
  custom image **must still be MAF-conformant** — a **non-MAF harness is out of v1 scope,
  deferred to a separate FRD**.
- **Unverified platform limits.** Any cap on committed-image count or commit-chain
  depth per Sandbox Group, and the boot latency of a committed vs stock public image
  (given image caching), are assumed-workable but unmeasured.

*Path 1 v1 residuals.* Path 1 pays a per-session **unpack + first-import** at create —
there is **no in-sandbox install** (the bootstrap sys.path-points at the already-installed
captured `.python_packages` via `site.addsitedir()`; ~2.2 s unpack + 0.35–0.70 s first
MAF import in the spike) — and genuinely network-at-install cases (or OS-level needs a
stdlib bootstrap + captured env can't supply) fall to the **custom-image escape hatch**
(MAF-conformant in v1). Both are acceptable for the pilot scope; if per-session
cost proves material, that is precisely the trigger to adopt Path 2.

**Reconsider triggers (when to adopt the deferred Path 2).** Promote Path 2 from
deferred to shipped if: Path 1's per-session **unpack + first-import cost** (not an
install — there is none in-sandbox) materially hurts sandbox-create latency against the
0008.5 targets; real agent projects routinely
need **network-at-install / build-from-source** deps (so the escape hatch is hit too
often); or cold start dominates for high session-churn workloads. Adopting Path 2 then
also activates its deferred machinery — version-coupling policy (0008.7),
committed-image prune/GC, and priming egress — and, only if the team wants the runtime
(not deploy tooling) to own image GC, the option (B) governance hook, which needs an
explicit Decision 30 rights change (loop 0008.4).

  with 0008.3: `digest` is **SHA-256** in canonical `sha256:<hex>` form, carried as a
  pair with a `digest_kind` discriminator (`funcs_zip` | `aca_image`) and compared
  pairwise (within matching kind). **A content-digest change is not a generation bump**
  — the generation tracks the *backing* only (0008.3); a different content digest is a
  **new content identity handled as a new session (drain-on-deploy, 0008.3 row 70)**. For
  Path 2 the property that matters is **ID immutability**, not just
  digest availability (0008.3): the manifest must attest the committed image's
  **`--disk-id` (`.diskImage.id`)**, which is **create-only** — each `aca sandbox
  commit` mints a new image with a new id, boot is by id, and there is no documented
  operation to re-point an existing id to different bytes — and must **not** attest the
  mutable `--name`/labels. That satisfies 0008.3's "content-addressed or create-only
  immutable" soundness condition, so exact-equality within `aca_image` holds with no
  silent-swap window. **For v1 (Path 1) only `funcs_zip` + SHA-256 is used; the
  `aca_image` sub-case above is deferred with Path 2.** The `(digest_kind, digest)`
  pair shape is retained in the v1 routing record (trivially single-kind) so adopting
  Path 2 later is **additive — no routing-record or generation-semantics change**
  (agreed with 0008.3). **Open verification (Path 2, deferred):** obtain an explicit
  immutability guarantee for disk-id from the ACA
  Sandboxes API/team (preview docs imply but don't state it); if ACA ever exposes only
  a mutable reference, fall back to also attesting a content hash of the committed layer
  (0008.3's mutable-tag fallback). **Ownership:** 0008.6 owns this ACA-facing
  verification; 0008.3 holds the consuming trust condition and cross-references this
  item, so it is tracked once, here.
- **Committed-image versioning vs `protocol_version` (deferred with Path 2).** Only
  relevant once Path 2 ships: define the re-commit policy on a base/`protocol_version`
  bump and how committed-image IDs are tracked per deployment. Path 1 v1 **bakes no

- **Deploy-identity rights for priming (deferred with Path 2).** Path 2 would require

  (0008.4.)
- **Committed-image GC / prune trigger/cadence (deferred with Path 2).** Ownership is

- **Escape-hatch boundary — descoped for v1 (Human, 2026-07-22).** A full decision table

  non-MAF harness deferred to a separate FRD);
  authoring a predictive table is deferred.
- **Transfer / latency measurement (v1, Path 1).** Measure Path 1's **controller
  capture + zip + SHA-256 + file-transport delivery + in-sandbox unpack** against the
  0008.5 acceptance targets — note there is **no in-sandbox install** (deps are
  pre-installed in the captured `.python_packages`; the bootstrap sys.path-points at that

  Path 2 is ever needed. **Run jointly with 0008.5** as a large-payload transport spike

  catalog/package size to "platform defaults" leaning on this captured-content size +

  (FRD 0007) — a multi-agent app's envelope is the union across the coordinator + every
  reachable specialist, which this measurement should cover.

- **[0008.3](0008.3-state-store-and-tamper-evident-trust.md)** — routing digest is the
  deployment-artifact / committed-image content hash. *Resolved with 0008.3:* SHA-256
  canonical `sha256:<hex>`, carried as `(digest_kind, digest)` with `digest_kind ∈
  {funcs_zip, aca_image}` and compared pairwise; a **content-digest change is not a
  generation bump** — the generation tracks the *backing* only, and a different content
  digest is a **new session (drain-on-deploy, 0008.3 row 70)**, not an in-place swap.
  *Per 0008.3's redesigned trust model (Decisions 32-R/39-R):* the digest is
  **written by the controller onto the authoritative state row and verified against the
  live sandbox manifest** — no per-binding Key Vault signature or WORM log (dropped);
  the row is authoritative-by-construction (scoped RBAC + disabled Shared Key). This is
  a wording change only; everything packaging relies on (pair-compare, content change ⇒
  new-session drain not a bump, funcs_zip/SHA-256 for v1) is unchanged. *Round 2
  (2026-07-24):* the digest byte-source is now the **controller-captured app-content
  zip** (script root: code + vendored `.python_packages`), not a storage-resident
  Run-From-Package zip; SHA-256, pair-compare, and generation semantics are unchanged.
  The `funcs_zip` kind label still denotes "Path 1 Functions app content" — 0008.3 may
  relabel if it prefers, but the semantics hold.
- **[0008.4](0008.4-resource-residency-and-provisioning.md)** — ⚠️ **Round 2

  the **sandbox is identity-less and has no storage access**; the **controller**
  captures the app content from **its own** local script root and delivers it over the
  file transport (0008.5). So there is **no SG-runtime-identity read grant on deployment
  storage for content** — the prior note that "the SG runtime identity gets a scoped

  footprint further, consistent with 0008.4's least-privilege posture; please confirm no

- **[0008.5](0008.5-controller-sandbox-transport-and-protocol.md) — content delivery

- **[0008.7](0008.7-harness-compatibility-and-conformance.md) /
  [0008.10](0008.10-authoring-surface-and-config.md) — ABI requirement (confirmed with

  CPython 3.13/3.14** to match the generic   harness image ABI. **ABI mechanism (Round 3, larohra 2026-07-24):** the harness image
  is built *FROM* the Azure Functions Linux Python base image
  (`mcr.microsoft.com/azure-functions/python:<ver>`), inheriting the same
  architecture/glibc/CPython-minor as the app worker, so captured wheels import

- **[0008.5](0008.5-controller-sandbox-transport-and-protocol.md)** /
  **[0008.7](0008.7-harness-compatibility-and-conformance.md)** — committed images are
  children of a specific base image (and bake the captured runtime, which carries
  `protocol_version`), so the **re-commit fan-out is Path 2
  only (deferred)** — Path 1 **bakes no committed image**, so there is nothing to
  re-commit on a base bump. (Two independent version axes: the **generic image is
  version-agnostic** — stdlib bootstrap only, no baked MAF — picked up on next session
  create; while each **session's runtime/MAF version** is exactly what its captured
  `.python_packages` pinned, i.e. the customer's redeploy concern.) *Version-lifecycle policy — ACCEPTED (larohra,
  2026-07-22; owned by 0008.7):* **Lazy, latest-is-source-of-truth for the generic base
  image, no supported-version window.** This governs the **generic base image (stdlib
  bootstrap) for NEW sessions only**: a base bump triggers **no fleet action**; each app
  picks up the newest generic base when its **next session is created** (and, under
  Path 2, re-primes + re-commits on redeploy). **`protocol_version` is NOT governed by
  this policy** — it belongs to the **captured runtime** (per-session, travelling with the
  customer's `.python_packages`, per 0008.7), so it is **not "latest" and not tied to the
  base image**: a new session's protocol is whatever its captured runtime pinned, and a
  content/runtime change **drains the session** (row 70) rather than advancing it. So
  there is no "latest-protocol-against-an-old-session": an old session either runs its own
  captured-runtime protocol until it ends, or is drained on a content change. There is
  **no policy window to maintain in v1**. *Detection (0008.5):* the `ensure_ready`

  protocol is compatible with the current controller** and rejects **only on actual
  incompatibility**, *not* on a policy cutoff (backstop, not a version-window enforcer). The *stale-committed-image* backstop specifically is
  **Path 2 / deferred**. The ratified execution chain still

  no-window** shape; *proactive-fleet + a supported-version window* remain documented

  need lifecycle/GC (child-before-parent). *Create-path (settled here):* the
  image is produced at **deploy time** by the deployment/packaging flow (never at
  session create), and is labeled app/owner/build so its sandbox reference set is
  queryable. *Ownership (0008.4 has now chosen):* per 0008.4 "creator owns teardown,"
  per-deploy image **deletion is deploy/customer-side** (Decision 30 preserved — the
  runtime reaper never deletes images and never gains commit). *Why (A), not a
  runtime-reaped (B):* 0008.4's reason is **least-privilege** — giving the runtime
  image delete/manage rights would re-broaden the deliberately narrow per-session
  data-plane footprint (SandboxGroup Data Owner) that Decision 30 / 17-R keep tight.
  (B) is therefore **out for v1**, recorded as a governance-hook reconsider-trigger
  (runtime-owned reference-counted image GC = an explicit Decision 30 rights change →
  loop 0008.4). **Correctness = platform child-before-parent; the disk-id query is only
  an optimization.** Safety is guaranteed by the platform refusing to delete an image
  while any sandbox pins it, so deploy-side pruning is **blind best-effort** (attempt →
  rejected-while-pinned → retry) that **self-sequences** once the reaper has drained
  the pinning sandboxes; the `--disk-id` + app/owner/session labels (packaging
  guarantee) let the deploy side *optionally* query "zero references" to skip futile
  attempts — they are not a correctness dependency. No reaper→deploy eligibility signal,
  no image rights on the reaper, and no mirror-before-reap coupling (that is discharged
  at the *sandbox* layer — the reaper deletes a sandbox only after its terminal
  checkpoint is mirrored, so once a sandbox is gone no image durability is at stake).
  Compose contract (direction only, no deadlock): the 0008.12 reaper's per-session
  reclamation **drains references** on superseded images → the deploy identity
  **deletes** them, order enforced by the platform. **0008.12 and 0008.4 have both
  confirmed (A)**; the reaper lists committed images out-of-scope, stays purely
  sandbox-tier, and holds no image rights (Decision 30 verbatim). The **prune
  trigger/cadence is packaging-owned** (see the open question below).
