Network egress & OBO

How the sandbox can call approved services without ever holding credentials, and why that is the safe foundation for enterprise delegated auth.

Owns Decisions 10, 11, 16, 56 deny-by-default egress v1 · group-wide policy Finalized

1The big idea

A session sandbox runs partly untrusted agent work, so it starts with no open internet. Every outbound call must cross an egress proxy that both decides whether the destination is allowed and, when needed, injects the credential after the request has left the sandbox.

In plain terms: the sandbox is identity-less. It has no managed identity, no AAD token, no API key, and no secret on disk or in memory. If a model, MCP endpoint, telemetry sink, artifact service, or future broker is allowed, the proxy adds the right credential at the boundary. If it is not on the allow-list, the call never leaves.

◆No general internet

Default action is Deny, active before the harness runs. There is no startup window where code can fetch arbitrary packages or exfiltrate data.

◆Proxy owns auth

Managed-identity tokens or static-secret fallbacks are injected by proxy transforms. The workload never handles reusable credentials.

◆Enterprise seam

Because tokens stay outside the sandbox, a future OBO broker can call downstream APIs as the user without baking credentials into agent code.

2What happens on an outbound call

The proxy is both the reachability gate and the credential-injection point.

1
Sandbox code asks to call out — for example a model endpoint, MCP server, artifact service, telemetry endpoint, or future credential broker.
2
Traffic is forced through the proxy — no broad non-HTTP egress and no alternate identity path are available from inside the sandbox.
3
Allow-list is evaluated — ordered rules put exact host/path/method denies or transforms before broader host allows. A missing or narrowed rule produces a deny.
4
Credential is injected, if required — the preferred transform mints a scoped managed-identity token on the proxy side; static secrets are a fallback from the Sandbox Group secrets store.
5
Result returns to the sandbox — the credential itself never enters sandbox memory or disk, so compromise of the workload leaves nothing reusable to steal.

This depends on the packaging decision in 0008.6: the controller delivers the already-captured app environment, so sandbox startup does not need internet access.

3Key decisions

Decision 10 — deny from create

Production sandboxes start with full inspection and default egress Deny. The policy is active before the harness executes, so there is no permissive bootstrap phase to exploit.

Decision 56 — v1 sandbox is identity-less

The v1 sandbox gets no managed identity and no AAD token. The controller remains the sole writer of session state (0008.3), while outbound auth happens at the proxy boundary. That is why secrets and tokens never live in partly untrusted compute.

Decisions 11 and 16 — be precise about OBO

A workload managed identity is not user On-Behalf-Of. True OAuth OBO means calling a downstream API as the signed-in user, and v1 does not put user tokens in the sandbox. The FRD reserves the safe broker seam and defers the broker implementation.

Group-wide allow-list for v1

Destination intent comes from authored capability config, MCP server URLs, model endpoints, telemetry, artifacts, and the future broker. The controller compiles the union into one Sandbox Group policy, aligned with group provisioning in 0008.4.

✗ Rejected: credentials in agent code or sandbox memory

Passing user tokens, API keys, or workload tokens into the sandbox would turn a sandbox escape or malicious tool call into credential theft. The chosen pattern keeps those credentials outside the workload and scopes them at the proxy.

4Why enterprise customers care

Enterprise auth is less about making outbound calls possible and more about proving who can act, where, and with what blast radius.

◆Least privilege by construction

Allowed destinations are explicit. Credentials are scoped to host, path, method, and resource where the proxy transform supports it. The sandbox itself cannot reuse the credential elsewhere.

◆No credentials to leak

Auditors can reason about a strong invariant: agent code and model-driven tool calls do not receive tokens. The sensitive boundary is the proxy policy and its privileged operators.

◆Clean OBO path

A future broker can receive a proxy-injected workload token, perform delegated-user OBO outside the sandbox, call allow-listed downstream APIs, and return only the result.

◆No auth baked into agents

Authors do not hardcode secrets or special credential flows in agent code. Local authoring describes destination intent; deployment maps it to proxy-side transforms.

Important boundary: v1 reserves the OBO seam; it does not yet deliver true user-delegated downstream access. Sessions without an Entra user have no user to act for.
