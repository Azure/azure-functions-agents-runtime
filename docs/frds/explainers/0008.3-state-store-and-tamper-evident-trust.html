State store & tamper-evident trust

How the controller keeps the durable routing record authoritative when the sandbox is ephemeral, identity-less, and unable to write state.

Owns Decisions 5, 20, 31, 32-R, 33, 39-R Azure Table source of truth v1 · generation fixed Finalized

1The big idea

Every session needs a durable control-plane record that says which owner, app, content epoch, run status, and sandbox backing belong together. In v1 that record lives in an Azure Table, and it is the source of truth for session and run status.

In plain terms: the sandbox can run the agent loop, but it cannot update the routing ledger. The Azure Functions controller is the sole writer. The sandbox is identity-less, holds no storage credential, and therefore physically cannot write state. That makes the Table row tamper-evident: routing reads verify the row against a live sandbox manifest before submitting work.

◆Durable pointer

The session row stores owner/app partitioning, sandbox pointer, status, protocol, due-time fields, content digest, and generation. Run rows store run status and timeout deadlines.

◆Controller-only writes

All Table writes go through the controller under ETag-guarded conditional updates. End users never receive storage credentials, and the sandbox has no identity capable of reaching storage.

◆Verify before routing

Routing reads compare row fields to a live manifest from the ACA sandbox. A mismatch fails closed, emits a security signal, and quarantines rather than blindly following a stale pointer.

The design separates the hot, queryable control plane from optional archival data. For v1 routing, the Azure Table is the load-bearing system.

The storage is customer-owned: it lives with the app owner, not in a runtime-team service. The key invariant is not the account name; it is that Shared Key is disabled, roles are scoped narrowly, and only the controller can write the Table.

3The fail-closed routing check

A Table row is authoritative, but routing still verifies the row against the live sandbox before any turn is submitted.

Digest is routing evidence: the digest comes from the controller-captured content described in 0008.6. Because every session row carries that digest, the controller always knows which content epoch the session belongs to and can refuse to talk to the wrong epoch.

4Digest, deploys, and generation are different things

This sub-FRD is the canonical place where the difference is settled: the digest tracks content; generation tracks the sandbox backing.

◆Digest = content epoch

The digest is stamped once when the session is created. It identifies the captured app content for that session. If the controller's current content digest changes after a deploy, the old session is drained rather than made compatible.

◆Generation = backing

The generation identifies the concrete sandbox backing: instance plus disk. It never encodes a content change, and it does not advance just because a new deployment exists.

Drain-on-deploy: row 70

When the session's stamped digest differs from the controller's current captured-content digest, the lifecycle path drains the session: in-flight grace, abandon if needed, tombstone, then 410 Gone. The next session stamps the new digest. The drain mechanics live in 0008.12; this state row supplies the digest comparison.

v1 generation is fixed at creation

A state-preserving generation advance requires rebuilding committed state on a different sandbox backing, which needs the external checkpoint mirror. That is v2-only. In v1, suspend/resume and crash-with-disk-intact stay on the same generation; true backing loss tombstones and returns 410, never a bump.

5Lifecycle reads the same table

The reaper does not have a special index or side ledger. It scans the same authoritative Table records that routing and status reads use.

◆Run timeout

Run rows use expires_at as the run-timeout deadline. The reaper filters by status plus due time, then applies controller-owned conditional updates.

◆Idle reclaim

Session rows use expires_at as the idle-reclaim deadline, with last_activity_at and idle_policy_armed on the session row.

✗ Rejected: separate due-work index

A reaper-friendly index would need a different partitioning scheme, so it could not be co-written atomically with the owner-partitioned session/run row. v1 keeps one source of truth and lets the reaper scan it directly at the expected scale; 0008.12 owns the detailed lifecycle policy.

6What makes it tamper-evident

The design is intentionally platform-native: controller-only writes, identity-less sandboxing, ETags, generation, and live ACA manifests.

◆No sandbox state credential

The sandbox cannot write the Table because it has no identity or token. Outbound auth is injected by the egress proxy, not stored inside the sandbox (0008.9).

◆Rollback is visible

The generation is monotonic on the ETag-guarded row. A stale pointer cannot be silently accepted as the latest backing.

◆Wrong sandbox is visible

The live manifest must agree with the row's owner, app, session, group, generation, digest, and protocol. If it does not, routing fails closed.
