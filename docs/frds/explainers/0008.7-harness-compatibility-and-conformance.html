Harness compatibility & conformance

How v1 keeps the same MAF behavior inside ACA, proves it with golden traces, and fails closed when a feature is not proven.

Owns Decisions 34–37 MAF-only v1 Golden-trace gate Finalized

1The big idea

A harness is the engine that runs the agent loop: model calls, tools, skills, events, cancellation, and final output. For v1, ACA changes where that engine runs, not which engine runs.

In plain terms: v1 keeps Microsoft Agent Framework (MAF) as the only trusted harness. Before any sandbox harness is trusted, it must pass a normalized golden-trace conformance check against today's local MAF behavior. If an agent needs something the harness has not proven, registration fails instead of silently downgrading.

◆One variable at a time

Relocate MAF into the session sandbox, but do not swap to a different harness in the same release. That keeps regressions attributable.

◆Proof before trust

The sandbox adapter must match core MAF behavior: event ordering, key fields, terminal status, errors, cancellation, tools, MCP, skills, and structured-output cases.

◆Fail closed

Unsupported or unrecognized capabilities stop startup. A capability is supported only after a conformance trace exercises it.

2What the harness contract actually is

The design separates the stable runtime protocol from the code that adapts a specific harness to it.

1
Wire protocol — the harness-neutral file/event contract: request envelope, status/result, monotonic events, cancellation, checkpoints, manifest, and protocol_version. It rides on the six-verb controller↔sandbox transport (0008.5).
2
Library adapter — the v1 path. The MAF adapter wraps the existing Python runner behavior inside the sandbox and recreates clients after resume.
3
Process shim later — future CLI/process harnesses need their own reviewed shim, exit-code mapping, event translation, and denial rules. They are not implied by image compatibility.
4
Manifest capabilities — instructions, history, tools, MCP, skills, streaming, structured output, reasoning/tool-call records, cancellation, checkpoints, observability, and subagent delegation (0008.13) are enumerated under the single v1 protocol_version.

3Conformance: same core behavior, not byte-identical logs

Golden traces make “MAF still behaves like MAF” testable without locking the system to model wording or streaming timing.

◆What is asserted

Event type and ordering, presence of key fields, terminal status, status/error body contracts, input/output success, structured-output failure, timeout, mid-run cancellation, and tool/MCP/skill behavior across a small core suite.

◆What is normalized away

Reasoning text, exact wording, token-by-token streaming timing, and provider-specific metadata. Re-baselining happens only for an intentional behavior change or protocol_version bump.

Invalid output is a failed run

If the harness completes but returns output that fails schema or conformance validation, the run is terminal failed with a typed validation RunError. It is never reported as succeeded with a bad payload. The controller remains the authoritative input pre-dispatch and output post-run validation gate.

ensure_ready is a session consistency guard

ensure_ready asks: “does this sandbox still speak this session's captured-runtime protocol?” It is not a supported-version window and does not make old and new content epochs coexist. In v1, a content digest change drains and tombstones the old session; clients start fresh.

4Image and ABI boundaries

This sub-FRD owns the harness runtime/ABI definition, but it does so by inheriting the Functions base image rather than inventing a new customer contract.

In plain terms: the bootstrap image is built FROM the Azure Functions Python base for Linux Python 3.13–3.14. The customer's vendored .python_packages — including compiled wheels — were built for that same base, so importing them in the sandbox is ABI-compatible by construction. The image bakes no MAF and no app dependencies; it runs the single captured environment delivered by packaging (0008.6).

◆Custom image is allowed

A custom sandbox image may be used, but v1 still requires it to be MAF-conformant and to pass the same golden-trace gate before it is trusted.

◆What is deferred

A non-MAF or bring-your-own harness is deferred to a separate FRD with its own adapter, shim validation, capability map, and conformance suite.
