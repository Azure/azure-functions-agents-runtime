Sandbox packaging — image & content

How the agent's code and its dependencies get into the sandbox — safely, with no internet at startup and nothing to install.

Owns Decisions 8, 17, 17-R/48 Model-1 packaging v1 · Path 1 only Finalized

1The big idea

Before an agent can run inside its sandbox, two things must meet there: a generic bootstrap image and the captured app environment (the author's code + its resolved dependencies). This sub-FRD decides how they come together.

In plain terms: we do not let the sandbox pip install or git clone anything at startup. Instead, the Azure Functions controller captures the app it already has on its own disk — the code plus the dependencies Functions already vendored — zips it, fingerprints it, and hands it to the sandbox over the secure transport. The sandbox just runs what it's given.

◆Generic image

A tiny stdlib-only bootstrap, built from the Azure Functions Python base. It bakes no MAF and no app code — so it never needs rebuilding when an author changes their agent.

◆Captured content

The app's .agent.md files, tools, skills, MCP config, and one pip-resolved dependency tree — which already contains our runtime and the MAF it pulls in.

◆One coherent env

Because the runtime is a normal pip dependency, the customer's build already resolves runtime + MAF + tools together. There is only ever one MAF — so dependency-isolation isn't a problem to solve.

2Model-1: run from the captured environment

The single most shaping decision — and it removes a subsystem rather than adding one.

Transport remains the identity-less six-verb file plane (0008.5).

✗ Rejected: install-at-startup

pip install / curl | bash / git clone at session start are rejected outright — they force a startup window with permissive network access before lockdown, and re-fetch from the internet for every session. The prebuilt image + delivered content avoids both.

3Key decisions

Reuse the deployment content — no bespoke format (Decision 17-R / 48)

The per-app layer is not a new signed content-package format. It's exactly the content the Azure Functions deployment already produced. We capture it from disk rather than inventing a delivery scheme.

Digest source: the captured script-root zip — not the deploy artifact

The epoch digest is a SHA-256 over the controller-captured script-root content (code + vendored .python_packages), not an IaC-pinned Run-From-Package deploy artifact. It fingerprints what actually runs.

Build FROM the Functions Python base (ABI)

The bootstrap image is built from the Azure Functions Python base (Linux, Python 3.13–3.14), so the vendored .python_packages — including compiled wheels — are ABI-compatible with the interpreter that runs them. protocol_version travels with the captured runtime, not the base image.

Content change ⇒ drain the session (not a generation bump)

A redeploy changes the captured content digest. Rather than keep old sessions compatible, v1 drains the session (grace → tombstone → 410); the client starts fresh on the new epoch (0008.3 row 70). Generation tracks the sandbox backing only.

MAF-only for v1

A custom sandbox disk image is permitted, but in v1 it must be MAF-conformant (golden-trace gate, 0008.7). A non-MAF / bring-your-own harness image is deferred to a separate FRD.
