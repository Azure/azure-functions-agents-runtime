HTTP API — sync, async & streaming

The caller-facing contract: simple chat waits for an answer, long work opts into a small LRO model, and streaming is replayable SSE.

Owns Decisions 3, 19, 25 Sync default 180 s cap Finalized

1The big idea

This is the part callers see: HTTP routes, waits, status codes, and reconnect rules while Azure Functions acts as the authenticated controller for one ephemeral ACA sandbox per session.

In plain terms: POST /agents/{slug}/chat is still request→answer by default. Add Prefer: respond-async when the turn may run long. Use SSE for stream updates, and reconnect with Last-Event-ID; losing the connection does not stop the run.

◆Default sync

/chat and /chatstream preserve today's default shapes, including x-ms-session-id.

◆Explicit async

Prefer: respond-async returns 202 Accepted, run_id, and URLs to status, result, events, and cancel.

◆Replayable stream

SSE frames carry monotonic id: values. The client re-attaches by sending the last seen id.

2Synchronous vs asynchronous / streaming

v1 allows one active run per session. A distinct second submission gets 409 active_run_exists unless the caller cancels first (0008.2).

◆Synchronous default

1
Call chat — POST /agents/{slug}/chat, no async preference.
2
Wait under 180 s — sandbox lookup/create/resume, verification, and execution all fit inside the controller's cap.
3
Answer or fail — success is 200; typed request/app failures use the normal HTTP model; a sync window breach returns 504.
4
Cap breach cancels — if the run would still be going, the controller cancels it and the terminal state is canceled.

◆Asynchronous / streaming

1
Ask explicitly — POST /agents/{slug}/chat with Prefer: respond-async.
2
Get the LRO shell — 202, Location, Retry-After: 2, plus status_url, result_url, events_url, and cancel_url.
3
Poll or stream — read status, fetch the result, or consume replayable SSE from the events route.
4
Re-attach — reconnect SSE with Last-Event-ID; a normal lease close is not cancellation.

The status route is the run URL itself — there is no separate /status suffix. Every route re-checks auth and session ownership.

4Status, result, and failure semantics

Async uses a small long-running-operation model: HTTP says whether the read/submission worked; state and error describe the run.

◆Status is readable state

GET .../runs/{run_id} returns 200 when the run row is readable, even for terminal failed runs.

◆Result can expire

GET .../result returns the answer while retained. Once reaped or tombstoned, it returns 410 Gone; status can still report the terminal state.

◆Streaming failures are in-band

/chatstream can use HTTP status only before the stream starts. Later run failures surface as named terminal SSE events, then close.

◆Sync never auto-asyncs

A sync 504 carries retry_with: respond-async and x-ms-retry-with: respond-async; SDK retry helpers are opt-in.

5Reconnect, cancellation, and v1 boundaries

Connection liveness and run liveness are separate. The sandbox keeps journaling until the run reaches a terminal state or the controller explicitly cancels it.

Disconnect ≠ cancel

A dropped SSE connection, graceful lease close, or closed client socket does not kill the run. Clients reconnect with Last-Event-ID or poll status/result.

Only cancel or the sync cap stops it

POST .../cancel is the normal stop path. The other v1 stop case is controller cancellation when the 180-second synchronous cap is hit.

Replay and conflict stay unambiguous

Same Idempotency-Key + same payload replays the same attempt. A distinct submission while a run is active returns 409 active_run_exists; same key with a different payload returns 422 idempotency_key_conflict.
