Dynamic Workflows on ACA — compatibility analysis

Why "dynamic workflows" + the ACA sandbox stays fail-closed in v1 — and what a future fix would actually need.

Analysis only · no binding decision v1 · fail-closed (Decision 36) Finalized (analysis)

⚠ This combination is not enabled in v1

An app with workflows.enabled: true plus the ACA sandbox backend fails closed at startup (Decision 36, owned by 0008.7). "Finalized" here means this analysis is reviewed and accepted as part of FRD 0008 — not that the feature is turned on. The actual compatibility fix is deferred to a future implementation FRD.

1What "dynamic workflows" are

Dynamic Workflows is a feature of this runtime — not of the Microsoft Agent Framework (MAF).

In plain terms: a tool can mark itself @workflow_tool-safe (deterministic, idempotent). At request time the LLM can hand a small DAG of those tools to a durable Azure Durable Functions orchestrator instead of running them as ordinary in-turn calls. The runtime wires that orchestrator at app-registration and exposes exactly five control tools — start_workflow, get_workflow_status, list_workflows, cancel_workflow, terminate_workflow. MAF never sees a "workflow" — just five ordinary async callables.

2The tension with ACA

FRD 0008 moves the whole harness into one ACA sandbox and turns Functions into a thin controller (0008.1). Crucially, the sandbox is not a Functions Host.

◆What the sandbox carries

Under 0008.6's Model-1 packaging the image is a stdlib-only bootstrap that bakes in no MAF; the runtime + MAF arrive as the customer's captured .python_packages. The stack that executes is a fixed entry point over MAF — never a Functions Host.

◆What workflows need

Promoting a tool call into a Durable orchestrator run depends on exactly the Functions Host machinery the sandbox deliberately does not carry. That is the whole tension.

3The precise finding (a useful reframe)

The headline is sharper than "the orchestrator doesn't exist under ACA."

✓
The orchestrator DOES exist — the controller is still an ordinary Functions app, and it registers a fully wired Durable orchestrator for any project with workflows.enabled, regardless of which backend runs the chat turn.
✗
Only the bridge is missing — what ACA lacks is the path from the sandboxed MAF agent's tool-call boundary back to that already-running controller-side orchestrator.
➜
So the problem shrinks — from "build a workflow engine inside a locked-down sandbox" (hard, likely wrong) to "give the sandbox a controller-mediated path to invoke five specific control tools" (bounded, and analyzed in the FRD).
