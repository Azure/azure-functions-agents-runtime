Snapshot, auto-suspend & durability

How a sandbox session survives idle time and ordinary crashes in v1 — and where the line is drawn before v2 durability.

Owns Decisions 9, 18, 27, 28 Platform-only v1 durability Mirror deferred to v2 Finalized

1The big idea

FRD 0008.8 decides what durability means for a persistent ACA sandbox session. v1 deliberately uses the platform boundary: ACA snapshot plus auto-suspend/resume keeps the same sandbox warm enough to continue between turns, then scale to zero while idle.

In plain terms: v1 does not copy every completed turn to an outside checkpoint store. The sandbox writes its conversation state to its own on-disk session directory. ACA then suspends that idle sandbox and later resumes the same backing — same instance, same disk, same generation — before the controller sends the next turn.

◆Common case

Idle between turns becomes cheap: the sandbox is suspended, its disk remains the session record, and resume brings it back warm before work continues.

◆Hard boundary

If the sandbox and its suspended state are truly lost in v1, the conversation content is gone. The session tombstones with 410 Gone; the client starts a new session.

◆v2 target

The owner-scoped external checkpoint mirror — losing a sandbox without losing the conversation — is retained as the v2 durability add, not part of v1.

2The all-or-nothing turn commit

Platform suspend is only safe if the disk is never left halfway through a turn. The harness therefore commits a whole turn with one atomic pointer move.

1
Stage the whole turn — conversation history, tool working files, and run result data for turn N are written into a private staging tree, never over the live committed turn.
2
Flush the staged files — files and directories are fsynced so the full staged set is durable before it can become current.
3
Pointer-commit once — one atomic rename advances a current pointer or manifest to turn N. That pointer and its parent directory are fsynced before the turn is acknowledged.
4
Resume cleanly — after crash or warm resume, the harness reads current and discards incomplete staging. Either turn N committed completely, or turn N-1 remains the last truth.

Why a single pointer matters

A turn is a multi-file state change. Per-file temp-write and rename is not enough, because a crash can land between independent renames. The single pointer-commit makes the turn an all-or-nothing unit.

3Active runs do not nap

ACA idle reclamation is based on quiet request traffic, not on whether an agent is thinking. So v1 explicitly controls suspend around every run.

◆Before accepting work

The controller disables auto-suspend and keeps the session non-idle before the run starts. A sandbox watchdog bounds the authored timeout; the platform cooldown is not the run limiter.

◆After terminal

When a sync or attached run reaches terminal state, the controller re-arms the idle policy. For detached async, the periodic reconciler in 0008.12 repairs any terminal-or-crashed sandbox still left in the run-disabled state.

Crash vs loss: a harness crash with disk intact abandons the in-flight run but keeps the session. The next resume returns to the same sandbox backing and last committed turn. A truly lost sandbox is different: v1 has no outside copy to rebuild from, so it tombstones.

4Resume, generation, and redeploy

Resume is verified before new work, but it is not a state migration. In v1 it always means the same backing and the same generation.

◆Same-generation resume

After suspend/resume or crash-with-disk-intact, live clients, token providers, MCP connections, and leases are recreated. The controller verifies the manifest, protocol, content digest, owner/app/session identity, sandbox ID, generation, and last-run journal before submitting work. See 0008.3 for the generation model.

◆Generation advance is v2-only

A generation advance means state-preserving rebind to a different sandbox backing. That requires the external mirror to reconstruct state, so v1 never advances generation: same backing resumes; lost backing tombstones.

✗ Not silent redeploy recovery

A content-digest change is a deliberate lifecycle boundary. Row 70 drains the session by design — grace, abandon in-flight work, tombstone, then 410 — and the client starts fresh on the new epoch. That is the packaging/epoch rule from 0008.6, not a warm-snapshot compatibility bug and not silent loss.

6The honest residual

The remaining v1 question is intentionally narrow.

Tracked preview-durability item

v1 assumes ACA auto-suspend reliably preserves the on-disk session directory within a single epoch. If the platform drops that disk state, v1 has no mirror fallback and must tombstone. Redeploy is not part of this risk; digest changes already drain by design.

Why the v1 cut still wins

It keeps the always-needed correctness rules — atomic turns, no suspend during active runs, verified resume, explicit tombstone on true loss — while deferring only the larger external-mirror machinery to v2.
