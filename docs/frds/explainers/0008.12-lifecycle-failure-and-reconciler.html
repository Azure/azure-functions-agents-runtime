Lifecycle, failure & reconciler

How sessions/runs move through state, how failures become terminal records, and why v1 needs a small timer reaper — not Durable Functions.

Owns Decisions 4, 21, 22, 24 State machines v1 timer ≈ 1 h backstop Finalized

1The big idea

A session is one ephemeral ACA sandbox running the whole MAF agent loop. Azure Functions is the authenticated controller and sole ledger writer: it admits one active run, records terminal status, and the reconciler handles cases no request is guaranteed to observe.

In plain terms: the sandbox does the long-running work; the controller keeps the official scoreboard. If the sandbox finishes, crashes, disappears, idles too long, or becomes stale after a deploy, the controller writes one monotonic outcome and either keeps the session reusable or returns 410 Gone so the client starts fresh.

◆Two state machines

Sessions move through create, ready, running, suspend/resume, delete, and terminals. Runs persist only accepted/running plus finals.

◆Verified liveness

A stale heartbeat is only suspicion. Before freeing a slot, the controller confirms the process is dead or destroys the sandbox to make death definitive.

◆One reconciler

A plain Functions timer plus fast-paths scans the source-of-truth table directly. No Durable orchestrator; no separate due-work index.

2State machines and terminal states

The design is small: one session row gates the active run; run rows record durable terminal status. Every terminal clears active_run_id.

◆abandoned is no-fault

No terminal was reported: the sandbox was lost, or the harness died before journaling. Written only after death is confirmed.

◆Status and content split

Terminal status survives in Azure Tables. In v1, result content stays in the sandbox until fetched or idle-retention expires.

3Drain-on-deploy: digest epochs

Epochs are keyed by the SHA-256 digest of the captured script-root zip — controller code plus vendored .python_packages, defined by 0008.6 and stamped by 0008.3.

1
Next request detects stale epoch — the session's captured-script-root digest differs from the controller's current digest. A worker restart with the same digest does nothing.
2
Grace — any in-flight run gets a short chance to finish and report a real terminal.
3
Abandon in-flight — if it does not finish, the run is written terminal abandoned, clearing the one-active-run slot.
4
Tombstone — the session row is tombstoned; old-epoch sandboxes are idle-reaped within the retention window.
5
410 Gone — the same session_id is dead. The client creates a new session on the new epoch.

✗ Rejected for v1: carry the live session across a redeploy

Durable continuity across an epoch change needs the external checkpoint mirror deferred by 0008.8. v1 drains and tombstones instead.

4Crash-liveness and verified kill

The reconciler must never create split-brain by freeing a slot while the old process may still hold the OS lock.

◆Crash with disk intact

Reachable sandbox, no terminal, stale heartbeat → probe. Only a released OS lock/process group or verified kill authorizes abandoned. The sandbox is retained.

◆Unverifiable death

If death cannot be proven, reclaim the sandbox to produce definitive death; only then abandon the run and free the slot.

◆Lost sandbox

Gone or disk unrecoverable: write abandoned, tombstone the session, return 410. No v1 rebuild.

◆Adopt before abandon

If a reachable sandbox has terminal status.json/result.json, adopt succeeded/failed/timed_out/canceled before considering abandonment.

5The due-time model and bounded scan

The timer reads the single source-of-truth session/run table from 0008.3 directly. There is no separate due-work index in v1.

Due caseRows scannedAction
Run timeout backstopRUN rows in accepted or running with expires_at ≤ nowVerify liveness, then time out/abandon safely.
Idle reclaimSESSION rows with terminal-idle expires_at ≤ nowETag-CAS confirms active_run_id = null, then delete sandbox/snapshot and tombstone.
Idle-policy repairSESSION rows terminal with idle_policy_armed = falseRe-arm the ACA idle policy that was disabled during the run.
The whole due-time contract: one state-dependent expires_at is the next due timestamp (run timeout on RUN rows, reclaim deadline on SESSION rows). idle_policy_armed marks terminal sandboxes needing policy repair, and last_activity_at feeds idle expires_at. There is no separate reclaim_at.

The scan stays bounded because terminal and tombstoned rows are pruned/archived after retention; at v1 scale it covers only the live plus recently-terminal working set. Writes still rely on ETag-CAS and generation guards.
