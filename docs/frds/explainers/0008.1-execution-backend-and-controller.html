FRD 0008.1 · Sub-FRD · for team feedback

Execution backend & the controller model

Where the agent actually runs — and what Azure Functions becomes once it is no longer the compute.

Owns Decisions 1, 2, 12, 13 opt-in · provider: aca_sandbox default unchanged Finalized

1The big idea

Today the runtime runs an agent's whole "thinking loop" — calling the model, using tools, keeping history — inside the Azure Functions Python worker. This sub-FRD adds a second, opt-in place to run that loop, and redefines what the Functions app is.

In plain terms: introduce one clean seam — an AgentExecutionBackend interface — between "the Functions app" and "wherever the agent runs." Then move the agent into one ACA sandbox per session and let Azure Functions step back into the role of an authenticated controller: neither the agent runtime anymore, nor a dumb byte-shuffling proxy.

◆One sandbox / session

The complete harness (the MAF loop + its tools) runs inside a single ACA sandbox per session — not in the worker, and not split across the two.

◆Controller, not proxy

Functions authenticates the caller, checks who owns the session, creates or resumes the sandbox, and routes the run. A trusted control plane — not a runtime, not a pass-through.

◆Default stays put

provider: in_process (today's in-worker execution) remains the default; provider: aca_sandbox is experimental and must be explicitly turned on.

2The seam — one small interface

The controller talks to any execution location through a tiny async interface. Only typed, serializable data crosses it — never a live agent or Python tool object.

class AgentExecutionBackend(Protocol):
    async def start_run(self, request: StartRunRequest) -> RunHandle: ...
    async def get_run(self, context: RunContext) -> RunStatus: ...
    async def read_events(self, context: RunContext, after_sequence: int) -> AsyncIterator[RunEvent]: ...
    async def cancel_run(self, context: RunContext) -> RunStatus: ...

◆Two implementations

LocalExecutionBackend wraps today's runner.py; AcaSandboxExecutionBackend drives a sandbox. Handlers depend on the interface, never on the ACA SDK.

◆Sync is not a special case

start_run always creates a run resource — so a synchronous chat is just "start a run and wait." Run IDs, telemetry, cancellation, and idempotency stay identical for sync and async.

In the runtime's pipeline (discover → translate → register → execute) the seam lives in execute; registration stays the only Azure-aware stage that picks and wires the backend. "Who the agent is" is bound once at registration — a closure over resolved + capabilities for in-process, or the controller-captured script-root content for the sandbox (0008.6).

4Key decisions

Decision 1 — where the agent executes

The complete harness runs inside one ACA sandbox per session — not inside the Functions worker, and not split across the two.

Decision 2 — what the Functions app is

An authenticated session controller: authenticate, check ownership, create/resume the sandbox, route the run. Neither the agent runtime nor a byte-shuffling proxy.

Decision 12 — default behavior unchanged

In-worker execution (in_process) stays the default; the sandbox backend (aca_sandbox) is experimental and opt-in — this feature adds a path, it doesn't replace one.

Decision 13 — direct Functions Host integration deferred

A Python-level controller is enough to prove the product; wiring this deeper into the Functions Host is postponed (a longer-term, cross-team effort).
