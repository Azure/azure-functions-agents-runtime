Controller ↔ sandbox transport & protocol

The single authenticated file/exec plane that lets the controller deliver content, start runs, stream journal events, fetch results, and cancel — without opening sandbox ingress.

Owns Decisions 7, 23, 26, 29 Six verbs v1 · pull/cursor based Finalized

1The big idea

Once a session has an ACA sandbox, Azure Functions still stays the authenticated controller. This sub-FRD defines the only way the controller talks to that sandbox: one authenticated six-verb file/exec transport over the ACA data plane, with the sandbox exposing no anonymous port and no second inbound control path.

In plain terms: the controller writes files, starts one detached entry point, and reads the files the sandbox journals back. That same channel carries run-control, the exec / journal data plane, and content delivery for the captured app. The sandbox is identity-less and never fetches its own code; it only runs what the controller delivers.

◆Only inbound path

No sandbox HTTP listener is part of v1. Every controller action is initiated through authenticated file operations plus detached exec.

◆Connectionless by design

A run is not tied to the Functions instance that submitted it. Another instance can reattach by resolving state, running readiness, and reading the journal.

◆Same plane, three payloads

Run envelopes, status/events/results, and the delivered app content all ride the same plane. Content is a larger payload class, not a seventh run verb.

2The six-verb contract

The controller depends on a small transport abstraction. The v1 implementation is the ACA file+exec journal; any future transport must preserve the same semantics before controller code can ignore the swap.

VerbWhat it meansImportant return / rule
submit(run_id, envelope)Write the run request and launch the detached entry point.Idempotent: duplicate run_id returns the existing run, never a second process.
get_status(run_id)Read current or terminal state.In v1, terminal status can still be answered from the controller-owned Tables record after the sandbox is reaped.
read_events(run_id, since)Read journal events after the caller's cursor.Returns events or snapshot-restart when Last-Event-ID is older than retention.
get_result(run_id)Read the per-run result payload.Returns result while retained, or result-evicted after post-terminal grace and reap.
cancel(run_id)Signal the recorded process group through the entry point.Escalates to verified kill before forcing terminal canceled; never frees a slot while work may still run.
ensure_ready(sandbox)Resume if needed and verify the session manifest before work.Checks content digest and protocol_version compatibility for this session.

All six verbs are controller-initiated. The sandbox executes and journals; it does not call back into Functions. Streaming details are consumed by 0008.11.

3How a run moves through the journal

Sync and async use the same detached execution pattern so the SDK's fixed exec-read timeout never becomes the runtime limit.

1
Submit — the controller writes inbox/{run_id}.json and starts the sandbox entry point in a detached process.
2
Accept atomically — the sandbox creates runs/{run_id}/, records process metadata, and journals accepted. Duplicate submissions reuse that directory.
3
Journal progress — status, append-only events.jsonl, and the eventual result.json are all per-run files under runs/{run_id}/.
4
Poll by cursor — clients reconnect with Last-Event-ID; the controller reads events after that cursor instead of holding a live socket.
5
Finish or cancel — terminal state frees the one-active-run slot only after the run is actually terminal or death is verified.

✗ Rejected: anonymous ingress or mandatory tunnel

An anonymous sandbox port is not an allowed fallback. A required private tunnel adds heavy networking prerequisites. File/exec won because the live spike proved the core mechanism while keeping the sandbox sealed from inbound traffic.

4Streaming, reconnect, and retention

Events are pull/cursor-based. That is the intentional trade: less immediacy than token-level push, but no connection-bound run and no sandbox ingress.

◆Run journal

events.jsonl rotates in bounded 1 MiB segments and acts as a transient replay buffer. status.json and result.json do not rotate and hold the authoritative terminal record while the sandbox exists.

◆Reconnect cursor

read_events uses the caller's Last-Event-ID. If the cursor is too old, the controller returns snapshot-restart with the earliest retained event so the client re-reads status/result, then resumes without a silent gap.

Why this survives controller recycle: a Functions instance owns no in-memory stream. A later instance resolves the current binding, runs ensure_ready, and continues reading the same on-disk journal from the caller's cursor. A live stream would fail that scenario; the journal is deliberately connectionless.

5Content delivery rides the same plane

The transport is not just for runs. Under Model-1 packaging, the controller-captured script root is delivered into the identity-less sandbox over this same authenticated file plane.

1
Capture — the controller captures its own script root: app code plus the vendored .python_packages tree described by 0008.6.
2
Fingerprint — it zips that content and computes the SHA-256 digest that identifies this session's content epoch.
3
Deliver — the controller writes the large content payload into session/content/. This path is separate from the 4 MiB run-journal cap.
4
Verify before submit — the sandbox unpacks and verifies the digest before any run is accepted; delivery is a bring-up gate, not interleaved with turns.

The sandbox never downloads the app, resolves dependencies, or reads storage. Content capture/format belongs to 0008.6; this sub-FRD owns the delivery channel, digest gate, and size/throughput envelope.

6Protocol version belongs to the captured runtime

protocol_version is a session-scoped compatibility guard, not a base-image constant and not a fleet-wide "latest" comparison.

◆Travels with .python_packages

The runtime and MAF version are captured per session from the app's vendored dependency tree. The sandbox reports the protocol for that captured runtime epoch; 0008.7 owns the protocol / ABI policy.

◆Checked during readiness

ensure_ready refuses to submit if the sandbox manifest does not match the session's captured epoch. If app content changes, v1 drains the session and the client starts fresh on the new epoch.
