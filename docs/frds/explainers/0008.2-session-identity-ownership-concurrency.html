Session identity, ownership & concurrency

Why a session is the durable unit for routing, state, ownership, and admission — and why v1 allows only one active run inside it.

Owns Decisions 6 & 15 session_id is the anchor v1 · one active run Finalized

1The big idea

A sandbox-backed agent conversation is not just a request. It is a long-lived session: the thing that owns memory, files, the active run slot, and the backing ACA sandbox. The public session_id is the lookup key for all of that — but it is never proof that the caller is allowed to use it.

In plain terms: every call says, “I want to use this session_id.” The Azure Functions controller then checks who the caller is, compares that caller to the session's stored owner, and only then routes work to the sandbox. The sandbox is identity-less, so it cannot decide ownership or write session state for itself.

◆Routing key

The session_id points to one controller-authoritative state row, one owner binding, one content epoch, and the current backing sandbox when the session is alive.

◆Owner binding

Ownership comes from the Functions platform gate: either an Entra user surfaced by Easy Auth or the Function App itself for app-level calls such as function-key access.

◆Active-run slot

v1 admits at most one top-level run per session. A second overlapping submission on the same session gets 409 Conflict with the active run_id.

2What the controller stores and checks

The controller is the trusted boundary. It is the only component that resolves caller identity, authorizes session access, and writes the control-plane row that every later decision uses.

1
Platform auth runs first — function keys or App Service Authentication / Easy Auth gate the endpoint before controller code runs. The runtime does not invent a second identity system.
2
Controller resolves an owner — entra_user when Easy Auth provides a stable user principal; otherwise function_app, bound to the app identity plus the agent slug.
3
Owner is stored with the session — raw claims stay out of the session_id and labels. A versioned SHA-256 owner hash is used for paths/labels, with the canonicalization version on the state row owned by 0008.3.
4
Every call is re-authorized — any controller instance recomputes the incoming owner from the request and compares it to the session binding before reading, writing, running, canceling, or routing.
5
Only then does the sandbox run — the sandbox receives typed run work over the authenticated transport. It never receives raw owner claims and cannot write the state store itself.
Important consequence: when the owner is function_app, the app is the trust boundary. The runtime cannot separate two end users who share the same app-level credential; apps that need per-user isolation should use Easy Auth / Entra.

3How one-active-run admission works

The concurrency rule is intentionally small: one top-level run may occupy the session's active slot. Nested in-process agent delegation is still part of that same run, not a second run.

◆Start is compare-and-set

Run start updates the session row with an ETag-conditional active_run_id: null → run_id. If two callers race, only one wins the compare-and-set; the loser sees the already-active run.

◆The sandbox also locks locally

Inside the sandbox, an OS file lock and run journal are the live-process authority while a detached run is active. The short storage lease used for submit is not treated as proof that the process stopped.

4Verified kill and disconnect semantics

The controller must never free or reuse a backing just because a lease expired or a client disappeared. It must prove the old run/process is gone, then record that fact in state.

◆Verified kill prevents split-brain

Before a session frees or reuses its sandbox backing, the controller confirms the prior process is actually dead. That check pairs the control row with sandbox liveness evidence so two processes cannot both believe they own the same session.

◆Disconnect is not cancel

If the client drops the HTTP connection, the run continues. Only an explicit cancel request moves the run toward cancellation; lifecycle owns how that process is stopped and adopted terminally.

Crash with disk intact resumes; true loss tombstones

If the harness crashes but the sandbox disk is intact, the session resumes from the last committed checkpoint on the same backing. If the sandbox or snapshot is truly lost, the session is tombstoned: the same session_id returns 410 Gone, and the client creates a new session.

✗ Rejected: treating disconnect or lease expiry as process death

A dropped client connection and a released submit lease are control-plane signals, not proof about the sandbox process. v1 requires verified liveness before freeing the active slot or backing, which is the split-brain guard coordinated with 0008.12.
