Subagent delegation compatibility

How FRD 0007's coordinator-plus-specialists model runs inside the ACA session sandbox without creating extra sandboxes or a new run surface.

Owns Decisions 42–46 FRD 0007 compatible v1 · single sandbox Finalized

1The big idea

FRD 0007 shipped multi-agent delegation: a coordinator sees each specialist as an in-process delegate_<slug> tool and calls it inside the coordinator's own Microsoft Agent Framework run. FRD 0008 keeps that shape under ACA.

In plain terms: think of the session sandbox as the brain + hands for a whole team of agents. The coordinator and every reachable specialist live together in one room, share the same delivered app content, and use the same controlled outbound doorway. Delegation is still one top-level run asking an in-room specialist for help — not a new session, not a new sandbox, and not a second API call.

◆Coordinator

The entry agent owns the user-facing run and receives delegate_<slug> tools for its declared subagents:.

◆Specialists

Each specialist is built fresh per delegated call and runs in-process through MAF Agent.run(), using only the task string passed by the coordinator.

◆One sandbox

All reachable agents co-locate inside the one ephemeral ACA sandbox for the session. Specialists get no separate session, binding, identity, or sandbox.

2What happens on a delegated turn

Delegation stays inside the harness. The controller still drives one session, one sandbox, and one active top-level run.

✗ Rejected: one sandbox per specialist

A per-specialist sandbox would multiply latency and cost, split the session's ownership/binding model, and contradict FRD 0007's rule that delegation starts no new request or top-level compute. v1 deliberately co-locates the team.

3The shared things span the whole team

Because specialists live in the same sandbox, the package, catalog, and network policy must be computed for the whole reachable delegation graph.

◆Captured content package

The controller-captured content includes the coordinator plus every referenced specialist: each .agent.md, tools, skills, MCP config, and the single captured pip-resolved .python_packages.

◆Agent catalog

The in-sandbox AgentCatalog is the immutable catalog for the reachable set. Packaging only the entry agent would make delegate_<slug> fail at runtime.

◆Egress policy

The deny-by-default allow-list is the union of destinations required by the coordinator and all reachable specialists, enforced as one group-wide policy per 0008.9.

Security intuition: v1 treats one app's reachable agent team as one trust domain. The union policy is still tighter than today's normal in-process worker network, but it is not per-specialist isolation. Any code in the sandbox can reach any allowed destination in the union; future hardening may add identity-scoped per-delegate proxy rules.

Identity stays outside the sandbox

The sandbox remains identity-less. Outbound auth is applied by the shared egress proxy through credential injection, and no specialist receives an in-sandbox credential or its own session identity.

4Delegation is a negotiated harness capability

The API surface does not grow. Instead, the harness advertises whether it can preserve FRD 0007's in-process delegation semantics.

◆Capability gate

subagent delegation is an enumerated capability under the single protocol_version. If an app declares subagents: and the harness cannot run them in-process, startup fails closed.

◆Conformance trace

0008.7 requires a golden trace that exercises a coordinator calling a specialist and integrating its answer before the capability can be advertised as supported.

One top-level run is preserved

Delegation is just an in-harness tool call. It does not create a second top-level run, session row, binding, or client-visible API. The synchronous budget is whole-run: coordinator plus any nested delegated work share the same wall clock.
