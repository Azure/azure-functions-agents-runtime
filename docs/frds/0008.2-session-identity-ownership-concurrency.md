# FRD 0008.2 — Session identity, ownership & one-active-run concurrency

> reviewed parent. During review it also **revised Decision 15** (reuse Azure
> Functions platform auth instead of mandating Entra) and detailed Decisions 6 and
> 15 with the resolutions logged below (all *Human*-decided, 2026-07-22). Status:
> **Finalized** (docs-only; *Human* sign-off 2026-07-22). Cross-cutting changes for
> other documents are flagged, not applied, in "Cross-cutting impact"; the parent
> owns their consolidated reconciliation.

## What this is and why it matters

An agent **session** is a long-lived conversation that keeps its memory, files,
and (in this design) its own compute across many back-and-forth turns. To route
each turn to the right place, the system needs a name for the session — a
`session_id` — and a trustworthy answer to "who is allowed to use this session?"

This area sets three rules: the `session_id` is an opaque lookup key and **not**
proof that you're allowed in; ownership **reuses the same authentication the
Azure Functions platform already enforces** (function keys, or App Service
Authentication / "Easy Auth" for Microsoft Entra ID) and records whatever
principal the host resolved — so an app can own a session just as a signed-in
user can; and only **one run at a time** may be active in a session. These rules
are the foundation the tamper-evidence (sibling 0008.3) and lifecycle (0008.12)
work depend on. Get identity wrong and a caller could hijack someone else's
conversation and the sandbox behind it.

## Decisions this sub-FRD owns

- **Decision 6 — One active run per session.** A session runs at most one turn at
  a time; a second concurrent submission is refused with `409 Conflict` naming the
  already-active `run_id`. **v1 keeps this a flat refusal** — there is no
  supersede/interrupt affordance. A caller that wants to start a different turn
  must first cancel the active run via the run-management route (0008.11/0008.12),
  then submit. The rule counts **top-level runs**: FRD 0007 multi-agent delegation
  (subagents co-located in the same sandbox, per 0008.13) is a *nested in-process
  call* inside the single active run, not a second concurrent run, so it never
  triggers a `409`.
- **Decision 15 (revised) — Reuse Azure Functions platform authentication for
  ownership.** Persistent sandbox sessions authenticate exactly like every other
  Functions endpoint: the App Service / Functions Host auth gate (function keys,
  or App Service Authentication / Easy Auth) runs *before* the controller. If a
  request reaches the controller, it is already authorized; the controller does
  **not** add a second identity layer. Ownership binds the session to whatever
  principal the host resolved — an Entra user subject when Easy Auth is
  configured, otherwise the app itself (its Function App identity). Function-key
  callers **can** create persistent ACA sessions in v1 (the app is the owner).

### How identity and ownership actually work (parent §4.6)

- The public `session_id` keeps today's safe-character/length rules and is
  server-generated. It is a *routing key*, never an authorization proof.
- Authentication is **not reinvented**. The Functions platform's existing auth
  gate (function keys, or App Service Authentication / Easy Auth) is the security
  boundary, and it runs before any controller code. Reaching the controller means
  the request already cleared that gate, so it is treated as authorized.
- The backend records ownership in a versioned, discriminated **`OwnerContext`**
  built from the principal the host already resolved — the controller reads it, it
  does not mint it:
  - `kind: entra_user` — when Easy Auth / Entra resolves a user: tenant ID, the
    immutable user subject claim, the Function App identity, and the agent slug.
    (Strongest granularity; fully supported, just no longer mandatory.) v1 binds to
    whatever stable user principal Easy Auth already surfaces — it does **not** add
    bespoke per-claim validation or special-case guest / B2B / cross-tenant / MSA
    callers; they work exactly as they do for any Easy-Auth-protected Functions
    endpoint. If no stable user principal is resolved, ownership falls back to
    `kind: function_app`.
  - `kind: function_app` — when the call is authorized by function key (or other
    app-level platform auth) with no end-user principal: bound to the **Function
    App identity** (a stable app identifier, e.g. the site resource ID) plus the
    agent slug. **The app owns the session** (and may own many). v1 deliberately
    binds to the *app*, not to the specific key or key-name, so **key rotation
    never orphans sessions**. Finer per-key segmentation (revoke-by-rotation) is a
    deferred enhancement, gated on the host reliably surfacing the key identity and
    on a session-orphan/rotation story.
  - `kind: trigger_binding` — reserved for non-HTTP trigger sessions (FRD 0009);
    not implemented here.
- Raw identity claims never appear in the `session_id` or in sandbox labels.
  Instead, a **versioned** SHA-256 hash of a canonical owner tuple is used in
  storage paths and labels for data minimization. The scheme is pinned so it can
  evolve safely:
  - **Deterministic serialization.** The `OwnerContext` discriminator is hashed
    first, then a fixed field order, with unambiguous length-prefixed/escaped
    UTF-8 fields (so two distinct tuples can never serialize identically) and Entra
    GUIDs lower-cased. Including the discriminator guarantees an app-scoped and a
    user-scoped owner can never collide. Collision resistance is the security
    property that matters; authorization never depends on the hash being secret.
  - **Versioning.** An `owner_hash_version` is recorded on the
    controller-authoritative state row (0008.3) — cross-checked against the live
    sandbox manifest — and carried as a prefix on the label/path (e.g. `o1-<hex>`).
    The controller retains **all historical canonicalizers**, keyed by version.
  - **No eager migration.** Because the caller re-presents their identity on every
    turn, the controller re-derives the tuple live and recomputes the hash *under
    the version stored for that session* — so old and new sessions coexist and the
    authorization check never needs a bulk rewrite. New sessions adopt the current
    version. Retiring an old canonicalizer is only ever a physical re-key of the
    affected state rows (0008.3), and is out of scope for v1.
- The ownership check on each turn is a straight comparison: does the incoming
  request's resolved `OwnerContext` match the one stored for the session? Because
  the owner can be app-scoped, **the app is the trust boundary**: the runtime does
  not distinguish two end users behind the *same* function key — separating them,
  if needed, is the app's responsibility, exactly as it is for Functions today.
  The check is **stateless and per-request**: any controller instance resolves
  ownership from the incoming principal plus the stored binding, holding no
  in-memory session state. So the `session_id` is a stable, instance-independent
  lookup key — a recycled or replacement controller instance reattaches to the
  same session and its current-generation sandbox via the controller-authoritative
  binding row. 0008.5's
  instance-death reattach depends on this. The binding's storage and its
  forward-only `generation` counter (used for state-preserving rebind to a
  different sandbox instance) are owned by 0008.3. In v1, true
  sandbox/snapshot loss is **not** handled as a generation bump; it is a
  tombstone outcome (same `session_id` returns `410`, client creates a new
  session). See the one-active-run note below for the run-terminal behavior.
- Ownership is a **controller-side** concern. The controller resolves and
  authorizes the `OwnerContext` *before* invoking the execution backend, so raw
  owner identity never crosses the `AgentExecutionBackend` seam (0008.1) —
  `StartRunRequest` / `RunContext` / `RunStatus` stay typed run data only. The only
  owner-derived value that leaves the controller is the *hashed* owner label
  applied to the sandbox/storage at provisioning, never the raw claims. This keeps
  identity out of the sandbox, consistent with data-minimization (and 0008.9's
  keep-credentials-outside-sandbox posture).
- **One active run** is enforced with two independent locks: the controller takes
  an ETag-protected storage lease for the short create/resume/submit window, and
  the sandbox itself takes an OS file lock before starting the harness. The OS
  lock and the sandbox's run journal are authoritative while a detached run is
  live; the storage lease is released after submission and is *never* used to
  infer that a process has stopped. The **one-active-run slot** is therefore bound
  to a non-terminal run record whose liveness authority is that sandbox
  OS-lock/journal — not the released storage lease and not a free-standing
  controller flag. The controller stores only the session-row `active_run_id`
  admission pointer, which is a linearizable slot guard (single-entity ETag CAS,
  `null -> run_id`, in the run rows' partition) and is cleared only after
  terminal adoption. 0008.12 writes that terminal transition by three paths that
  share one idempotent, ETag-conditional write: (1) a **fast path** — when a caller
    resubmits, the controller reconciles a non-terminal run *inline, before* evaluating
    one-active-run: if the sandbox is **intact** (crash-with-disk), the stale slot is
    cleared and the same session proceeds; if the sandbox is **lost**, the run is
    marked `abandoned`, the slot is freed, and the session is tombstoned — the caller
    receives `410 Gone` and must create a new session; and (2) an **opportunistic cleanup path** —
  the next create / quota-failure sweep reconciles abandoned runs for sessions
  nobody is actively touching; and (3) a **minimal periodic reconciler/reaper
  timer** (plain Functions timer, v1 backstop, configurable around ~1h) for crash
  / idle cleanup. So the slot is freed **on next submit, on opportunistic cleanup,
  or by the periodic timer backstop** — a phantom active run can never wedge the
  session at `409`. The periodic timer is mandatory in v1; a ~1/min cadence is a
  v2 tightening tied to the mirror SLO. The specific terminal label does not
  affect slot-release: any terminal state frees the slot.

  Crash and loss outcomes are intentionally distinct in v1: if the harness crashes
  but sandbox disk/state is intact, the session continues and resumes from the
  last committed checkpoint on that **same** sandbox (same generation). If the
  sandbox/snapshot is truly lost (no recoverable state), the session is
  **tombstoned** — the same `session_id` returns `410 Gone` for new routing/
  submission and the client creates a new session. There is no same-session
  regeneration after true loss in v1. Historical run-status reads remain
  available from the control records.

  For those loss cases, the in-flight run still resolves terminally in the
  control record (`abandoned` in v1). The external checkpoint mirror (0008.8
  Decision 18) is deferred to **v2**; when it ships, a completed-then-reaped run
  can be labeled by its mirror-verified `succeeded`/`failed`, but this does not
  change slot release or v1 tombstoning behavior.

Why reuse platform auth rather than mandate Entra: a *function key* authenticates
an *app*, not a *person* — but for this design that is acceptable, because an app
is allowed to own a session on behalf of its own users. Forcing Entra everywhere
would fork the auth story away from the rest of Azure Functions and lock out
existing function-key deployments for no boundary gain the platform doesn't
already provide. Easy Auth / Entra remains available and gives the finest-grained
(per-user) ownership for callers who want it; it is simply not a precondition for
using the ACA backend. The controller still fails closed if it cannot resolve
*any* owner principal from the host — it just no longer insists that principal be
Entra.

## Alternatives considered & why the choice won

- **Per-session concurrency (Decision 6).** Considered: unlimited concurrent
  runs, queue the turns, one active run with a flat `409`, or one active run with a
  supersede/interrupt affordance. Chosen: one active run with a **flat `409`** on a
  second submission. This keeps the v1 state machine tiny and sidesteps
  shared-sandbox races; queuing, fan-out, and supersede/interrupt are explicitly
  deferred (queuing/fan-out tie to the "no Durable Functions in v1" rationale in
  sibling 0008.12; a supersede affordance would need cancellation semantics owned
  there too). The v1 escape hatch is an explicit cancel-then-submit. Decided by
  *Human + Agent* (flat `409` reaffirmed by *Human*, 2026-07-22).
- **Persistent-session authentication (Decision 15, revised).** Considered:
  require Entra ownership for every ACA session; invent a bespoke signed
  session-capability token; or reuse the Functions platform auth gate as-is.
  Chosen: **reuse the platform gate** (function keys or Easy Auth/Entra) and bind
  ownership to whatever principal the host resolved — app-scoped for function-key
  calls, user-scoped for Entra. Mandating Entra would diverge from how every other
  Functions trigger is secured and exclude existing function-key deployments for
  no boundary the platform doesn't already enforce; a custom capability token is
  unproven and reinvents the wheel. Reusing the existing gate is the pragmatic,
  already-supported answer, and Easy Auth/Entra stays available for callers who
  want per-user ownership. Decided by *Human* (revises the earlier
  *Agent reviewer* choice to require Entra).

## Honest critique

**Strengths.** Separating "identity of the caller" from "name of the session" is
exactly right and prevents the most common session-hijack class. Reusing the
Functions platform auth gate keeps one consistent security story across every
trigger instead of forking a special rule for ACA sessions. The dual lock
(storage lease *and* OS file lock) is a thoughtful acknowledgement that a
distributed lease can't prove a live process stopped. Hashing the owner tuple is
good data-minimization hygiene.

**Risks / assumptions.**
- **App-scoped ownership shifts end-user isolation to the app.** When a session is
  owned by a function key, the runtime cannot tell two end users behind that key
  apart, so any caller holding the key can reach any session the app owns.
  Isolating end users is then the app's responsibility. This is deliberate and
  matches Functions today, but callers who assumed per-user isolation must opt into
  Easy Auth / Entra to get it. (0008.3 records the same consequence at the state
  layer: a Function-App-owned session is addressable by any valid Function-Key
  holder, and the state store does not provide co-holder isolation.)
- **Only as strong as the platform gate.** Ownership now inherits whatever the
  Functions auth configuration provides. A weak or misconfigured gate (e.g. a
  leaked function key) weakens session ownership with it; the runtime adds no
  compensating check.
- **One-active-run may frustrate legitimate patterns.** A user who opens two tabs,
  or a UI that fires a background summarization while a chat turn runs, will hit
  `409`. The design assumes callers serialize their own turns.
- **The immutable-subject assumption (Entra path only).** v1 deliberately does not
  define or validate its own subject claim — it binds to whatever stable user
  principal Easy Auth surfaces and falls back to `function_app` otherwise. This
  keeps us aligned with the platform, but it means per-user isolation is only ever
  as precise as what Easy Auth resolves for a given caller type (home user, guest,
  B2B, MSA); a deployment needing finer guarantees must configure Easy Auth
  accordingly rather than expecting 0008.2 to normalize it.
- **Hash canonicalization is load-bearing (now versioned).** The owner-hash is a
  stable key baked into long-lived storage paths, so a change to the tuple or
  hashing would otherwise strand data. This is addressed by the versioned scheme
  (per-session `owner_hash_version`, retained historical canonicalizers, recompute
  under the stored version) — but that discipline must actually be honored, and the
  shared spec lives with 0008.3.

**Reconsider triggers.** Revisit if: app-scoped ownership proves too coarse and a
first-class per-user proof (e.g. a signed session capability) becomes necessary
for function-key or non-HTTP callers; the platform auth gate proves an inadequate
ownership boundary in practice (e.g. key-leak incidents) and the runtime needs a
compensating check; product feedback shows one-active-run is too strict (then
coordinate with 0008.12 on queuing); or the owner-tuple/hash canonicalization
needs to evolve after data already exists.

## Resolved in this iteration (2026-07-22)

- **One-active-run stays a flat `409` (Decision 6).** No supersede/interrupt
  affordance in v1; a caller cancels the active run (via 0008.11/0008.12) then
  resubmits. Decided by *Human*. *(Reflected in the Decision 6 restatement and
  alternatives above.)*
- **Per-owner/app session ceiling is out of scope here.** It is a
  lifecycle/quota concern, **not** an identity concern — deferred to **0008.12**
  (which owns the quota discussion; parent §4.8). No ceiling is defined or enforced
  by 0008.2. Decided by *Human*.
- **`function_app` binds to the Function App identity (Decision 15 detail).**
  v1 owns sessions at the app level, not per-key, so key rotation never orphans
  sessions; named-key segmentation is deferred (see "How identity … works" above).
  Decided by *Human*.
- **Owner-hash uses a versioned canonicalization scheme.** Discriminator-first
  deterministic serialization; `owner_hash_version` on the controller-authoritative
  row; historical canonicalizers retained; no eager migration. Shared spec with
  0008.3. Decided by *Human*.
- **Entra subject definition — no bespoke spec in v1.** On the `entra_user` path we
  bind to whatever stable user principal Easy Auth surfaces; no special handling
  for guest / B2B / cross-tenant / MSA, and `function_app` is the fallback when no
  stable user resolves. "Reuse the platform, don't over-engineer." Decided by
  *Human*.
- **`trigger_binding` stays reserved; FRD 0009 adds it additively.** No placeholder
  is built now. The versioned, discriminator-first owner-hash makes adding a new
  `OwnerContext` kind additive — new kinds hash in their own space with no version
  bump and no re-key of existing sessions — so 0009 can introduce `trigger_binding`
  when needed. Decided by *Human*.

## Cross-cutting impact (Decision 15 revision — flagged, not yet applied elsewhere)

The revision of Decision 15 (reuse platform auth; app-scoped ownership allowed)
reaches beyond this sub-FRD. These are flagged here for the owning documents to
reconcile; **this sub-FRD does not edit them**:

- **Parent 0008 — Goals/Non-goals + Decisions log + §6 prose.** The parent
  currently lists "Require Entra-authenticated ownership for persistent ACA
  sessions in v1" as a **Goal** and "Allowing function-key callers to create
  persistent ACA sessions in v1" as a **Non-goal**. This revision *inverts both*.
  The master Decisions log row 15 (owner 0008.2) needs an append-only revision
  entry (revised by *Human*, 2026-07-22). Also stale (flagged by 0008.10): the
  parent §6 line stating "ACA persistent sessions require Entra auth; function-key
  surfaces stay on the in-process backend" no longer holds under the
  function-keys-or-Easy-Auth + app-scoped ownership model.
- **0008.3 (state store & tamper-evident trust).** Owns the
  controller-authoritative state row — now **authoritative-by-construction**
  (scoped RBAC + disabled Shared Key make the controller MI the only writer), with
  routing validated by a monotonic `generation` + live-manifest cross-check; its
  Decisions 32-R/39-R dropped the per-binding Key Vault signature and the immutable
  WORM binding-log. It carries `owner_hash_version` on that row and hosts the
  canonical serialization spec. The tuple must include the `OwnerContext`
  discriminator so `function_app` and `entra_user` owners never collide, and its
  versioning must match the no-eager-migration model above (retain historical
  canonicalizers; physical re-key of affected rows only to retire a version).
- **0008.1 (execution backend & "Functions as controller").** Its
  "authenticated controller" narrative should reflect that authentication is the
  standard Functions gate (keys or Easy Auth), not an ACA-specific Entra
  requirement, and that ownership may be app-scoped.
- **0008.11 (HTTP API).** Any auth-mode wording for the sandbox-backed routes
  should align with "same auth as every other Functions endpoint" rather than an
  Entra precondition.
- **0008.12 (lifecycle, failure & reconciler).** Owns the **per-owner/app session
  quota** discussion (deferred here, 2026-07-22). With `function_app` ownership, a
  single key could otherwise open unbounded sessions, so a per-app ceiling is worth
  considering there (parent §4.8). 0008.2 defines no ceiling.
