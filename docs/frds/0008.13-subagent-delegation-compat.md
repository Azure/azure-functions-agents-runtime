# FRD 0008.13 — Subagent (multi-agent delegation) compatibility

> Sub-FRD of [FRD 0008](0008-aca-sandbox-session-runtime.md). It re-expresses,
> in plain language, one self-contained decision area from the reviewed parent
> (§4.16). It re-expresses parent decisions in plain language and introduces no
> new technical decision that alters Decisions 42–46; the v1 scoping calls it
> records (catalog size → platform defaults; handoff → v2) are consistent with the
> reviewed parent. **Finalized 2026-07-23 (Human).**
>
> **Why this sub-FRD exists.** After the parent design was reviewed, `main`
> merged a separate feature — **multi-agent delegation**, shipped as
> [FRD 0007](0007-multi-agent-delegation.md). This sub-FRD captures how that
> feature coexists with the ACA Sandbox session backend, as a decision area the
> team can iterate on independently. A targeted independent re-review of this
> compatibility (parent **Decision 47**) returned **READY** with no blockers; its
> three precision notes — adding "subagent delegation" to the §4.5 capability
> list, an explicit shared-egress-proxy trust-domain caveat, and pinning egress as
> one group-wide policy — are reflected below.

## What this is and why it matters

A **subagent** (a.k.a. multi-agent delegation) lets one agent — the
**coordinator** — hand part of a task to a **specialist** agent and use its
answer. In the merged FRD 0007 model, a coordinator's `.agent.md` declares a
`subagents:` list, and each specialist becomes an in-process tool named
`delegate_<slug>` whose handler simply runs that specialist through the
Microsoft Agent Framework (**MAF** — the SDK that runs the agent loop) via
`Agent.run()`, *inside the coordinator's own run*. There is no network hop and no
second request; it is one program calling a helper function.

This matters here because FRD 0008 proposes running the whole agent engine (the
**harness**) inside a single isolated container — an **ACA Sandbox** (an Azure
Container Apps sandbox) — one per session. The obvious question is: when a
coordinator delegates, does each specialist get its *own* sandbox? The answer is
**no** — everything runs together in the one session sandbox. This sub-FRD
records that and the handful of consequences (what must be packaged, what egress
must be allowed, and how delegation is treated as a harness capability), plus a
forward reservation for a future "handoff" feature.

## Decisions this sub-FRD owns

- **Decision 42 — Where delegated specialists execute.** *All* delegated
  specialists run inside the session's **single** sandbox. Delegation opens **no**
  per-specialist sandbox. (Alternatives: a separate sandbox per specialist vs. the
  shared session sandbox.)
- **Decision 43 — What the content package / catalog contains.** The v1 content —
  which per **0008.6 Decision 68** the **controller captures from its own local
  script root** (`/home/site/wwwroot`) at session start and **delivers over the file
  transport (0008.5)** into the identity-less sandbox (integrity via a **SHA-256
  digest over the captured bytes**, cross-checked per 0008.3; **not** an IaC-pinned
  Run-From-Package zip the sandbox fetches) — and the in-sandbox **`AgentCatalog`**
  include the coordinator
  **and every referenced specialist** (each agent's `.agent.md`, tools, skills,
  MCP config) — not just the entry agent. (Alternatives: entry agent only vs. all
  reachable agents.)
- **Decision 44 — Egress scope with delegation.** The deny-by-default egress
  allow-list is the **union** of destinations across the coordinator and all
  reachable specialists (each model endpoint and MCP host). Deny-by-default and
  full inspection still apply. (Alternatives: per-agent policy vs. union.)
  **Confirmed by 0008.9 (Finalized, Human, 2026-07-23):** v1 accepts the single
  group-wide union with **no per-specialist egress isolation**; identity-scoped
  per-`delegate_<slug>` rules are named as **future hardening**, not a v1 feature.
- **Decision 45 — Delegation as a harness capability.** "Subagent delegation" is a
  **negotiated harness capability**, not an assumption. MAF supports it (it is
  plain `Agent.run()`); a harness that cannot run a specialist in-process must
  **fail closed at startup** if a coordinator declares `subagents:` — never
  silently drop delegation. A **delegation golden trace** is added to the
  conformance suite. (Alternatives: assume every harness supports it vs. negotiate
  with fail-closed.) **Reinforced by 0008.7 (2026-07-22):** "subagent delegation"
  is now an enumerated member of the typed capability set carried under the single
  `protocol_version` (no separate capability version in v1); a **total
  feature→capability map** means an unenumerated feature fails closed as
  "unrecognized," never "supported by omission"; and a capability may be advertised
  *supported* only once a conformance trace exercises it — which delegation's golden
  trace satisfies.
- **Decision 46 — Future handoff session state (reserved).** Reserve room in the
  session **checkpoint/manifest** schema for a future handoff feature's "active
  participant + shared context"; explicitly **out of v1 scope**. (Alternatives:
  ignore now vs. reserve schema room. Cross-referenced from durability sub-FRD
  **0008.8**.) **Sharpened after 0008.8 finalized (2026-07-22):** because that
  sub-FRD's v1 re-scope defers *all* external durability (the Blob mirror) to v2,
  handoff durable state is now **"v2+ by construction"** — there is no v1 durable
  substrate to persist active-participant/shared-context into. The schema
  reservation still stands as its natural home; any concrete handoff-durability
  design co-reviews against the v2 mirror (see the handoff open question below).

### How delegation maps onto one-sandbox-per-session (parent §4.16)

- **Co-location, not fan-out (42).** Because the whole harness runs in the session
  sandbox, the coordinator and its specialists run in the *same* sandbox, in one
  process. One session = one sandbox = one coordinator + its in-process
  specialists. This matches FRD 0007's own rule that a delegated call starts no new
  request-scoped compute.
- **Catalog spans all agents (43).** The sandbox rebuilds the `AgentCatalog`
  locally from the *digest-verified content the controller captured and delivered*
  (consistent with "the sandbox reruns discovery/translation locally" — see
  0008.1/0008.6). The controller never ships live MAF agents or catalog objects over
  the wire; it must therefore *capture and deliver* every reachable agent's content,
  not just the entry point.
- **Concurrency unchanged (context, not a new decision).** Delegation is
  synchronous nested calls within one top-level run, so **one active run per
  session** (owned by 0008.2) is preserved — delegation never creates a second
  top-level run. The **180-second synchronous HTTP budget** (owned by 0008.11,
  Finalized) is a *whole-run* wall — a **30 s setup sub-budget** (binding lookup,
  sandbox create/resume, content transfer + digest-verify) plus a **≥150 s execution
  floor** —
  and it covers the coordinator *plus* every nested delegated call. On breach the
  controller returns a **typed `504`** carrying a `reason` and an
  `x-ms-retry-with: respond-async` hint (sync never silently degrades to async), so
  deep or slow delegation chains should use `Prefer: respond-async`.
- **Egress is the union (44).** All specialists share the sandbox, so the
  deny-by-default allow-list (owned by 0008.9, Finalized) must cover every reachable
  agent's destinations. Deployment computes this union **once from the app-wide
  catalog as a single group-wide policy** (a superset of any per-coordinator union),
  *not* a per-session-recomputed set — consistent with the hard 1:1
  per-Sandbox-Group provisioning in 0008.4 (Finalized). 0008.9 owns the
  compile-and-enforce step (an ordered ACA rule list) and has **accepted no
  per-specialist isolation for v1** (Human, 2026-07-23): any code in the sandbox can
  reach any destination in the union. Per **Decision 66 / 0008.9 (Tier-A,
  2026-07-24)** the v1 session sandbox is **identity-less** — no managed identity
  and no AAD token inside, ever — so the co-located specialists inherit that
  posture: none holds an in-sandbox credential. Each specialist's outbound auth is
  applied by the **shared egress proxy via credential injection** (proxy-side MI
  `Transform` preferred, else a Key Vault reference / static secret) on the union
  allow-list, and the **controller delivers the content package** — so no token ever
  lives in the sandbox. User-delegated (OBO) egress, the earlier assigned-app-MI
  mechanism (superseded #56/#57), and HOBOv2 are all deferred to a future version.
  Deny-by-default and full inspection still apply.
- **Identity stays per-session (context).** Delegation stays inside one session,
  one owner, one session→sandbox binding — which per 0008.3's finalized 32-R/39-R
  is **the authoritative session/run Table row itself**, validated by scoped RBAC +
  a monotonic generation + a live-manifest cross-check (**no** Key Vault signature,
  **no** WORM log); session identity, ownership, and the one-active-run rule are
  owned by 0008.2. Specialists get no separate session, ownership, or binding row.
  FRD 0007's new **globally-unique file-stem slug** guarantee strengthens the
  `agent_slug` recorded on that row/manifest: the coordinator's slug unambiguously
  identifies the entry agent.
- **Delegation is negotiated (45).** "Subagent delegation" is an enumerated member
  of the typed capability set the sandbox manifest advertises under the single
  `protocol_version` (owned by 0008.7). Registration fails closed before session
  creation if a coordinator declares `subagents:` on a harness that doesn't support
  in-process delegation, and 0008.7's total feature→capability map ensures no
  delegation feature can pass by omission. The conformance suite gains a golden
  trace of a coordinator calling one specialist and integrating the result — the
  prerequisite for advertising the capability as supported.
- **Telemetry nests in-sandbox (context).** FRD 0007's `af.delegate.*` spans and
  delegate call/error metrics are emitted by the harness *inside* the sandbox and
  must be captured by in-sandbox telemetry and correlated to the controller's run
  span, using the separate sandbox/harness fault domains — never the Dynamic
  Sessions `FaultDomain.SANDBOX`.
- **Code execution stays native (context).** FRD 0007 gives a delegated specialist
  no per-request Dynamic Sessions `execute_python`; in this backend code execution
  is native to the session sandbox, so a specialist just runs code in the shared
  sandbox. Nested Dynamic Sessions remain rejected (see 0008.7).

### v1 delegation model (from FRD 0007, for context)

v1 delegation is **single-level**, passes only the `task` string (no shared
session/history), builds each specialist **fresh per call**, relies on
globally-unique file-stem slugs, and reads an **immutable** `AgentCatalog` built
once at composition. This sub-FRD hosts that model without regressions.

## Alternatives considered & why the choice won

- **Execution locus (Decision 42).** Considered: a separate sandbox per specialist
  vs. the shared session sandbox. Chosen: shared session sandbox — the harness (and
  therefore every specialist) already runs there, a per-specialist sandbox would
  multiply cost/latency and break the "delegation starts no new request-scoped
  compute" rule, and it would fracture the one-owner/one-binding session model.
  *Agent.*
- **Package/catalog scope (Decision 43).** Considered: package the entry agent only
  vs. all reachable agents. Chosen: all reachable agents — the sandbox rebuilds the
  catalog locally from the digest-verified captured content and must be able to resolve every
  `delegate_<slug>` target, so the entry agent alone would fail at delegation time.
  *Agent.*
- **Egress scope (Decision 44).** Considered: per-agent egress policy vs. a union
  across coordinator + reachable specialists. Chosen: the union — since all
  specialists execute in one shared sandbox, per-agent network isolation isn't
  achievable there; deny-by-default is preserved by allowing exactly the union and
  nothing more. *Agent.*
- **Delegation as capability (Decision 45).** Considered: assume every harness
  supports delegation vs. treat it as a negotiated capability with fail-closed.
  Chosen: negotiated capability + fail-closed + a conformance golden trace — a
  future CLI/process-shim harness may not be able to run a specialist in-process,
  and silently dropping delegation would change agent behavior. *Agent.*
- **Future handoff state (Decision 46).** Considered: ignore it now vs. reserve
  checkpoint-schema room. Chosen: reserve room but keep it out of v1 — because an
  ACA session persists across turns, a future handoff's "active participant +
  shared context" becomes durable session state that must survive suspend/resume,
  so the checkpoint schema should not paint itself into a corner. *Agent.* **Update
  (0008.8 finalized, 2026-07-22):** since v1 now ships no external durable store,
  handoff durable state is v2+ by construction — the reservation is still the right
  home, but nothing can persist there until the v2 mirror exists. *Human (0008.8).*

## Honest critique

**Strengths.** Co-location is the only choice consistent with "the whole harness
runs in the sandbox," and it keeps the clean one-session/one-owner/one-binding
model intact. Treating delegation as a *negotiated capability* (rather than an
assumption) is consistent with the harness-compatibility discipline in 0008.7 and
prevents a future non-MAF harness from silently degrading. Reserving — but not
building — handoff state (46) is appropriately humble.

**Risks / assumptions.**
- **Egress union widens the blast radius.** Because specialists share one sandbox,
  the union allow-list means *every* reachable agent's destinations are reachable
  by *all* code in that sandbox. A compromised or misbehaving specialist can reach
  a peer's endpoints; per-agent network isolation is lost by construction. This is
  the natural consequence of co-location and matches the **"one app = one trust
  domain"** framing (FRD 0007 delegation, Decision #10). The re-review (Decision
  47) noted it is nonetheless *strictly tighter* than the current in-process model,
  which shares the worker's network with **no** per-agent egress isolation at all —
  so it is a weakening only relative to hypothetical per-specialist isolation, not
  relative to today. **0008.9 explicitly accepted this for v1** (Finalized, Human,
  2026-07-23) and named identity-scoped per-`delegate_<slug>` rules as future
  hardening — so the risk is acknowledged and owned, not unresolved.
- **One shared budget for a whole delegation tree.** The 180 s sync cap now spans
  the coordinator plus every nested call; a modest fan-out of slow specialists can
  blow the budget and force async, which may surprise authors who think of each
  delegate as "just a tool call." 0008.11 (Finalized) softens the sharp edge: a
  breach returns a **typed `504` with an `x-ms-retry-with: respond-async` hint** (and
  first-party SDKs expose an opt-in async-retry helper) rather than a silent stall.
  What is **not** in v1 is *per-delegate* budget attribution or a pre-flight "this
  plan should be async" estimate — the budget is accounted whole-run only.
- **Package/catalog growth.** Capturing every reachable agent (plus its tools,
  skills, MCP, offline deps) can substantially enlarge the controller-captured
  content zip (0008.6) and sandbox cold-start (interacts with 0008.6's
  transfer-cost concern).
- **Capability check depends on static reachability.** Fail-closed at startup
  assumes the set of "reachable specialists" is known statically from `subagents:`.
  If reachability were ever dynamic, the union egress and the capability gate would
  both need rethinking.
- **v1 limitations may frustrate.** Single-level, task-string-only, no shared
  history, fresh-per-call specialists — all inherited from FRD 0007 — may feel
  limiting; when they evolve (e.g. handoff), the durable-state reservation (46)
  will need real design.

**Reconsider triggers.** Revisit if: the shared-sandbox egress union proves too
permissive for a real security requirement (may force per-specialist isolation or
an in-sandbox egress sub-policy); delegation trees routinely exceed the sync
budget (coordinate with 0008.11); packaging all reachable agents materially hurts
cold-start, or 0008.5's load gate surfaces a per-session packaging/cold-start
limit that would bite large delegation graphs (coordinate with 0008.6 for the
one-capture/one-boot transfer cost and 0008.5 for the concurrency-load exposure —
0008.5 holds the reciprocal trigger to notify us); delegation becomes multi-level
or dynamic; or handoff moves from reserved to funded (then design the durable
state with 0008.8).

## Resolved & deferred questions

> **Finalization status (2026-07-23).** At finalization there are **no v1-blocking
> open questions**. Items settled by *finalized* siblings or by an owner call are
> under **Resolved / decided**; the two remaining items are **deferred / not
> v1-blocking** — the information is captured here for the implementer and for a
> future FRD, but neither changes a v1 decision.

**Resolved / decided**

- **✅ Egress union vs. isolation** — *Resolved (0008.9 Finalized, Human,
  2026-07-23).* v1 **accepts the single group-wide union with no per-specialist
  egress isolation**; identity-scoped per-`delegate_<slug>` proxy rules are named as
  **future hardening** for high-security deployments, not a v1 feature. Reflected in
  Decision 44 and the egress mapping bullet.
- **◑ Budget accounting for delegation trees** — *Partially resolved (0008.11
  Finalized).* The "go-async" surface exists: a 180 s whole-run breach returns a
  **typed `504` + `x-ms-retry-with: respond-async`** hint (plus an SDK opt-in
  async-retry helper); sync never auto-degrades. **Deferred (not v1):** *per-delegate*
  budget attribution/visibility and a *pre-flight* estimate — the budget is
  whole-run. Track as an observability follow-up with 0008.11.
- **✅ Catalog / package size limits — use platform defaults** *(Human,
  2026-07-23).* v1 sets **no delegation-specific numeric bound** on how many
  reachable agents a session may package. The operative envelope is the **existing
  platform defaults** owned elsewhere: the **controller-captured content** transfer
  size (0008.6 Decision 68), sandbox create/resume cold-start (0008.6), and the
  **100-concurrent** target whose load gate is still pending (0008.5). If those
  defaults prove insufficient for real delegation graphs, revisit then — this is
  already a named *reconsider trigger* below. Rationale: a bespoke cap would be an
  arbitrary guess ahead of the 0008.5 load data; the natural limits already bound
  the captured content and cold-start. **Grounding (0008.6):** 0008.13 is recorded as a
  downstream consumer of 0008.6's Path-1 latency-measurement item, and because the
  captured content spans *all reachable agents*, that measurement covers the **multi-agent
  union envelope** (coordinator + every reachable specialist) — so the "use
  defaults" call gets validated against real multi-agent numbers once they exist.
  No dependency blocks v1 either way.
- **⏸ Handoff durable-state design (Decision 46) — punted to v2** *(Human,
  2026-07-23).* No further v1 design here. Handoff's "active participant +
  shared/broadcast context" is **v2+ by construction**: 0008.8 finalized (2026-07-22)
  with no v1 external durable store, so there is no v1 substrate to persist it into.
  The checkpoint/manifest **schema reservation stands** as its future home; concrete
  field/versioning/suspend-resume design happens in v2, co-reviewed against the v2
  Blob mirror with 0008.8.

**Deferred / not v1-blocking (captured for reference)**

- **Delegation conformance-trace scope — implementer guidance, not a v1 decision.**
  v1's commitment is fixed by **Decision 45**: *a* delegation golden trace exists in
  the conformance suite (and per 0008.7 a capability may be advertised *supported*
  only if a trace exercises it, with **semantic / core-behavior** comparison that is
  robust to event reordering — not a brittle byte match). Pinning the *exact*
  assertion list is an **implementation detail**, not a blocking design question, so
  it is captured here rather than left open. Candidate assertion set for the
  implementer: (1) the coordinator's tool set contains `delegate_<slug>` for each
  declared specialist; (2) on a delegating turn a `delegate_<slug>` invocation is
  observed; (3) the `af.delegate.*` span is emitted with expected attributes (target
  slug, `delegated` role) and nested under the coordinator run span; (4) the
  specialist's final answer is integrated into the coordinator's output; (5) a
  **failing** specialist surfaces as a *recoverable tool error* that returns control
  to the coordinator (not a whole-run crash); (6) **no** second top-level run /
  session / binding is created (co-location invariant). Finalize the concrete set
  with 0008.7 at implementation time.
- **Multi-level / dynamic delegation — out of v1 by design; captured for a future
  FRD.** v1 is deliberately **single-level and static**: a specialist built for the
  `delegated` role gets *no* `delegate_*` tools (recursion removed structurally), and
  the reachable set is fully known at composition from `subagents:`. Two distinct
  future extensions would each break current invariants and need their own design —
  neither is in v1 scope:
  - **Multi-level (nesting):** wiring a specialist's own `subagents` so it can
    sub-delegate. Needs an explicit **depth / delegation-budget** bound (MAF has no
    cross-level guard; its ~40-iteration per-run cap does not compose), and the
    **whole-run 180 s budget** (0008.11) would span a deeper tree — sharpening the
    deferred per-delegate-accounting item above. Because v1's block is a single
    construction decision, bounded nesting stays a *localized* future builder change
    (wire `subagents` below a limit, pass depth+1); `AgentCatalog` and the run path
    need no change now to keep that option open.
  - **Dynamic (runtime-resolved) specialists:** choosing delegate targets at run
    time rather than from a static `subagents:` list. This breaks **two v1
    load-bearing assumptions**: the **egress union** (0008.9) is precomputed once
    from the static app-wide catalog, and the **fail-closed capability gate**
    (0008.7 / Decision 45) validates declared `subagents:` at startup — a target
    unknown until run time can be neither pre-authorized for egress nor
    pre-validated, so both would need a run-time authorization/negotiation model.
  - *Caveat (already true in v1):* the single-level guarantee covers only native
    `subagents` expansion; an arbitrary MCP or user tool could still call another
    endpoint over HTTP, subject to the same egress union.
