# FRD 0008.5 — Controller↔sandbox transport & sandbox runtime protocol

> Sub-FRD of [FRD 0008](0008-aca-sandbox-session-runtime.md). It re-expresses,
> in plain language, one self-contained decision area from the reviewed parent,
> and records the deep-dive resolutions that *refine* (never overturn) the
> parent's owned decisions (7, 23, 26, 29). Status: **Finalized** (human sign-off
> 2026-07-23 — see [Status & finalization](#status--finalization)); the parent
> FRD 0008 remains In review.

## What this is and why it matters

Once an agent runs inside an **ACA Sandbox** (an isolated Azure Container Apps
container), the **controller** (the Azure Functions app) needs a way to *talk to
it*: start a turn, watch progress, fetch the result, and cancel. There are two
obvious channels — open a network port on the sandbox and call it, or use the
authenticated **ADC data plane** (ACA's built-in "read/write files in the sandbox"
and "run a command in the sandbox" APIs). This area picks the second and defines
the file-based protocol that rides on top of it.

The choice matters because it trades away low-latency streaming in exchange for
*never exposing an anonymous control endpoint on the sandbox*. Instead of a live
socket, the controller writes a request file, the sandbox runs the turn and writes
status/event/result files, and the controller polls those files. This "journal
over the data plane" is the v1 transport, and it was gated on a **live spike**
proving it actually works.

## Decisions this sub-FRD owns

- **Decision 7 — Controller transport.** Use the **ADC file+exec data plane** as a
  journal in v1; keep a transport abstraction so it can be swapped. Anonymous
  sandbox HTTP ports and mandatory private-network tunnels are the rejected
  alternatives.
- **Decision 23 — Transport confidence (qualifies #7).** Official ACA samples
  establish detached exec and the SDK's 300-second exec-read limit, but a *live
  spike* is required before finalizing file/exec. Anonymous ingress is forbidden.
- **Decision 26 — Live functional gate.** The spike (SDK `0.1.0b3`) passed create,
  4 MiB file round-trip, detached launch, ~1.14s p95 events, idempotency, ~1.3s
  cancel, and cleanup — so file/exec is retained for v1.
- **Decision 29 — Concurrency target.** Design and validate for **100 concurrent
  active runs** per Function App / Sandbox Group.

### How the transport works (parent §4.4)

The sandbox exposes a fixed on-disk layout the controller reads and writes:

```text
/var/lib/azure-functions-agents/
  protocol.json
  session/ manifest.json  checkpoints/  content/ (app.zip + app.sha256)
  inbox/{run_id}.json
  runs/{run_id}/ status.json  events.jsonl  result.json  process.json
```

The flow: (1) write a request envelope to `inbox/{run_id}.json`; (2) start *every*
run through the same **detached** entry point (using `setsid`/`nohup`) so sync and
async share execution semantics and don't hold the SDK's fixed 300-second exec-read
timeout; (3) return from submission only after the sandbox atomically journals
`accepted`; (4) read status/result and append-only JSONL events via authenticated
file operations; (5) cancel by invoking the entry point's cancel command, which
signals the recorded process and journals the terminal state.

**Idempotency:** the controller generates `run_id` and puts it in the envelope; the
sandbox must atomically create the run directory and, on a duplicate `run_id`,
return the *existing* status instead of starting a second process. That is the
idempotency boundary for ambiguous data-plane responses.

**Per-run isolation:** all run outputs are namespaced under `runs/{run_id}/` (so
`result.json` is per-run, never a single shared file overwritten each turn). This matters
because a terminal frees the one-active-run slot (0008.2 Decision 6), so a **new run can start
while an earlier run's result is still unretrieved** — the two must coexist. Per-run
directories give that for free: `get_result(run_id)` reads `runs/{run_id}/result.json`, and
0008.12's per-run result-retention/eviction (`result-evicted`) applies independently per run.

**A spike-discovered gotcha:** `sandbox.get().state` can *lag* the file/exec plane
— a state read reported `Running` immediately before a file op returned
`GlobalSandboxNotRunning`. So the controller treats the *operation result* as
authoritative: call resume, wait for readiness, and verify the protocol/session
manifest before submitting work (this feeds the resume-readiness handshake in
sibling 0008.8). That manifest check includes the sandbox's **`protocol_version`**
(`protocol.json`): the controller refuses to submit unless the sandbox's `protocol_version`
matches the **captured runtime epoch of *this* session**. Under Model-1 (0008.6 row 69) the
runtime/MAF version is **per-session** — captured from the app's vendored `.python_packages` at
session start — so `protocol_version` belongs to *that session's* captured runtime, and the
controller operates against **the session's own epoch**, not a fleet-wide "latest". There is
therefore **no** "latest protocol vs. an old session" comparison and no supported-version
window: per 0008.7 (row 70; `docs/frds/0008.7…:331-333`) a change to the captured content
digest **drains the session** rather than being reconciled against a newer controller. So
`ensure_ready`'s check is a **session-scoped consistency guard** — does this sandbox still speak
the epoch this session was created with? — not a version-window enforcer. This check is
**v1-active**. The specific
*committed-image* case below — a stale Path 2 image after a base/`protocol_version` change — is
**Path 2 / future**: larohra scoped **v1 to Path 1 (controller-captured
content delivered over the file transport, not a committed image) only**. The
detection design stays valid and simply activates if/when Path 2 lands.

**Acceptance conditions** (why this candidate is only conditionally accepted):
idempotent detached acceptance surviving disconnect; p95 status/event visibility
≤ 2s while polling ≤ 1/s per stream; request/result files capped at 4 MiB and
event journals rotating in 1 MiB segments; reliable cancellation; auto-suspend
disabled while active and repaired after failure; acceptable cost/throttling at
100 concurrent runs. If any fails, authenticated private ingress becomes a v1
prerequisite — **anonymous ingress is never an allowed fallback.**

**Default-quota assumption (imported from 0008.4).** Sibling
[0008.4](0008.4-resource-residency-and-provisioning.md) resolved that
resource residency uses the **ACA Sandboxes preview default quotas** and will not
special-case, pre-request, or design around raised quotas (its Decision 30). That
makes it **0008.5's responsibility** to prove that a *single Sandbox Group under
default preview quota* sustains the 100-concurrent target (Decision 29) through the
load gate below. If the default quota proves insufficient, that is recorded here as
a **0008.5 acceptance finding** (feeding the reconsider triggers — authenticated
private ingress and/or a load-shaping cap) rather than reopening 0008.4's
Decision 30.

## Alternatives considered & why the choice won

- **Transport (Decision 7).** Considered: anonymous sandbox HTTP port; ADC
  file+exec; or a mandatory private-network tunnel. Chosen: ADC file+exec journal,
  keeping a transport abstraction. An anonymous port is a security non-starter; a
  mandatory tunnel adds heavy networking prerequisites. *Agent.*
- **Confidence gate (Decision 23).** Considered: finalize from docs; require a
  live spike; or switch immediately to public ingress. Chosen: require a live
  spike first — samples prove *mechanism* but not *latency/idempotency/cost*.
  *Agent reviewer.*
- **Functional gate result (Decision 26).** Considered: approve from docs; require
  authenticated ingress; or run a preview spike. Chosen: the spike ran and passed,
  so file/exec is retained. *Human + Agent.*
- **Concurrency target (Decision 29).** Considered: 25 / 100 / 1,000 active runs.
  Chosen: 100 — a pragmatic pilot target bounding the load-validation gate.
  *Human.*
- **Long-running streaming transport (gRPC-style), discussed 2026-07-22.** A persistent
  bidirectional channel was raised as an alternative to journal polling. Summary: it would
  give token-level streaming and message-based cancel, but it reintroduces the two things
  the journal deliberately avoids — a sandbox **ingress path** (an anonymous port, which is
  forbidden, or a heavyweight private tunnel) and a **connection-bound, stateful** run that
  dies with its controller instance. Recorded as a possible *future* transport behind the
  transport abstraction interface (see Resolved design details), not a v1 choice. *Human + Agent.*

## Honest critique

**Strengths.** Refusing anonymous ingress and riding the *authenticated* data
plane removes an entire class of exposure. Making every run detached-and-idempotent
is elegant: sync and async become the same mechanism, and duplicates are safe.
Grounding the decision in a *measured* spike (not just docs) is exactly the rigor a
preview dependency deserves, and the "state read can lag the data plane" finding is
the kind of thing only a real spike surfaces.

**Risks / assumptions.**
- **Streaming latency is degraded by design.** Polling a journal yields ~1–2s p95
  event visibility versus today's token-by-token stream. That's an explicit,
  accepted regression (see 0008.11) but a real UX cost.
- **Preview SDK fragility.** The whole transport is validated against SDK
  `0.1.0b3`; API shape, the 300s exec limit, quotas, and file-op envelopes can all
  change under preview.
- **100 concurrent is validated only functionally so far.** Decision 26 passed a
  *single-sandbox* functional gate; the *load* gate at 100 concurrent is still an
  implementation-readiness gate (parent §4.16). Data-plane throttling at scale is
  an open risk that could send the transport back to review.
- **Polling cost.** ≤1/s per active stream across 100 runs is a lot of data-plane
  calls; cost/throttling at scale is asserted-acceptable but not yet proven.

**Reconsider triggers.** Revisit (and potentially adopt authenticated private
ingress) if: the 100-concurrent load test reveals a data-plane limit below target;
any acceptance condition regresses on a newer SDK; polling cost/throttling proves
unacceptable; or token-level streaming becomes a hard product requirement
(coordinate with 0008.11).

## Resolved design details

These close the design-level open questions raised in the deep-dive (only the
100-concurrent *load* gate and the SDK-pinning *policy* remain open, below). Decided by
Human + Agent, 2026-07-22; refined and finalized 2026-07-23 (see Status & finalization);
docs-only.

**v1 durability scope (per 0008.8, finalized).** 0008.8 deferred the **external checkpoint
(Blob) mirror to v2**. So in v1 there are two layers, and "durable" means different things at
each — do not conflate them: (a) the sandbox's own non-rotating `status.json`/`result.json`
(this transport layer) are durable *across suspend/resume* (snapshot preserves them) but are
**sandbox-scoped — not durable against sandbox loss/reaping**; once the sandbox is reaped they
are gone, with no external copy until the v2 mirror; (b) the customer **Tables control-plane
record** (session/run status/pointer/generation, 0008.3 Decision 20) is the layer that
**survives reaping**. Two consequences thread through the notes below: (1) on a **sandbox/snapshot
loss**, the in-flight run is terminal `abandoned`, and *session* fate is **v1/v2-dependent**: in
**v1** (no external mirror) a loss **tombstones the session** — the same `session_id` returns
`410` (master-log row 67); in **v2** (external Blob mirror) a sandbox-*instance* loss **may be
recovered by rebuilding the session from the mirror — a state-preserving rebind (generation bump
per 0008.3), not a tombstone** — and a tombstone occurs only on a *true* loss where the mirror is
also gone (exact v2 recovery semantics deferred to 0008.8/0008.12). Session *continuation* within
a generation still applies to the harness-crash-with-sandbox-intact case (resume from the last
committed checkpoint on the **same** sandbox); and (2) every reference below
to recovering a completed-then-reaped run *from the mirror*, or to a *mirror-first* abandon
ordering, is likewise a **v2** capability. 0008.12 defines the v1 answer as a
**status-vs-content split** consistent with the two layers above: after a sandbox is reaped, a
completed or abandoned run's terminal **status** survives in the **Tables control record**
(0008.3) — which is what frees 0008.2's slot and answers `read_status` — while its terminal
**content** (transcript/checkpoint/`result.json`) is *not* recoverable in v1 and returns in
**v2** with the mirror. While the sandbox is still alive, its non-rotating
`status.json`/`result.json` serve the full terminal record (status + content). **None of this
changes a transport verb** — the file
journal and the six-verb interface are identical in v1 and v2.

**Event-journal retention & compaction (resolves the rotation question).** `events.jsonl`
rotates in 1 MiB segments; the controller retains the **last 16 segments (≈16 MiB)** per
run as a tunable default. Compaction is **deletion, not archival**: when a new segment
rolls, the oldest segment beyond the window is deleted from the sandbox disk. There is no
`archived/` rollup — the event journal is a *transient resume buffer*, not the source of
truth; the completed-turn terminal record is the sandbox's non-rotating
`status.json`/`result.json` (sandbox-scoped — durable across suspend/resume but not against
reaping; the reaping-surviving copy is the Tables control record for status, and the v2 mirror
for content — see the v1 durability-scope note above). Sixteen 1 MiB segments hold tens of
thousands of recent event lines — far more than a brief client disconnect needs — while keeping
per-run disk bounded.
Rotation applies to `events.jsonl` **only**: `status.json` and `result.json` are separate,
non-rotating files (the 4 MiB request/result cap) that hold the authoritative terminal
state. So segment rotation bounds *streaming replay depth*, **not durability** — terminal
state lives in the non-rotating `status.json`/`result.json`, so a chatty run cannot rotate its
terminal recovery point away. The durability question is instead about preserving those files
against sandbox loss/reaping (0008.12's domain — in v1 without an external mirror, via the
mirror in v2), never about event rotation.

**Replay beyond the retained window → `snapshot-restart` (resolves `Last-Event-ID` depth).**
When a client polls events with a `Last-Event-ID` older than the oldest retained segment,
the controller does not silently skip. It returns a control frame naming the earliest event
it still has and pointing the client at authoritative state to re-sync first:

```json
{ "type": "snapshot-restart",
  "reason": "last-event-id-evicted",
  "earliest_available_event_id": "E",
  "authoritative": ["status.json", "result.json"] }
```

Client contract: on `snapshot-restart`, re-read `status.json`/`result.json` for
authoritative state, then resume the stream using the exclusive cursor immediately before
`earliest_available_event_id` — i.e., `after_sequence = E - 1` when the frame reports
`earliest_available_event_id = E`. The client always knows it jumped — no silent gaps — and
event `E` is not skipped. This bounds the "replayable chunks" guarantee in
0008.11: replay is guaranteed only within the retained window; older reconnects restart from
a snapshot. `snapshot-restart` is a **typed control record on the cursor-bearing
`read_events` path only** — the cursorless `get_status`/`get_result` reads never emit it,
because they *are* the authoritative state it points back to. How the HTTP layer renders it
to callers (a named SSE event vs. an in-band data frame) is 0008.11's to finalize.

**Cancellation reaches a terminal state regardless of load (resolves cancel reliability).**
Cancel invokes the entry point's cancel command, which signals the recorded process and
journals `canceled`. To remove the "stuck in `running`" failure mode, the controller applies
a **cancel timeout**: if the cancel command does not confirm a terminal journal entry within
a bounded window, the controller escalates to a **verified process-group kill** in the sandbox
and only then forces terminal `canceled`; if the process group cannot be verified dead or the
sandbox is lost during escalation, the reconciler adopts `abandoned` instead. The controller
must never merely overwrite status while a process may still be running with external side
effects. A later run's sandbox OS-lock acquisition remains the backstop: if a stale process
still holds the lock, admission/submission fails and reconciliation continues rather than
running concurrently. **The same verified-death rule governs crash liveness / `active_run_id`
release:** a suspected-crashed run's slot is freed (via terminal `abandoned`) **only after
*confirmed* death** — the harness OS-lock / process-group is observably released, **or** a
verified process-group kill / sandbox-reclaim produced definitive death. An *unverifiable*
death does **not** free the slot by status-overwrite; it **escalates to verified-kill/reclaim
first**, because a process that still holds the OS lock may still be emitting external side
effects. (Verified-kill + the compare-and-set slot release are owned by 0008.2; the reconciler
that drives this is 0008.12.) This
guarantee holds independent of concurrency, so it does not depend on the still-pending load
gate — the load gate may additionally *measure* cancel p95 at 100 concurrent, but
correctness does not rely on that measurement.

**Cancel during a resume race → serialize (resolves the resume-race question).** Because
`sandbox.get().state` can lag the data plane, a cancel arriving while the sandbox is
suspended/resuming is **serialized behind `ensure_ready`**: the controller resumes, verifies
the protocol/session manifest (the 0008.8 handshake), and only then cancels the rehydrated
process — so the signal always lands on the correct PID.

**Transport abstraction interface (resolves the swap-seam shape).** The controller depends
only on a small, transport-agnostic verb set; the ADC file-journal is one implementation of
it, and any future transport (e.g. the gRPC option above) must satisfy the same contract
without touching controller code:

```text
submit(run_id, envelope)                 -> accepted     # idempotent on duplicate run_id
get_status(run_id)                       -> state         # v1: sandbox while alive, else Tables (0008.3)
read_events(run_id, since=Last-Event-ID) -> [events] | snapshot-restart
get_result(run_id)                       -> result | result-evicted   # v1: evicted after post-terminal grace+reap
cancel(run_id)                           -> terminal     # forced-terminal on timeout
ensure_ready(sandbox)                    -> ok           # resume + manifest handshake (0008.8)
```

Two verbs carry a v1 durability nuance from 0008.12's status-vs-content split (see the v1
durability-scope note): `get_status` is answerable even after the sandbox is reaped (terminal
status lives in the Tables control record), whereas `get_result` returns the payload only while
it survives — 0008.12's reaper keeps a terminal-but-unretrieved async result alive until the
earlier of retrieval or a bounded **post-terminal grace window**, after which reap makes the
content unrecoverable and `get_result` returns **`result-evicted`** (surfaced as HTTP `410` by
0008.11; status still resolvable via `get_status`). This parallels `snapshot-restart` for
`read_events`: a typed "the durable answer moved / is gone" signal, not a silent miss. v2's
mirror upgrades `get_result` to survive reaping.

All six verbs are **controller-initiated** (controller writes/reads; sandbox executes and
journals). That direction is a deliberate property, not an accident — it is why the transport
needs no sandbox ingress. A *future, exploratory* need for the reverse direction — a
**sandbox-initiated host call** (the sandbox asks the controller to run a control-plane
operation and awaits the result) — has been surfaced by sibling 0008.14 (Dynamic Workflows
compatibility), which sketches proxy `@workflow_tool` handlers that ride the existing journal:
a typed `events.jsonl` record requests the call, the controller services it against its
`durable_client`, and the result is written back to a `runs/{run_id}/workflow_calls/{...}.json`
sub-path. **Transport ruling (this FRD's call):** reusing the file primitives is fine, and the
sketch correctly avoids the rejected gRPC channel (stateless, connectionless, no ingress). But
this is **not** an unversioned convention — it is a **formal, versioned protocol capability**
when a real FRD adopts it, for three reasons: (1) it is *not safely ignorable* — a controller
that doesn't service the request leaves the proxy's `await` hung forever, so both ends must
agree they speak it, which is exactly what `protocol_version` (via the `ensure_ready`
compatibility check) must gate; (2) it is the **first sandbox-initiated interaction**, inverting
the control direction, so it carries its own reliability surface — `request_id` idempotency
(mirroring `run_id`), a cancellation story (run canceled while a host call is pending), and an
instance-death story (the durable orchestrator survives on the controller, but the transient
bridge poll must be re-serviceable after a controller recycle); (3) it adds data-plane polling
volume that a future load gate must fold in. Recommended shape when adopted: a **generic
reverse-RPC verb pair** — e.g. `request_host_call(run_id, request_id, op, args)` +
`deliver_host_call_result(run_id, request_id, payload)` — rather than a workflow-specific verb,
so it generalizes (future brokered/control-plane calls reuse it). **v1 is unaffected** —
Dynamic Workflows cannot run in the sandbox in v1, so no seventh verb is added now; this is
recorded as a forward-looking constraint for whoever implements it.

**Instance-death handoff / reattach (a transport strength).** The journal is
*connectionless*, so a run outlives the controller instance that launched it. If the original
Functions instance recycles mid-run, any later instance can reattach. Ownership resolution is
stateless/per-request — `session_id` + `OwnerContext` resolution is owned by 0008.2 and holds
no in-memory session state — while the **binding record** it reads is owned by 0008.3.
That record is *not* immutable for the session lifetime; per 0008.3's (finalized) trust model
it is **durable, single-active, monotonic, and rollback-proof** — a forward-only `generation`
counter carried **on the authoritative state row itself (ETag-guarded)**, so the sandbox
pointer is stable *within a generation* and only ever advances via a recorded rebind (never a
silent swap or rollback); authoritativeness comes from scoped RBAC + disabled Shared Key
making the controller MI the sole writer, and routing authenticity from the live sandbox
manifest. A reattaching instance must therefore resolve the **current, row-generation-verified
(ETag-guarded) binding** (highest generation), not cache
the generation the dead instance saw. Within that current generation the sandbox is the same,
so the instance runs `ensure_ready` (0008.8), reads
`status.json`/`events.jsonl`/`result.json`, and resumes streaming from `Last-Event-ID`
(subject to the retained window above). Liveness authority is the **sandbox OS-lock + run
journal** (this FRD) — never 0008.2's storage lease, which is released after submission and is
explicitly not a liveness signal, so a reattaching instance cannot get a stale-lease false
positive. Idempotency protects the race where the new instance re-submits the same `run_id` —
the sandbox returns existing status instead of launching a duplicate. A connection-bound
transport (e.g. a live gRPC stream) would fail this scenario; the file journal survives it by
design. One completeness note: reattach reads the *live* sandbox, so it assumes the sandbox
still exists. If the run already completed and the sandbox was reaped between instances, there
is nothing to reattach to. In **v2**, the terminal checkpoint is recovered from the 0008.12
external mirror (guaranteed present by that FRD's **mirror-before-reap invariant** — the reaper
must not delete a sandbox whose terminal checkpoint the mirror has not confirmed). In **v1**
(no external mirror — see the v1 durability-scope note), once the sandbox is reaped only the
run's terminal **status** survives (in the Tables control record, 0008.3) — enough for
`read_status`, but the transcript/checkpoint **content** cannot be recovered across instances
until v2. While the sandbox is still alive — 0008.12 defers reap/idle-suspend for a
terminal-but-unretrieved result until retrieval or a bounded grace window — full content-level
reattach works from its `status.json`/`result.json`. Either way this FRD's transport contract
is unchanged.

**Reattach never spans a generation bump of an in-flight run (answers 0008.3).** Live-run
reattach is always *within a single generation* — the same sandbox, including across an
auto-suspend/resume cycle (0008.8), which is state-preserving and stays on the **same
generation**. A **generation bump** is a **v2-only** event owned by 0008.3: in **v1 the
generation is fixed at session creation** (advancing it requires the external mirror, which is
v2). In **v2** a bump is a state-*preserving* rebind of the session to a **different sandbox
instance** (the row generation advances while the session continues from its committed
checkpoints) — it is **not** a sandbox loss; a true loss tombstones (410) and does not bump.
Even so, an in-flight (not-yet-committed)
run cannot migrate across a bump,
because in-flight turn state lives only on the prior instance's disk and is **not** durably
mirrored — 0008.12 mirrors only *committed* turns. So a run interrupted this way is
**abandoned, not migrated**; and per master-log row 67 the interruption cases split by *what
happened*:
- **Sandbox/snapshot lost:** the in-flight run is terminal `abandoned` (its OS-lock + journal
  died with that sandbox); *session* fate is **v1/v2-dependent**. In **v1** (no mirror) this
  **tombstones the session** — the same `session_id` returns `410`; it is **not** a generation
  bump (no rebind). In **v2** (external mirror) a sandbox-*instance* loss **may be recovered by
  rebuilding from the mirror = a state-preserving rebind (generation bump per 0008.3), not a
  tombstone**; a tombstone occurs only on a *true* loss where the mirror is also gone (exact v2
  semantics deferred to 0008.8/0008.12).
- **Harness crash with the sandbox/disk intact** (same generation, no bump): the crashed run is
  terminal `abandoned`, but the **session continues** — it resumes from the last committed
  checkpoint on the **same** sandbox (disk, OS-lock, and on-disk `session/checkpoints/` survive
  the process; resume mechanics are owned by 0008.8/0008.12).

This composes with the two siblings: one-active-run
(0008.2) is not left blocked, because the abandoned run's OS-lock/journal are gone with the old
sandbox and the run is **reconciled to a terminal state by 0008.12's reconciler** — since the
lost sandbox can no longer journal its own terminal state — which is the only thing that frees
0008.2's slot. In **v2**, to avoid a false-abandon race, 0008.12 checks the external mirror
**first**: a run that actually completed before its sandbox was reaped adopts its *mirrored*
terminal (`succeeded`/`failed`), and only a sandbox-gone run with **no** verified terminal
checkpoint is written `abandoned` — so a completed turn is never mislabeled (the reconciler
side of the mirror-before-reap invariant in the reaped-completed-run note above). In **v1**
(no external mirror), there is no mirrored terminal to adopt; the abandoned/terminal **status**
is written to and read from the **Tables control record** (0008.3), which is what frees
0008.2's slot once the sandbox is gone. Distinguishing a completed-then-reaped run from a
genuinely abandoned one at content level is a v2 capability (needs the mirror); in v1 the
Tables status is the authority. `abandoned` is treated as a **distinct, no-fault terminal
outcome** (infra loss — not an
agent/harness `failed`, nor an explicit `canceled`), keeping the terminal-state taxonomy
clean for `read_status`/reattach; the exact surfaced status string is 0008.11's to confirm.
Meanwhile resume-readiness (0008.8) applies to same-generation suspend/resume **and** to the
harness-crash-with-disk-intact case. Across a **generation bump** (v2-only; a state-preserving
rebind to a *different* sandbox instance), the in-flight *uncommitted* run does not migrate — it
terminates/abandons and the caller re-submits against the new generation, with session state
preserved from the committed checkpoints. A sandbox **loss** is not a rebind: in v1 it
tombstones (410); in v2 it may be rebuilt from the mirror (a state-preserving rebind),
tombstoning only if the mirror is also lost.

**Session content delivery over the file transport (v1-active, from 0008.6 rows 66+68;
post-finalization addition).** This makes content-package delivery an **additional payload class
on the same file transport**, completing the transport's v1 role: the one authenticated
controller→sandbox file/exec plane now carries (i) **run-control traffic** (submit/status/events/
result/cancel via the run journal), (ii) the **exec/journal data plane**, and (iii) **session
content-package delivery** — all three as payloads on the same plane, **none a new verb**. The
sandbox is identity-less with no storage access (0008.3/
0008.9), so it cannot fetch its own app content. 0008.6's resolved v1 Path-1 makes **this file
transport the content-delivery channel**: at session start the controller captures the customer
app content from its own script root (code + vendored `.python_packages`), zips it, SHA-256s it,
delivers it into the sandbox over the same authenticated controller→sandbox file plane used for
runs (to `session/content/`), and the sandbox unpacks and **verifies the digest before any run is
accepted**. Two points confirmed for 0008.6:
- **(1) Payload class / size — distinct large-payload path.** The 4 MiB acceptance cap applies to
  *run-journal* files (`inbox`/`result`), **not** to the content package, which with vendored
  packages can be tens–hundreds of MiB. Content delivery therefore uses a **separate large-payload
  path** (the `session/content/` location, single large write or chunked), not the run-journal
  caps. The `0.1.0b3` spike measured only ≤4 MiB round-trips, so **large/chunked content
  throughput is unverified** → a targeted spike extension, and the content size + transfer time is
  a **new input to the 100-concurrent load gate and the latency envelope** (same p95/throughput
  budget as the spike numbers, at a larger size and once per session-create, not per run).
- **(2) Ordering — deliver-then-run, confirmed.** Content delivery is a **pre-run session
  bring-up step**, not interleaved: deliver → unpack → verify SHA-256 → mark session ready, gated
  before the first `submit`. It slots into the same bring-up family as the `ensure_ready`
  protocol/session-manifest verification — the content-digest check is a bring-up gate exactly
  like the `protocol_version` check. **No new run verb; the six-verb run interface is untouched.**
- **Scope / ownership.** Content-package *capture and format* are 0008.6's; the *delivery channel,
  bring-up digest gate, and size/throughput envelope* are 0008.5's. This is a genuine **additive**
  v1 surface surfaced after finalization (a content-delivery bring-up phase + large-payload path),
  not a change to any of the six run verbs or a locked decision — flagged to the parent as a
  scoped addition rather than a silent reopen.

- **Load gate not yet run.** The 100-concurrent validation (p50/p95/p99 latency,

  default preview quota** — insufficient quota is a 0008.5 acceptance finding, not a
  reason to reopen 0008.4's Decision 30. *Kept at preview defaults for now; not run in

  scoped **v1 to Path 1 (content delivered over the file transport, not a committed image)
  only**, which adds no committed-image accumulation, so this
  is not a v1 load-gate input. If 0008.6's optional Path 2 committed disk images land later, a
  single Sandbox Group would hold not just concurrent session sandboxes but an accumulating set
  of per-deploy committed images, both drawing on the same default-quota storage — so a Path 2
  load gate must then treat committed images as an additional quota/storage consumer (and assume
  bounded image retention/pruning rather than unbounded growth — pruning/teardown is
  **deploy/customer-side** per 0008.4's creator-owns-teardown boundary, while 0008.6 owns image
  creation/packaging/format). **Downstream consumer — 0008.13 (subagents):** subagent
  delegation uses platform defaults with no delegation-specific size bound, and its operative
  envelope explicitly includes this 100-concurrent target (Decision 29). If the load gate
  surfaces a **per-session packaging/cold-start limit** that would bite large delegation graphs
  (many reachable agents packaged into one artifact), that is a named reconsider trigger on
  0008.13's side — **notify 0008.13** with the finding.
- **SDK version-pinning policy (deferred).** The transport is validated against preview
  SDK `0.1.0b3`; the fragility concern is recorded (see Honest critique), but the exact
  pin format and the upgrade re-gate policy are **deliberately deferred** to
  implementation rather than decided here. *Recorded `0.1.0b3` lifecycle-surface findings
  (0008.12 spike): no auto-reverting/TTL auto-suspend disable; max idle interval = 3600 s;
  no in-sandbox data-plane self-suspend verb (only control-plane `set_lifecycle_policy`).
  These bound the auto-suspend-restore options below and are inputs to the upgrade re-gate.*
- **Per-sandbox lifecycle-set at create (SDK-feasibility input from 0008.12; post-finalization,
  additive).** 0008.12's approved hybrid retention overrides per-sandbox lifecycle at create so a
  global/app config can reset retention without customer group-IaC edits. It splits into two
  durations by enforcement mechanism, and **neither blocks v1**: (1) **auto-suspend timeout →
  ACA per-sandbox lifecycle-set** — the only part needing the ACA lifecycle surface, and the
  `0.1.0b3` spike *proved* auto-suspend control (evidence: "auto-suspend disabled while active" +
  memory stop/resume; 0008.8 D27 also depends on it). Create-flow fit is clean —
  `create → set_lifecycle_policy → ensure_ready → submit`, one extra data-plane op, **no transport
  verb change**. (2) **reclaim window → reaper-enforced data-plane delete**, *not* ACA
  `auto_delete` — 0008.12's reaper deletes an idle-expired sandbox via the data-plane delete the
  spike already covered as cleanup, so reclaim needs no new surface. Consequently the unverified
  `auto_delete`/`AutoDeletePolicy` surface is **off v1's critical path** — recorded as a *future
  optimization* (let the platform reclaim natively) gated on a **targeted spike extension** (a
  small Decision-26 extension, not a full new gate per Q2), never a v1 blocker. **Load-gate
  input:** the create-time auto-suspend write adds one per-sandbox data-plane write per create
  (scales with session-creation rate, not run volume) — folded into the 100-concurrent gate's
  budget like the Path-2 committed-image consumer. Retention policy is 0008.12's; this bullet
  records only the SDK/create-flow/load feasibility they cited.
- **Auto-suspend restore after a detached async run (design-investigation input from 0008.12;
  post-finalization, additive).** During a run, auto-suspend is disabled (0008.8 D27); for a
  *detached async* run the controller is gone at `202`, so something must restore auto-suspend at
  terminal (heartbeat ruled out). Transport-owner read on the three candidate mechanisms, two of
  which are answered directly by this FRD's *finalized invariants*:
  - **(a) sandbox self-action.** Two distinct in-sandbox operations (distinction from 0008.8):
    - **(a1) self-policy-REWRITE** (in-sandbox `set_lifecycle_policy` to re-enable/retime its own
      auto-suspend): **OUT.** This is a *management/control-plane* op; my spike exercised it
      **controller-side only**. In-sandbox it would need a managed identity with rights to mutate
      its own ACA lifecycle **plus** egress to the management endpoint — breaking the sealed-sandbox
      boundary and pulling in 0008.9 (identity) + 0008.6 (egress). Agreed with 0008.8: out for the
      harness.
    - **(a2) self-suspend-REQUEST** (data-plane "I'm idle, you may nap me"): **not surfaced on
      `0.1.0b3`, and not creds-free the way it first appears.** 0008.12's spike found only the
      control-plane `set_lifecycle_policy` (out for the sandbox) — **no data-plane "nap me" verb
      was identified** on the pinned SDK; my own spike had only exercised *controller-initiated*
      suspend/resume. So (a2) is not merely untested but **absent on the current surface**, making
      it a **future** possibility contingent on ACA adding such a verb *and* its own targeted
      spike. Even then it is not free: an in-sandbox ADC call still needs (i) an ADC client inside
      the sandbox and (ii) **egress from the deny-by-default sealed sandbox to the ADC data-plane
      endpoint** (0008.6) — lower footprint than (a1) (no management identity) but still one narrow
      egress puncture. And the **free alternative already in the design** stands: the harness
      writes terminal to `status.json`, and that journal write *is* the creds-free, egress-free
      "I'm done" signal (it just doesn't itself trigger a nap) — so (a2) would only ever buy
      self-napping *promptness* over the reconciler, at the cost of one egress rule.
  - **(b) sandbox→FunctionApp completion callback:** **no such hook exists, and it is *dominated*,
    not merely disallowed.** The protocol is deliberately **pull-only/connectionless** — the
    sandbox journals terminal to `status.json`/`result.json`; there is no push. Why a callback is
    not the cheaper option (a natural "push is cheaper than a timer" intuition): (1) the periodic
    reconciler **must exist regardless** — it is the only thing that catches a *crashed* harness
    that never journals terminal and never calls back, and it already drives one-active-run slot
    release (0008.2) and the abandon-path (0008.12). So auto-suspend restore is a **free rider** on
    a mandatory sweep; a callback would be **additive (callback + timer), not a substitute** — a
    crash never fires a callback. (2) A callback needs new **controller ingress**, **sandbox
    egress** (0008.6), an **identity** to authenticate it (0008.9), and anti-spoof validation —
    the exact surface the pull-only transport exists to avoid — and is only best-effort, so it can
    never be the mechanism of record. (3) It is not even free on Functions: a scaled-to-zero app
    **cold-starts to receive** the callback, the same wakeup cost as a timer firing. (4) For the
    *promptness* goal a callback would serve, **(a2) self-suspend-request dominates it** — the
    sandbox naps itself directly with no controller round-trip, inbound endpoint, or controller
    auth. So the design-fit "completion hook" is simply the **next controller touch** (reconciler
    sweep, or a client polling `get_status`/`get_result`) observing the journal terminal. Rejected.
  - **(c) long-finite idle interval instead of full disable:** **optional, deployment-dependent
    hardening — and now concretely bounded by a 0008.12 spike finding.** The spike found ACA has
    **no auto-reverting/TTL disable form**, and a **maximum idle interval of 3600 s**. So "(c)"
    concretely means *set `interval=3600` at create instead of `enabled=False`*: it makes **ACA
    itself the fail-safe** (a leaked sandbox naps→reclaims within ≤1 h even if the reconciler never
    runs) **but caps the maximum in-run quiet period at ~1 h** — a run silent-on-disk >1 h (e.g. a
    long model call or open-ended human-in-the-loop wait with no journal writes) would be napped
    mid-flight, which is exactly D27's rationale for full-disable. `interval=3600` and full-disable
    are therefore **mutually exclusive at create**, trading *arbitrary-quiet-run support*
    (full-disable) against *ACA fail-safe + ≤1 h quiet cap* (`interval=3600`). **That trade is
    0008.8's D27 call, not this FRD's**; (c) is recorded here only as an optional hardening for
    deployments that accept a ≤1 h quiet ceiling. **The reconciler is the correctness floor either
    way**, so v1 correctness does not depend on which D27 picks.
  - **Recommendation (feasibility, not a decision — 0008.12 synthesizes):** the **reconciler is
    the correctness floor** (it's the only guaranteed restorer — a crashed harness can't
    self-signal). Optionally layer (c) `interval=3600` at create as an ACA fail-safe **where the
    deployment accepts a ≤1 h max-quiet ceiling** — else full-disable + reconciler (D27's call).
    Treat **(a2) self-suspend-request as an optional *promptness* optimization** — it only trims
    the awake tail before the reconciler sweep, and is justified **only if** a targeted spike
    confirms an in-sandbox data-plane self-suspend verb on `0.1.0b3` **and** 0008.6 grants the one
    narrow egress destination. Reject (a1) and (b) — (b) is dominated (additive to the mandatory
    timer; beaten by a2 on promptness). Net ranking: **reconciler [correctness floor] + optional
    (c) [if deployment accepts ≤1 h cap]** ≫ **+(a2)** [future promptness, spike+egress-gated] ≫
    (a1)/(b) rejected. No new transport verb in any case.
- **Retention time-floor (non-dependency, parked).** A time-floor on event-journal retention
  (e.g. "≥ N minutes regardless of volume") was raised by 0008.12 as possible defense-in-depth
  for replay UX under chatty runs. It is **not needed for correctness** — durability rests on
  the non-rotating `status.json`/`result.json` (and, in v2, the 0008.12 external mirror), and
  cursor eviction is handled by `snapshot-restart`. If it ever helps 0008.11's streaming UX it
  is a retention *tuning* call for the human, not a cross-FRD dependency.
