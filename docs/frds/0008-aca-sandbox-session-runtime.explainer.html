FRD 0008 · Preview / for team feedback

ACA Sandbox Session Runtime

Run the entire AI-agent loop inside one ephemeral Azure Container Apps sandbox per session — with Azure Functions as a thin, secure controller.

Validated · 5 rubber-duck rounds 70 recorded decisions 1 parent + 14 sub-FRDs v1 scope · MAF-only

1The big idea

Today, an agent's "thinking" runs in the Python Functions worker, but any LLM-generated code runs on a separate Dynamic Session — two different computes, and state can be lost between invocations. This feature collapses that into one place.

In plain terms: give every agent conversation its own private, disposable computer (an ACA "sandbox"). The whole agent — the model loop, its tools, its memory — lives on that one computer for the life of the session. Azure Functions stops being the compute and becomes the doorman: it authenticates callers, routes them to the right sandbox, and is the only thing allowed to write down "what happened."

◆One sandbox / session

Not one per invocation. The sandbox (and its snapshot) lives for the whole session, so agentic context is never scattered across computes — no state loss.

◆Functions = controller

A thin, authenticated proxy: auth, session lookup, routing, and the single writer of session state. It never runs the agent itself.

◆Brain + hands together

The MAF "brain" and its tool "hands" run in the same sandbox — the full agent loop runs end-to-end in one ephemeral, isolated container.

2Why an ACA sandbox

Four properties of ACA sandboxes map directly onto hard requirements.

🔒No secrets ever enter the sandbox

An egress proxy injects credentials into outbound calls, so tokens/keys never live inside the sandbox. The sandbox is identity-less — no managed identity, no AAD token, nothing to steal.

🎫Enterprise auth (OBO-ready)

The egress/identity broker pattern gives a path to on-behalf-of flows that several enterprise customers need — without baking credentials into agent code.

💾Snapshot & resume

ACA can suspend an idle sandbox and resume it later with disk (and memory) intact — enabling durable, long-lived sessions that scale to zero between turns.

📦Real container harness

A container makes it straightforward to host the agent harness (and, later, richer first-party harnesses) instead of only the vanilla in-worker model.

3How it fits together

One authenticated control path in; one credential-injecting egress path out; the controller owns the durable record.

authenticated control path (only way in) data / dependency identity-less sandbox

The controller reaches the sandbox over a single authenticated file/exec plane (six verbs) that carries run-control traffic, the exec/journal data plane, and the session content package — no other inbound path exists.

4What a request looks like

⚡Synchronous (default chat)

1
Call arrives — Functions authenticates & finds/creates the session's sandbox.
2
Content delivered — controller captures its own /app and ships it into the sandbox (first turn only).
3
Agent runs — the MAF harness executes the turn; tools call out via the egress proxy.
4
Result returns — within the 180-second cap; the answer is the HTTP response.

⏳Asynchronous / streaming (long work)

1
Submit — returns 202 + a result_url immediately.
2
Poll or stream — /status, or /events (SSE) with reconnect via Last-Event-ID.
3
Disconnect ≠ cancel — the run keeps going; you re-attach. Only an explicit cancel stops it.
4
Fetch result — /result returns the outcome (or 410 once evicted).

5The session's life

A session is one sandbox, one content epoch, from birth to reap.

▶
Create — controller provisions a sandbox, stamps it with the content digest (its "epoch"), delivers the app.
↻
Run & commit — each turn is written to disk with an all-or-nothing per-turn commit, so a crash never resumes half-written state.
💤
Idle → suspend / resume — ACA suspends the idle sandbox and resumes it (same instance, same generation) on the next turn.
✱
Harness crash, disk intact — the run is abandoned but the session continues on the same sandbox from the last committed turn.
⤳
Redeploy — a content change drains in-flight work and tombstones the session (410); the client starts a fresh session on the new epoch. (Cross-deploy continuity is a v2 feature.)
✝
Loss or idle-expiry — a truly lost sandbox tombstones (410); idle sessions are reaped after the retention window. Control-plane status stays durable in the Table.

6Key design decisions

The choices that most shaped the design — several deliberately remove complexity.

Model-1 packaging — run from the captured app environment

The runtime ships as a normal pip dependency (azurefunctions-agents-runtime, which pulls in MAF). So the customer's build already resolves runtime + MAF + their tools into one coherent environment. The sandbox image is a tiny stdlib-only bootstrap that simply runs that captured environment — it bakes no MAF. Result: the dependency-isolation problem disappears (there's only ever one MAF, already resolved together).

Identity-less sandbox

No managed identity or token lives inside the sandbox. Outbound auth is injected by the egress proxy. This also makes the controller the sole writer of session state — the sandbox physically can't tamper with the record.

Drain-on-deploy (the v1 version story)

Rather than build machinery to keep old sessions compatible across a redeploy, v1 simply drains a session when the app's content digest changes — so a session never spans a deploy, and controller & sandbox are always the same version. Simple, and it dissolved two would-be subsystems.

Sandbox loss ⇒ tombstone (never a silent recovery)

In v1 there's no external mirror, so a lost sandbox honestly fails the session (410, start fresh). A crash with the disk intact is different — that resumes. The "generation" counter that would let a session move to a new backing while preserving state is a v2-only capability (it needs the mirror).

Durability is platform-only in v1

v1 relies on ACA snapshot + auto-suspend/resume for warm continuity; only control-plane status is externally durable. A full owner-scoped external checkpoint mirror (so losing a sandbox never loses the conversation) is the headline v2 add.

MAF-only for v1

v1 ships only the Microsoft Agent Framework harness, gated by a golden-trace conformance check. A custom sandbox image is allowed but must still be MAF-conformant; a non-MAF / bring-your-own harness is deferred to its own FRD.
