# FRD 0008.1 — Execution-backend abstraction & the "Functions as controller" model

> Sub-FRD of [FRD 0008](0008-aca-sandbox-session-runtime.md). It re-expresses,
> in plain language, one self-contained decision area from the reviewed parent,
> and pins the contract detail beneath its owned decisions (1, 2, 12, 13) without
> changing them. Status: **Finalized** (whole-FRD human sign-off — larohra,
> 2026-07-27, after the consolidated 5-round rubber-duck validation). The parent
> overview ([FRD 0008](0008-aca-sandbox-session-runtime.md)) tracks overall
> program status.

## What this is and why it matters

Today the runtime runs an agent's "thinking loop" (calling the model, using
tools, keeping conversation history) directly inside the Azure Functions Python
worker. This FRD proposes a second, opt-in place to run that loop: an **ACA
Sandbox** — a programmatically created, isolated Linux container (from Azure
Container Apps) with its own disk image, network rules, and suspend/resume. The
piece of code that actually runs an agent (the model loop plus tools, skills, and
memory) is called the **harness**; today's harness is the **Microsoft Agent
Framework (MAF)**, the SDK the runtime already uses.

This area answers two foundational questions the rest of FRD 0008 builds on:
(1) *what is the seam* between the Functions app and wherever the agent actually
runs, and (2) *what is the Functions app's job* once the agent no longer runs
inside it. The answer is a provider-neutral **execution backend** interface plus
a redefinition of the Functions app as an authenticated **controller** (a trusted
control plane) rather than an agent runtime or a dumb proxy.

## Decisions this sub-FRD owns

- **Decision 1 — Where the agent executes.** The complete harness runs inside
  *one ACA Sandbox per session*, not inside the Functions worker and not split
  across the two.
- **Decision 2 — What the Functions app is.** It is an *authenticated session
  controller*: it authenticates the caller, checks who owns the session, creates
  or resumes the sandbox, and routes a run to it. It is neither the agent runtime
  nor a byte-shuffling proxy.
- **Decision 12 — Default behavior is unchanged.** The existing in-worker
  execution (`provider: in_process`) stays the default; the sandbox backend
  (`provider: aca_sandbox`) is experimental and must be explicitly turned on.
- **Decision 13 — Direct Functions Host integration is deferred.** The
  Python-level controller is enough to prove the product; wiring this deeper into
  the Functions Host is postponed.

> **Note — auth & ownership model (defers to
> [0008.2](0008.2-session-identity-ownership-concurrency.md)).** "Authenticates the
> caller" means the **standard Functions endpoint auth** — function keys or App
> Service Authentication (Easy Auth) — applied before the controller runs; the
> controller adds **no** second, ACA-specific identity layer, and there is no
> blanket Entra requirement. Session ownership is recorded as an **`OwnerContext`**
> that may be **app-scoped** (`kind: function_app`) or a **specific end user**
> (`kind: entra_user`); that ownership model is owned by 0008.2 (revised Decision
> 15, 2026-07-22). This does **not** change the `AgentExecutionBackend` contract:
> the controller authorizes the owner *before* calling the backend, so owner
> identity never crosses the seam (consistent with "typed requests and events
> only"). The *only* owner-derived value that leaves the controller is a **hashed
> owner label** applied to the sandbox/storage resource at **provisioning** time
> (a create-time resource label for owner-scoping/reaping — owned by
> 0008.2/0008.3/0008.4); it is never raw claims and never a field on
> `StartRunRequest`/`RunContext`/`RunStatus`.

### The contract, in plain terms

The controller talks to *any* execution location through a small asynchronous
interface (parent §4.3):

```python
class AgentExecutionBackend(Protocol):
    async def start_run(self, request: StartRunRequest) -> RunHandle: ...
    async def get_run(self, context: RunContext) -> RunStatus: ...
    async def read_events(self, context: RunContext, after_sequence: int) -> AsyncIterator[RunEvent]: ...
    async def cancel_run(self, context: RunContext) -> RunStatus: ...
```

Two implementations exist: `LocalExecutionBackend` wraps today's `runner.py`, and
`AcaSandboxExecutionBackend` drives a sandbox. A crucial subtlety: **`start_run`
always creates a run resource**, so a synchronous chat is just "start a run and
wait for it." Synchronous is not a separate code path — this keeps run IDs,
telemetry, cancellation, and idempotency identical whether the caller asked for
sync or async behavior. The interface deliberately carries *typed requests and
events only* — never live `ResolvedAgent` or Python tool objects — so nothing
compute-specific has to cross a process or network boundary.

Mapped onto the runtime's pipeline (`docs/architecture.md` §2:
discover → translate → register → execute), the seam lives in **execute**, while
**registration** stays the only Azure-aware stage that chooses and wires the
backend. Handlers depend on `AgentExecutionBackend`, not on the ACA SDK.

### Contract types (resolves open question 1)

The parent fixed only the four method *signatures*; this session pins the *data
shapes* they exchange. The guiding rule (restated): the seam carries **only
per-turn, serializable data** — never a live `ResolvedAgent`, tool object, or
catalog. Everything about *who the agent is* (instructions, model, tools, MCP,
skills, subagents, schemas) is bound once at **registration** — a closure over
`resolved` + `capabilities` for `in_process`, or the **controller-captured
script-root content** for `aca_sandbox` — the controller zips its own `/app` script
root (code plus vendored `.python_packages`), and that zip's SHA-256 is the **epoch
digest** (Decision 68; not a Run-From-Package deploy artifact; see
[0008.6](0008.6-sandbox-packaging-image-and-content.md)) — so
`StartRunRequest` stays deliberately small. For `aca_sandbox`, the controller always
supplies `session_id`; only the `in_process` backend may treat `session_id=None` as a
request to mint an ephemeral in-memory session. Provisioning context — owner hash,
monotonic generation, epoch digest, Sandbox Group, protocol version, and egress
policy — is assembled controller-side from `OwnerContext`, app configuration, and the
session record; it is not tunneled through `StartRunRequest`. The shapes below are
illustrative (dataclass/pydantic-style); field names are the contract, decorators are
not.

```python
# Per-turn request — only serializable, per-turn data crosses the seam.
class StartRunRequest:
    prompt: str                           # composed user message (as runner.py takes today)
    session_id: str | None = None         # aca_sandbox: controller always supplies; in_process may mint on None
    idempotency_key: str | None = None    # caller-supplied; pass-through only (see below)
    timeout: float | None = None          # agent-run watchdog budget (reuses authored 'timeout')

# Handle returned by start_run — a ticket for the run it just created.
class RunHandle:
    run_id: str
    session_id: str
    state: RunState
    created_at: datetime

# Minimal address the other three methods use to locate a run.
class RunContext:
    run_id: str
    session_id: str

# Current state; carries the result or error once the run is terminal.
class RunStatus:
    run_id: str
    session_id: str
    state: RunState
    last_sequence: int                    # highest event sequence emitted so far
    result_available: bool                # true iff a success result can still be read
    result: RunResult | None = None       # set iff state == "succeeded" and result_available
    error: RunError | None = None         # set iff state in {"failed", "timed_out", "abandoned"}

# One item in the event stream — today's SSE events plus a sequence number.
class RunEvent:
    sequence: int                         # monotonic per run (enables replay)
    type: str                             # session|delta|message|intermediate|
                                          #   tool_start|tool_end|done|error
    data: dict
    timestamp: datetime

# Non-terminal + terminal run states. Lowercase everywhere on the wire/state-store;
# canonical set unified with 0008.12 (`abandoned` = lost sandbox / silent crash).
type RunState = Literal[
    "accepted", "running",                                          # non-terminal
    "succeeded", "failed", "canceled", "timed_out", "abandoned",    # terminal
]

# Success payload — today's runner.AgentResult content fields (session_id moves to
# RunStatus/RunHandle; the events list is promoted to the first-class RunEvent stream).
class RunResult:
    content: str
    content_intermediate: list[str]
    tool_calls: list[dict]
    reasoning: str | None
    delegate_error_count: int

# Structured, already-sanitized failure.
class RunError:
    code: str                             # stable machine code
    message: str                          # human-readable, sanitized
    fault_domain: str | None = None       # e.g. app | runtime | sandbox-provision | harness (see FaultDomain / parent §6)
```

Design points baked into these shapes:

- **`start_run` always creates a run resource**, so a synchronous chat is just
  "start a run, then poll `get_run` until terminal, then project `result`." There
  is deliberately **no fifth "get result" method** — a terminal `RunStatus`
  *carries* the result. This keeps the interface at four methods and lets sync and
  async share one code path.
- **`prompt` is a plain `str` for v1**, matching what `runner.run_agent` accepts
  today. A structured multi-part `input` (attachments, non-text parts) is a
  reserved future extension, not v1 surface.
- **Terminal states stay distinct** — `canceled`, `timed_out`, and `abandoned`
  (lost sandbox / silent crash) are not folded into `failed` — because callers and
  telemetry treat them differently; the canonical lowercase state set and the
  mapping to the failure table are owned by
  [0008.12](0008.12-lifecycle-failure-and-reconciler.md).
- **`RunResult` carries today's `runner.AgentResult` content fields, and
  `RunEvent.type` reuses today's SSE vocabulary** verbatim — so
  `LocalExecutionBackend` is a thin wrapper and the sandbox backend has an exact
  parity target, enforced by the conformance suite in
  [0008.7](0008.7-harness-compatibility-and-conformance.md). (`AgentResult.session_id`
  moves to `RunStatus`/`RunHandle`; its `events` list is promoted to the first-class
  `RunEvent` stream.)
- **`idempotency_key` is pass-through only.** The contract *carries* the caller's
  key so a lost-response retry can resolve to the same run instead of starting a
  duplicate; it does **not** define the dedupe semantics. `run_id` stays
  **server-minted** ([0008.5](0008.5-controller-sandbox-transport-and-protocol.md))
  and is the only value used as the data-plane identity — a caller-supplied key is
  never trusted as routing/identity (Decision 2's rejection of the dumb-proxy
  framing). This is the standard client-idempotency pattern (e.g. Stripe
  `Idempotency-Key`, AWS `ClientToken`, Azure `Repeatability-Request-ID`).
- **`RunEvent.sequence` / `RunStatus.last_sequence` are new** relative to today's
  SSE (which carries no sequence numbers). They exist to make replay possible and
  are the hook the HTTP layer's `Last-Event-ID` builds on — see the **Event replay
  & cursor semantics** section below (open question 3).

### Timeouts & cancellation (resolves open question 2)

There is **one authored knob — `timeout`** — and it is the only run-duration
field authors set (it reuses today's `ResolvedAgent.timeout`; there is no parallel
`max_run_seconds`). At runtime that single knob yields **two derived bounds**,
which stay distinct because they answer different questions:

| Derived bound | Question it answers | Lives | Enforced by | On expiry |
| --- | --- | --- | --- | --- |
| Agent-run watchdog | "How long may the agent run?" | **Backend** — `StartRunRequest.timeout` | sandbox watchdog (0008.8) / `in_process` `asyncio.wait_for` | run → `timed_out` |
| Sync-wait cap | "How long may the HTTP connection wait?" | **Controller / HTTP layer** (0008.11) | controller wall-clock timer | unary → `504`; streaming → in-band terminal SSE frame |

Consequences for this contract:

- **The sync-wait cap is *not* a field on the contract.** The backend never sees
  the 180 s number; it only receives `timeout`. The controller races its own wall
  clock against polling `get_run`, so the cap is entirely a controller concern.
- **The cancellation entry point already exists — it is `cancel_run`.** The
  controller calls it in only two situations: an **explicit cancel** (the `/cancel`
  route, or a verified active-run kill) or when the **sync 180 s cap** fires. A
  **client disconnect does *not* cancel the run** — the run keeps running, and the
  client re-attaches by reconnecting and replaying from its cursor (`Last-Event-ID`
  / `after_sequence = E - 1`), per 0008.11's reconnectable-stream model. No fifth
  method is needed.
- **The two clocks map to two distinct terminal states.** The agent-run watchdog
  (the agent exceeded its own `timeout`) ends the run `timed_out`; an explicit
  cancel or the sync-wait cap goes through `cancel_run` and ends the run `canceled`.
  How a sync-cap breach is *surfaced* depends on whether the HTTP response has
  already started: on the unary `/chat` path the controller returns HTTP `504`; on
  `/chatstream` the SSE `200` headers are already flushed, so a late `504` is
  impossible — the breach is delivered as an **in-band terminal timeout SSE frame**
  and the stream then closes (aligning with 0008.11's in-band model). A client
  disconnect is **neither** `timed_out` nor `canceled` — the run stays `running`
  and remains re-attachable. This is why the `RunState` terminal set keeps
  `timed_out` and `canceled` separate.
- **The 180 s cap applies to the sandbox-backed path only.** `in_process` keeps
  today's behavior — an authored `timeout` above 180 s still runs synchronously —
  preserving Decision 12's "byte-for-byte unaffected" default. On the sandbox path
  the effective sync wait is `min(timeout, 180 s)`; a longer `timeout` is honoured
  only under `Prefer: respond-async`.
- **With co-located agents (0008.13), the entry agent's `timeout` governs the run.**
  `StartRunRequest.timeout` is taken from the authored `timeout` of the agent the
  run *addresses* (the coordinator in a delegation). Co-located subagents never
  extend it: per FRD 0007 a delegated call is bounded by `min(subagent timeout,
  coordinator remaining)` — already how `runner.py`'s `coordinator_deadline`
  behaves — so the watchdog enforces one run-level budget no matter how many agents
  share the sandbox. This also means the *app-level* backend selection (0008.10)
  and the *per-agent* `timeout` never conflict: a run always targets exactly one
  entry agent, whose `timeout` is authoritative.

### Event replay & cursor semantics (resolves open question 3)

`read_events(context, after_sequence)` is the **only** replay mechanism — there is
**no** separate "replay from beginning" mode or flag. Because `RunEvent.sequence`
is monotonic, `after_sequence=0` *is* "from the beginning," so a distinct mode
would be redundant surface. Precise semantics:

- `after_sequence` is an **exclusive lower bound**: the iterator yields only events
  whose `sequence` is strictly greater. `0` yields the whole run when the first
  retained event is `1`; it must never be treated as expired solely because the
  oldest retained event is `1`.
- When a cursor expires and the transport reports `earliest_available_event_id = E`,
  a client resuming via this exclusive cursor must use `after_sequence = E - 1`
  (equivalently, `Last-Event-ID: E-1`) to receive event `E`.
- The `Last-Event-ID` HTTP header maps directly: `Last-Event-ID: N` →
  `after_sequence=N`; a first connection with no header → `after_sequence=0`. (The
  header↔parameter mapping and its wire rendering are owned by 0008.11; this
  contract only defines the parameter's meaning.)
- The iterator **tails a live run** — it yields events as they are journaled and
  completes once the terminal (`done`/`error`) event has been delivered. A cursor
  at or beyond `last_sequence` simply yields nothing further until new events
  arrive (not an error).

The one hard case is a **cursor that has rotated out**. The event journal is
append-only and rotates in 1 MiB segments (0008.5), so the oldest events can be
compacted away. If `after_sequence` precedes the oldest retained event,
`read_events` **raises a typed `EventCursorExpiredError`** — it must **never
silently skip** the gap and resume at the oldest available event, because the
caller would then believe it has a complete stream. This error is deliberately
*distinct from `RunError`*: the run itself may be perfectly healthy (even still
running) — only the read cursor is unsatisfiable.

This is safe precisely because of the Q1 principle that **the terminal
`RunStatus.result` is the authoritative, complete answer** and the event stream is
only a *lossy live view*. A client that hits `EventCursorExpiredError` always has a
guaranteed recovery: call `get_run` and read `result.content`. Correctness never
depends on the event stream being replayable end-to-end.

> **Cross-cutting impact** (flagged only — those sub-FRD bodies are *not* edited here):
> - [0008.5](0008.5-controller-sandbox-transport-and-protocol.md) owns the journal
>   rotation/retention policy that decides *how far back* a cursor stays valid; this
>   contract defines behavior for whatever window exists, including raising

> - [0008.11](0008.11-http-api-sync-async-streaming.md) owns the `Last-Event-ID`

### Capability boundary: backend vs harness (resolves open question 4)

Three things in this design carry the word "capabilities"; only the first two
exist, and **v1 adds no third**:

| Concept | Owner | What it is |
| --- | --- | --- |
| `AgentCapabilities` | today's `registration/capabilities.py` | the resolved *concrete tool bundle* for one agent (filtered user/MCP tools, skills, web-request) — part of "who the agent is", bound at registration |
| Harness capability set | [0008.7](0008.7-harness-compatibility-and-conformance.md) | the typed set of *agent-features* the harness can provably deliver; drives fail-closed admission |
| Backend capability descriptor | — | would describe *transport/lifecycle* properties of a backend — **not introduced in v1** |

Decision for v1: **capability negotiation is entirely a harness concern (0008.7);
0008.1 introduces no backend capability descriptor.** v1 ships exactly two backends
(`in_process`, `aca_sandbox`) and one harness (MAF), and the controller already
knows which backend it wired at registration. So the two or three behavioral
differences that matter — whether the 180 s sync cap applies, whether `Prefer:
respond-async` is accepted, whether a replayable event journal exists — are
resolved directly from the selected provider, not negotiated. A typed, versioned
descriptor only pays off with a *third, a-priori-unknown* transport, which Decision
13 (defer Host integration) and Decision 34 (MAF-only) keep out of v1. Adding it now
would be exactly the premature generalization the honest-critique already warns
against ("the surface is only proven against two implementations").

The one real v1 case where a harness is *not* uniformly capable — MAF-in-process
supports `workflows.enabled`/nested Dynamic Sessions but MAF-in-ACA does not — is a
**harness** gap already handled by 0008.7's fail-closed startup (Decision 36), not
something a backend descriptor is needed for.

A backend may still expose a couple of plain properties (e.g. `supports_async`) as
an ordinary implementation detail so the controller need not string-compare the
provider; that is **not** a negotiated or versioned contract surface.

**Reserved extension.** A first-class backend capability descriptor is deferred
until a real third backend/transport or a non-MAF harness lands — the existing
reconsider trigger below ("a second harness/transport cannot fit the four-method
contract without leaking provider details up to handlers") is exactly that gate.

> **Cross-cutting impact** (flagged only): [0008.7](0008.7-harness-compatibility-and-conformance.md)
> owns the harness capability set and fail-closed feature admission; the controller
> reads *that* (not any backend descriptor) at registration.

## Alternatives considered & why the choice won

- **Execution location (Decision 1).** Considered: keep the MAF "brain" in
  Functions with only *tools* in a sandbox; run the *full* harness in a sandbox;
  or integrate directly into the Functions Host. Chosen: full harness in one
  sandbox per session. Splitting one logical turn across two compute boundaries
  (the parent's core motivation, §2) means a worker timeout, recycle, or client
  disconnect kills an agent loop that could otherwise keep running; a single
  owned compute boundary removes that split. A *Human* made this call.
- **Functions role (Decision 2).** Considered: Functions as the agent runtime, a
  dumb byte proxy, or an authenticated controller. Chosen: authenticated
  controller. A dumb proxy is explicitly rejected because the controller must
  authorize *every* session and run lookup and must never pass a
  caller-controlled sandbox identifier straight to the data plane (parent §4.2).
  Decided by *Human + Agent*.
- **Existing behavior (Decision 12).** Considered: replace the current runner, or
  add an opt-in backend. Chosen: opt-in — `in_process` stays default so existing
  apps are byte-for-byte unaffected and the preview dependency stays quarantined.
  Decided by *Agent*.
- **Host integration (Decision 13).** Considered: make it a P0, build it in
  parallel, or defer. Chosen: defer until the runtime-level contract is proven
  and host-team investment is justified. Decided by *Human + Agent*.

## Honest critique

**Strengths.** A narrow provider-neutral interface is the right lever: it lets
the risky preview dependency live behind a boundary the rest of the code never
sees, keeps the default path untouched, and makes "sync = wait on a run" a clean
unifying idea. Refusing the "dumb proxy" framing is what makes the whole security
story (ownership, tamper-evidence) possible downstream.

**Risks / assumptions.**
- The `AgentExecutionBackend` surface is only proven against two very different
  implementations (in-process and one specific ADC transport). A third harness or
  transport could reveal that the four-method shape is too narrow (e.g. no
  first-class notion of resume, health, or partial results).
- "The controller is lightweight but security-critical" is a tension: as more
  authorization, tamper-checks, and reconciliation land on it (sibling sub-FRDs
  0008.3, 0008.12), "lightweight" may stop being true, which is partly what
  Decision 13's deferral is betting against.
- Deferring Host integration (Decision 13) keeps routing in Python; if per-turn
  overhead or scale limits show up, that deferral may need revisiting sooner than
  expected.

**Reconsider triggers.** Revisit if: a second harness/transport cannot fit the
four-method contract without leaking provider details up to handlers; the
controller's per-request work grows past what a plain Function invocation should
do; or measured routing overhead justifies the Host binding that Decision 13
parked.
