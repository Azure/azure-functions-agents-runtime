# FRD 0008.7 — Harness compatibility & conformance

> Sub-FRD of [FRD 0008](0008-aca-sandbox-session-runtime.md). It re-expresses,
> in plain language, one self-contained decision area from the reviewed parent.
> It changes no technical decision. Status: **Finalized** (larohra-approved; the
> parent overview and remaining sub-FRDs flip together at the whole-FRD sign-off).

## What this is and why it matters

A **harness** is the engine that actually runs an agent: it calls the model, runs
the reasoning loop, invokes tools, loads skills, and emits events. Today the
runtime has exactly one harness — the **Microsoft Agent Framework (MAF)**, an SDK
running in-process. Moving execution into an **ACA Sandbox** (an isolated Azure
Container Apps container) tempts a bigger change: swapping in a different harness
(for example the Copilot CLI). This area deliberately says *no* to that for v1.

The decision: v1 **relocates MAF unchanged** and must *prove* it behaves
identically to today's in-process runner via a **conformance suite** (recorded
"golden traces" that the sandbox version must match). It also defines *three
separate contracts* so future harnesses can be added later without redesign, and
it makes the system **fail closed** — refuse to start — whenever an agent needs a
feature the selected harness cannot provably deliver. There is never a silent
downgrade or a quiet fallback to the in-process backend.

## Decisions this sub-FRD owns

- **Decision 34 — V1 harness.** Ship **MAF only** inside ACA for v1; compute
  relocation and harness replacement are separate changes. MAF must pass the
  conformance suite (parity with today's runner) first.
- **Decision 35 — Integration layers.** Split the integration into three contracts
  — a harness-neutral **runtime wire protocol**, **library adapters** (for
  in-process SDK harnesses like MAF), and a **process shim** (for CLI/process
  harnesses) — and version *capabilities* independently of the *protocol*.
  *(v1 refinement, 2026-07-22 — Human: to avoid version sprawl, v1 uses a **single
  joint `protocol_version`** that covers both the wire framing **and** the
  capability set; splitting them into independent version numbers is deferred until
  a real need appears. This narrows the parent Decision 35 phrase "independently of
  protocol version" for v1 — flagged for reconciliation in the master log, which is
  parent-owned.)*
- **Decision 36 — Unsupported MAF features on ACA v1.** **Fail startup** for
  `workflows.enabled` or nested Dynamic Sessions code-interpreter use with the ACA
  backend, until explicit compatibility designs land. No silent fallback.
- **Decision 37 — Non-MAF harness support.** Other harnesses require *separate*
  FRDs and conformance gates; FRD 0008 makes no support claim for them.

### The three contracts and capability negotiation (parent §4.5, second half)

1. **Sandbox Runtime Protocol** — the harness-neutral file/event contract (request
   envelope, status/result, monotonic events, cancellation, checkpoints, manifest,
   protocol version). This is the wire; it does not care *which* harness runs.
2. **Library Harness Adapter** — a Python interface for in-process SDK harnesses.
   The v1 **MAF adapter** wraps existing `runner.py` behavior and recreates network
   clients after resume.
3. **Process Harness Shim** — a *future* translator for CLI/process harnesses. It
   launches a pinned process, converts stdout/native events into the runtime event
   vocabulary, maps exit codes to the common error contract, and implements
   cancellation. A CLI is never treated as a Python adapter.

The sandbox **manifest advertises a typed capability set** (instructions, two-turn
history, plain tools, MCP, skills, workflows, **subagent delegation**, streaming
fidelity, structured output, reasoning events, tool-call records, cancellation,
checkpoints, observability — "subagent delegation" being the capability owned by
sibling 0008.13), carried under the **single `protocol_version`** (v1 does not give
capabilities a separate version — see the Decision 35 refinement above).
**Registration fails closed** before a session is created if an
agent's *resolved* features exceed the selected harness's capabilities — naming
the unsupported feature. Two governance rules make fail-closed *safe*: (i) each
resolved agent feature maps to a capability name via a **total** feature→capability
map, so a feature with **no enumerated capability is treated as unsupported**
(rejected as "unrecognized capability"), never passing by omission; and (ii) a
capability may not be advertised as *supported* unless the conformance suite has a
**golden trace exercising it** (as subagent delegation already does — parent
Decision 45). Two features are rejected at startup on the ACA backend, for
*different* reasons. **Dynamic Workflows** — an *agent-runtime* feature (not a MAF
feature) that registers tools dynamically during a run and promotes them into a
Durable Functions **orchestrator** run — is rejected **pending a compatibility
design** (delegated to sibling
[0008.14](0008.14-dynamic-workflows-aca-compat.md); this sub-FRD only owns the
**fail-closed gate**, Decision 36, not the workflows compatibility design). The
**nested Dynamic Sessions `execute_python` tool** is rejected for a *permanent,
by-design* reason: that tool exists to let the *in-process* runtime offload code
execution to a remote Dynamic Session, but in ACA mode the **sandbox itself is the
code-execution environment**, so nesting a Dynamic Session inside it is redundant.
It is therefore **not-applicable / superseded in this mode**, not a deferred gap —
no compatibility design is expected. *(Rationale refinement to parent Decision 36,
2026-07-22 — Human: the `execute_python` half is "superseded by native sandbox
execution," not "pending a design." The startup rejection is unchanged; flagged for
the master log, which is parent-owned.)*

The **conformance suite** captures golden observable traces from today's local MAF
runner and requires the sandbox MAF adapter to stay **core-behavior compatible** —
*not byte-identical*. Comparison is **normalized/semantic**: it checks event
**type + ordering + presence of key fields + terminal status** across a small core
scenario set (~8–12): instructions/model selection, two-turn history continuity,
plain/MCP/skill tool calls, event names/ordering, structured input/output success
*and* failure, timeout and mid-run cancellation, and error status/body contracts.
**Model-dependent content is excluded** from the diff — reasoning text, exact
wording, token-by-token streaming timing, and provider-specific metadata are *not*
asserted, only that reasoning/tool-call records appear where the provider emits
them. Traces are **captured once per baseline** (re-baselined only on an
intentional behavior change or `protocol_version` bump) and **verified every CI
run**. Input-schema and post-run output validation stay in the *controller*, so
structured-output enforcement is consistent across any future harness. This keeps
the parity claim in Decision 34 as **"same core behavior," not "identical
traces,"** so the suite stays cheap to maintain and resilient to model/provider
drift.

## Alternatives considered & why the choice won

- **V1 harness (Decision 34).** Considered: switch straight to a non-MAF harness;
  support an arbitrary image adapter; or MAF-parity-first. Chosen: MAF-only with
  conformance parity — changing *where* MAF runs and changing *which* harness runs
  are two risks, and doing both at once makes failures impossible to attribute.
  *Agent reviewers.*
- **Integration layers (Decision 35).** Considered: one generic Python adapter; or
  the three-way split (wire protocol + library adapter + process shim) with
  independent capability versioning. Chosen: the three-way split — a single
  adapter would wrongly assume every harness is an in-process Python SDK, which a
  CLI is not. *Agent reviewers.*
- **Unsupported features (Decision 36).** Considered: silent fallback; support
  nested Dynamic Sessions + remote workflow callbacks now; or fail startup. Chosen:
  fail startup — a silent fallback would quietly drop tools, workflows, schema
  validation, or event fidelity a user is relying on. *Agent reviewers.*
- **Non-MAF harnesses (Decision 37).** Considered: imply support from a custom
  image; include them in v1; or require separate reviewed adapters. Chosen:
  separate FRDs + conformance gates — image compatibility is not a support
  contract, and (per parent §4.5) e.g. Copilot CLI lacks a verified MAF-equivalent
  library/event/session API and has sharing/exfiltration flags that must be denied.
  *Agent reviewers.*

## Honest critique

**Strengths.** "Change one variable at a time" (relocate MAF, don't swap it) is
disciplined engineering, and golden-trace conformance turns "behaves the same" from
a claim into a test. The three-contract split is genuinely forward-looking: it
names the CLI-is-not-a-library trap before anyone falls into it. Fail-closed with a
named unsupported feature is the right anti-footgun default.

**Risks / assumptions.**
- **Golden traces can ossify or flake.** Observable traces (event names/ordering,
  reasoning metadata "where the provider emits it") depend on model/provider
  behavior that drifts; the suite risks being brittle or, worse, being loosened
  until it stops catching regressions. *(Mitigated — the suite is now
  normalized/semantic and excludes model-dependent content; see Open questions.)*
- **Capability enumeration completeness.** Fail-closed is only as safe as the typed
  capability list is *complete*. A feature nobody thought to enumerate could slip
  through as "supported" by omission. *(Mitigated — a **total feature→capability
  map** makes an unenumerated feature fail closed as "unrecognized," not "supported";
  see Open questions.)*
- **Three contracts, one implementation.** The wire/library/shim split is validated
  only by MAF (a library adapter). The process-shim contract is unexercised, so its
  fitness is theoretical until a real CLI harness tests it (Decision 37 defers
  that).
- **Workflows/Dynamic-Sessions rejection is a real feature gap.** Users combining
  ACA sessions with Dynamic Workflows or `execute_python` simply can't in v1;
  whether that combination is commonly wanted is an open product question. *(Dynamic
  Workflows compatibility is now under dedicated analysis in sibling
  [0008.14](0008.14-dynamic-workflows-aca-compat.md).)*

**Reconsider triggers.** Revisit if: golden traces prove too brittle to maintain
(need a more semantic conformance definition); a real non-MAF adapter reveals the
wire protocol or process-shim contract is under-specified; or user demand for
ACA + Workflows / ACA + Dynamic Sessions forces those compatibility designs
forward.

## Open questions / iterate here

- **Golden-trace robustness.** *(Resolved, 2026-07-22 — Human.)* Comparison is
  **normalized/semantic**, not exact-match: assert event type + ordering + key-field
  presence + terminal status over a small core set (~8–12 scenarios); **exclude**
  model-dependent content (reasoning text, wording, streaming timing, provider
  metadata). Traces are **captured once per baseline** and **re-baselined only** on an
  intentional behavior change or `protocol_version` bump; verification runs every CI.
  This deliberately relaxes Decision 34 parity to **"same core behavior," not
  "identical traces,"** so the suite is cheap and drift-resistant. Broader
  robustness tooling (auto re-baselining, richer semantic diff) is v2+.
- **Capability set governance.** *(Resolved, 2026-07-22 — Human.)* **Single
  version** — the capability set is carried under the one `protocol_version`; no
  separate capability version in v1 (avoids version sprawl; narrows parent Decision
  35 — flagged for the master log). Completeness is guaranteed by a **total
  feature→capability map**: an unrecognized/unenumerated resolved feature **fails
  closed** ("unrecognized capability"), never "supported by omission." And a
  capability is only advertised *supported* once a **conformance trace exercises
  it** (per parent Decision 45). An independent capability version can be split out
  later if a real need appears.
- **Process-shim validation.** *(Direction, 2026-07-22 — Human.)* The shim
  contract has no v1 exerciser (MAF is a library adapter). Rather than spike it
  under this FRD, its validation is **deferred to the first non-MAF harness FRD**
  (per Decision 37), which must spike-exercise the shim to confirm the wire
  protocol + process-shim contract before that contract is frozen. Not a v1
  blocker.
- **ACA + Workflows / + Dynamic Sessions.** These are hard-rejected in v1.
  **Dynamic Workflows** compatibility analysis is owned by sibling
  [0008.14](0008.14-dynamic-workflows-aca-compat.md) (**drafted 2026-07-22**). Its
  key finding **reframes the problem**: the Durable orchestrator wiring in `app.py`
  is gated on front-matter `workflows.enabled` alone, **never on the execution
  backend** — so the controller **already runs a live, fully-wired orchestrator next
  to the sandbox** for any workflows project. The gap is therefore **"no bridge
  yet," not "no orchestrator at all"**: what's missing is a path from the sandboxed
  MAF agent's tool-call boundary (only 5 named async workflow tools) to that
  already-running controller orchestrator. 0008.14's leading candidate —
  **controller-side orchestration** (keep registration as-is; replace the 5 tool
  handlers with thin sandbox-side proxies) — was deep-dived (2026-07-22) and found to
  ride on **already-proven 0008.5 primitives, not new transport**: a proxy tool
  appends an additive typed `workflow_tool_call_requested` record to its own
  `events.jsonl` journal; the controller's existing poll loop services it against its
  live `durable_client` and writes the result back via the existing
  `inbox/{run_id}.json` direction; the sandbox `await` resolves via a **local file
  poll** — **no new egress/ingress** ([0008.9](0008.9-network-egress-and-obo.md)
  untouched), and it does **not** reopen 0008.5's rejected gRPC option (no ingress
  port, stateless poll). Recomputed latency ~1–3s per *control-plane call* (not per
  DAG step). **Narrowed open dependency ([0008.5](0008.5-controller-sandbox-transport-and-protocol.md)'s
  call, not ours):** whether this rides as an *unversioned convention* on the existing
  file layout or warrants a *formal 7th transport verb*.
  **Decision 36 is unchanged** — 0008.14 confirms the fail-closed gate is still the
  correct v1 posture, and its "until explicit compatibility designs land" phrasing
  already anticipates this analysis; nor does it change this sub-FRD's negotiated
  capability set (workflows stays fail-closed on ACA v1 — the bridge is future design).
  The **nested Dynamic Sessions `execute_python`**
  rejection is now **resolved as not-applicable in ACA mode** (2026-07-22 — Human):
  the sandbox is itself the code-execution environment, so a nested remote Dynamic
  Session is redundant/superseded — the startup rejection is permanent-by-design, not
  a deferred gap, and no compatibility design is expected.
- **Protocol-version lifecycle & fleet coordination.** *(Ownership accepted, then
  re-scoped 2026-07-22 — Human/0008.6.)* Routed here from
  [0008.6](0008.6-sandbox-packaging-image-and-content.md) /
  [0008.5](0008.5-controller-sandbox-transport-and-protocol.md) because this sub-FRD
  owns what `protocol_version` (and the capability set) *mean*. **v1 re-scoping:
  larohra scoped v1 to Path 1 only** (Run-From-Package zip), whose captured
  `.python_packages` carries the **per-session runtime/MAF version** (the image bakes
  **no MAF**) and which produces **no committed image** — so there is **no
  committed-image version-coupling in v1**, and the **fleet bump-orchestration /
  re-commit-coordination role is DEFERRED WITH Path 2**, not a v1 deliverable.
  **Resolved under drain-on-deploy (Round-4, parent master-log row 70 — larohra):**
  cross-epoch `protocol_version` compatibility is a **non-issue in v1**. Because a
  content redeploy **drains** any session still on the old content digest (see the
  epoch/drain item below), the controller and every live sandbox are **always on the
  same epoch** — there is never a live cross-epoch pairing to reconcile.
  `protocol_version` **conceptually belongs to the captured runtime** (it travels with
  the per-session `.python_packages`, consistent with Model-1's "no MAF baked"). The
  machinery for *spanning* epochs — **persisting per-epoch schemas,
  additive/backward-compatible protocol evolution, and a supported-version window** —
  is therefore a **v2 concern**, and it **supersedes the earlier provisional
  "Lazy / latest-as-truth / no-window + `ensure_ready` as version policy" framing**,
  which had assumed live sessions could span a redeploy (drain-on-deploy removes that
  premise). The **Path-2 committed-image bump-orchestration** (0008.7 decides bump →
  0008.6 re-primes/commits → 0008.12 drains/GCs → 0008.5 `ensure_ready` backstop)
  remains **deferred with Path 2**.
- **Where does structured-output validation truly live?** *(Resolved, 2026-07-22 —
  grounded in source.)* It already lives in the **controller / HTTP request-handler
  layer** (`registration/_handlers.py`), **not** in the harness: input is validated
  by `validate_request_body()` → `jsonschema.validate(body, resolved.input_schema)`
  *before* the agent runs (HTTP 400 on failure); the JSON response-format
  *instructions* are injected controller-side by `_response_format_instructions()`;
  and output is validated post-run by `jsonschema.validate(parsed,
  resolved.response_schema)` (HTTP 500 on failure). The MAF runner only receives a
  prompt and returns text — it owns none of the schema enforcement. **Locked rule:**
  the **controller is the authoritative validation gate** (input pre-dispatch, output
  post-run); a harness may do *best-effort* output shaping but never owns the
  guarantee. This is not a new design — it **codifies today's behavior**, and it maps
  cleanly onto ACA: when the harness relocates into the sandbox, `_handlers.py` stays
  controller-side, so validation does **not** move and enforcement is identical across
  any future harness. It is a **feature/runtime** concern (per-run), not deployment.
  **Invalid-output terminal semantics (Round-3 resolution, 2026-07-24 — larohra):** a
  run that *completes* but produces output that **fails** schema/conformance
  validation is a **terminal `failed` run — never `succeeded` with a bad payload**.
  The controller marks it `failed` with a **typed validation `RunError`** (fault
  domain = harness/app). **No new status enum is introduced** — it reuses
  [0008.12](0008.12-lifecycle-failure-and-reconciler.md)'s `failed` terminal state,
  and [0008.11](0008.11-http-api-sync-async-streaming.md) surfaces it via the standard
  status model (async reads → 200 + typed error body; sync path → 5xx, matching the
  existing HTTP-500 behavior above). Conformance covers this explicitly: the
  structured-output *failure* scenario asserts a `failed` terminal outcome, not a
  successful run carrying an invalid payload.
  **Per-session epoch handling — drain-on-deploy (Round-4 reconciliation, parent
  master-log row 70 — larohra; supersedes the earlier retain-schemas approach):**
  validation always runs against the **current epoch's schemas**
  (`resolved.input_schema` / `resolved.response_schema`); the controller does **not**
  retain or resolve an old epoch's schemas. A session whose **captured-content
  `digest` ≠ the controller's current content `digest`** is **drained** — its
  in-flight run gets a grace period then is abandoned, the session is **tombstoned**,
  and subsequent calls get **`410`** (drain / tombstone owned by
  [0008.12](0008.12-lifecycle-failure-and-reconciler.md), surfaced per
  [0008.11](0008.11-http-api-sync-async-streaming.md)) — it is **not** validated
  against retained schemas. This **removes the earlier "retain the old digest's schema
  while the session is live" machinery** (`801bc93` / `17e5861`): under drain-on-deploy
  a session **never spans a content redeploy**, so there is no old-epoch schema to
  keep. **The captured-content `digest` remains the epoch stamp used to DETECT the
  mismatch**, persisted as `(digest_kind, digest)` on the session row
  ([0008.3](0008.3-state-store-and-tamper-evident-trust.md), `61b7dc4`). Drain triggers
  on a **content-`digest` change (a real redeploy), NOT on a `generation`/instance
  change or suspend/resume** — a **same-content rebind does not drain** (digest
  unchanged), preserving the earlier "pin to the `digest`, not the `generation`"
  distinction. Per [0008.3](0008.3-state-store-and-tamper-evident-trust.md)'s
  definitive model (`7c66c07`), a live session's content `(digest_kind, digest)` is
  **fixed at creation and immutable for the session's lifetime** — so a content change
  is a **new session** (via drain-on-deploy), never an in-session content bump — while
  the **`generation` identifies only the backing (instance + disk), never content**; a
  `generation` advance is **v2-only and orthogonal to the epoch** (it does not change
  the content digest, so it does not change the validation epoch). Detection is a
  digest **equality** check, so it works for both the v1
  `funcs_zip` SHA-256 digest and a future Path-2 `aca_image` disk-id digest — no
  content hash is required for mismatch detection. (Cross-referenced; no edits to
  sibling bodies.)
