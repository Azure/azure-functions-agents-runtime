# FRD 0008.11 — HTTP API: sync default, explicit async, chunked streaming

> Sub-FRD of [FRD 0008](0008-aca-sandbox-session-runtime.md). It re-expresses,
> in plain language, one self-contained decision area from the reviewed parent.
> It changes no technical decision. **Finalized 2026-07-23 (Human sign-off).** All
> five open questions are resolved and aligned with the Finalized siblings
> [0008.2](0008.2-session-identity-ownership-concurrency.md) and
> [0008.5](0008.5-controller-sandbox-transport-and-protocol.md) and with
> [0008.7](0008.7-harness-compatibility-and-conformance.md) conformance;
> Decisions 3 / 19 / 25 are unchanged.

## What this is and why it matters

This is the part callers *see*: the HTTP endpoints, what they return, and how long
they wait. Moving the agent into an **ACA Sandbox** (an isolated Azure Container
Apps container) must not break today's simple request→answer chat, and it must add
a clean way to run work that takes longer than an HTTP request should stay open.

The design keeps `/chat` and `/chatstream` **synchronous by default** (same
response shapes as today), and lets a caller *explicitly* opt into asynchronous
execution with the standard `Prefer: respond-async` header. Async returns
immediately with a `run_id` and management URLs the caller can poll. Two hard
limits shape everything: Azure Functions enforces a **230-second** maximum HTTP
response window, so the controller caps *synchronous* waits at **180 seconds** and
reserves the rest for clean cancellation/response. And because the v1 transport is
a polled journal (sibling 0008.5), streaming is **replayable chunks** with roughly
2-second visibility — not today's token-by-token stream.

## Decisions this sub-FRD owns

- **Decision 3 — Public run behavior.** Preserve **sync/streaming defaults**;
  `Prefer: respond-async` opts into long-running execution. (Neither async-only nor
  sync-only.)
- **Decision 19 — Synchronous HTTP budget.** Cap total sandbox-backed HTTP wait at
  **180 seconds**; longer work must use `respond-async`.
- **Decision 25 — Experimental v1 streaming guarantee.** Accept **replayable
  chunks** with ≤ 2-second p95 visibility; preserve event semantics; upgrade
  transport later for token-level latency.

### The API surface (parent §4.12)

Existing endpoints are unchanged by default:

```http
POST /agents/{slug}/chat
POST /agents/{slug}/chatstream
```

Without a preference header they wait for the sandbox run and preserve today's
success/error shapes and `x-ms-session-id`. The controller's **total** HTTP wait
budget is 180 s from admission — covering sandbox lookup/create/resume, package
verification, *and* run execution. (Functions' 230 s ceiling applies regardless of
`functionTimeout`; the remaining ~50 s is reserved for cancellation + delivery.) An
authored agent `timeout` above 180 s is honored *only* for explicit async.

Explicit async uses the standard preference header and returns `202` with URLs:

```http
POST /agents/{slug}/chat
Prefer: respond-async
x-ms-session-id: <optional existing session>
Idempotency-Key: <optional caller key>
```
```http
HTTP/1.1 202 Accepted
Location: /agents/{slug}/sessions/{session_id}/runs/{run_id}
Retry-After: 2
x-ms-session-id: <session_id>
{ "session_id":"...", "run_id":"...", "status":"accepted",
  "status_url":".../sessions/{session_id}/runs/{run_id}",
  "result_url":".../sessions/{session_id}/runs/{run_id}/result",
  "events_url":".../sessions/{session_id}/runs/{run_id}/events",
  "cancel_url":".../sessions/{session_id}/runs/{run_id}/cancel" }
```

Management routes (session-scoped — the run row key is
`run:{session_id}:{run_id}`, so `run_id` alone is not a Table locator):

```http
GET  /agents/{slug}/sessions/{session_id}/runs/{run_id}           # status (state + error)
GET  /agents/{slug}/sessions/{session_id}/runs/{run_id}/result    # terminal result, or 410
GET  /agents/{slug}/sessions/{session_id}/runs/{run_id}/events    # SSE; accepts Last-Event-ID
POST /agents/{slug}/sessions/{session_id}/runs/{run_id}/cancel
```

**Status-code model (industry-standard long-running-operation shape).** The HTTP
status code describes the **request's** health; the **run outcome** is a field in
the body (`state`, plus an `error` object on failure). Concretely:

- **Sync unary path** (`/chat` — the response *is* the result): `200` on
  success; `4xx` for caller/input fault; `5xx` for harness/app fault; `504` for the
  authored-`timeout` breach (per the 180 s model above).
- **Streaming path** (`/chatstream`): failures are HTTP status codes **only before
  the SSE stream starts** (i.e. before `200` + SSE headers are flushed) — e.g. a
  `4xx` input fault or an auth `401`/`403`. **Once the stream has started, an HTTP
  status can no longer be changed**, so a run failure, harness fault, or
  authored-`timeout` breach is delivered **in-band as a typed terminal error /
  timeout SSE frame** (a named `error` event carrying the same `error` object /
  `state` the unary path would return), followed by stream close. Clients must treat
  a terminal `error` event — not an HTTP code — as the failure signal on this path.
- **Async `/status` and `/result`**: `200` whenever the run is **readable**,
  carrying `state` and — on a failed run — an `error` object. A *failed run* is
  **not** a `5xx`: the read succeeded, the run didn't. Request-level failures still
  use codes: `404` unknown run, `410` evicted/tombstoned result, `401`/`403` auth,
  `409` conflict. `/result` returns the terminal result payload, or `410` when the
  result has been evicted (0008.5) or the session is tombstoned.

Invalid harness output settles the run to terminal `failed` (rule owned by
[0008.7](0008.7-harness-compatibility-and-conformance.md)); 0008.11 simply surfaces
`failed` per the model above — reusing 0008.12's `failed`, no new enum value.

Every route **reapplies the same authentication every other Functions endpoint
uses** — the App Service / Functions Host auth gate (function keys, or Easy
Auth / Entra) — and re-runs the session-ownership check. There is **no
ACA-specific Entra precondition**, and ownership may be **app-scoped**
(`function_app`) or **user-scoped** (`entra_user`) exactly as
[0008.2](0008.2-session-identity-ownership-concurrency.md) (Finalized) defines;
possessing a `run_id` grants no access. The controller still **recomputes the
owner partition from the authenticated `OwnerContext`**; the URL `session_id` is
only a row-key component, **not an authorization claim**. Sync calls **do not
silently become async** in v1: if they exceed the 180 s budget the controller
requests
cancellation and returns **504**. `/chatstream` preserves the semantic event
vocabulary but, under the polled transport, emits replayable chunks at ≤ 2 s p95
rather than token-by-token (token-level latency is a future
authenticated-transport upgrade); the events route additionally surfaces a named
`snapshot-restart` control frame (see **Resolved refinements**).

## Sync budget breakdown & fast-fail (resolves OQ#1)

Decision 19's 180 s cap is split into a **fixed setup sub-budget** plus a
**guaranteed execution floor**, so a slow cold start fails fast instead of burning
the whole window:

- **Setup sub-budget — 30 s.** Covers authoritative state-row lookup, sandbox
  create-or-resume, and package-verify / `ensure_ready`
  ([0008.5](0008.5-controller-sandbox-transport-and-protocol.md) /
  [0008.6](0008.6-sandbox-packaging-image-and-content.md)). If readiness is not
  reached within 30 s the controller **fast-fails to `504` before any run is
  launched** — the caller learns at ~30 s, not ~180 s, that setup (typically a
  cold start) is the bottleneck. No run exists to cancel; any partially-provisioned
  sandbox is reclaimed by [0008.12](0008.12-lifecycle-failure-and-reconciler.md)'s
  reconciler/reaper, not held open by the failed request.
- **Execution floor — ≥ 150 s.** Whatever setup does not consume is handed to the
  run, with a guaranteed floor of 180 − 30 = **150 s**; a warm 5 s resume leaves
  175 s. Because delegated subagents run **in-process within the same run**
  ([0008.13](0008.13-subagent-delegation-compat.md)), this whole-run budget covers
  the coordinator plus every nested delegated call — there is **no per-subagent
  reset**; per-delegate budget attribution is a non-v1 observability follow-up
  owned by 0008.13.
- **Overall 180 s wall.** Execution runs until the total admission-to-now budget
  reaches 180 s; on breach the controller requests cancellation and returns `504`,
  reserving the remaining headroom under the platform 230 s ceiling for clean
  cancellation + response delivery.

The two `504`s are **distinguishable** (feeds OQ#4): a **setup-timeout**
(`reason: setup_deadline_exceeded`) signals a cold-start / provisioning stall,
while an **execution-timeout** (`reason: run_deadline_exceeded`) signals the turn
itself is long. The `504` `reason` is the *transport-window* cause; the run's
**terminal** label is separate and set by cause — `timed_out` when the authored
`timeout` watchdog fired, `canceled` when the 180 s sync cap forced a controller
cancellation of an otherwise-still-running turn (see **504 handling**). The
30 s / 150 s split is a **tunable default**, not a wire
contract; only "a setup fast-fail exists, and the two `504` reasons are distinct"
is contractual.

## 504 handling & client guidance (resolves OQ#4)

Both timeouts return `504` with a **typed hint** and **no silent server-side
degrade to async** (Decision 3 holds — sync never becomes async on its own). The
response carries a machine-readable body — `{ "error": "…", "reason":
"setup_deadline_exceeded" | "run_deadline_exceeded", "retry_with":
"respond-async" }` — plus an advisory header (`x-ms-retry-with: respond-async`).

First-party SDKs **surface a typed error** (carrying `reason`) rather than
swallowing the `504`, and expose an **opt-in** async-retry helper — they do **not**
auto-retry silently, because re-issuing as async changes the response shape (a
`run_id`, not an answer) and could duplicate work. Retry semantics differ by
reason, mirroring the retry-after-abandon rule above:

- **`setup_deadline_exceeded`** — no run was launched, so a plain retry is clean
  and **may reuse the same `Idempotency-Key`** (a sync retry may now hit a warm
  sandbox; or switch to `respond-async` for provisioning-heavy sessions).
- **`run_deadline_exceeded`** — a run existed and has reached a terminal state, so
  its slot is briefly held while it settles; a re-issue must **rotate to a fresh
  `Idempotency-Key`** and wait for the slot to free (a too-eager resubmit gets the
  flat `409 active_run_exists` → cancel-then-submit). The **terminal label depends
  on the cause**:
  - **Authored-`timeout` watchdog fired** (`timeout ≤ 180 s` and the run-level
    watchdog tripped) → terminal **`timed_out`** (with its typed `RunError`). This
    is the *only* "timeout" terminal.
  - **180 s sync-wait cap elapsed** while the run was still within a **longer
    authored `timeout`** → the controller **cancels** the run → terminal
    **`canceled`** (this is a genuine controller cancellation; the run could have
    kept going under `respond-async`).

  Either way the opt-in helper encapsulates the recovery: await slot release, rotate
  the key, re-submit with `Prefer: respond-async` (which runs up to the full
  authored `timeout` instead of the 180 s sync cap).

A poll-only async caller never sees a `504` at all (it got its `202` immediately),
which is the cleanest path for provisioning-heavy or long turns.

## Alternatives considered & why the choice won

- **Public run behavior (Decision 3).** Considered: async-only; sync-only; or sync
  by default with explicit async. Chosen: sync/stream default + `Prefer:
  respond-async` — async-only would break every existing simple caller, and
  sync-only can't support work that outlives an HTTP request. *Human.*
- **Sync HTTP budget (Decision 19).** Considered: use the authored timeout up to
  900 s; use the platform maximum; or a bounded controller cap. Chosen: a 180 s cap
  under the 230 s ceiling — pushing to the platform max leaves no room for clean
  cancellation/response and risks the host killing the request mid-flight. *Agent
  reviewer.*
- **Streaming guarantee (Decision 25).** Considered: token-level parity;
  replayable chunks; or disable streaming. Chosen: replayable chunks at ≤ 2 s p95,
  preserving event semantics, with a later transport upgrade — token-level parity
  is impossible over the polled-journal transport chosen in 0008.5, and disabling
  streaming would regress the API. *Human.*

## Honest critique

**Strengths.** Preserving the default sync/stream contract means zero migration for
existing callers — the single most important compatibility property. Reusing the
*standard* `Prefer: respond-async` / `202 + Location` / `Retry-After` pattern is
idiomatic HTTP rather than a bespoke protocol. Re-checking auth on every route and
making `run_id` non-authoritative is the correct security posture. Explicitly
returning `504` (not silently degrading to async) keeps behavior predictable.

**Risks / assumptions.**
- **Streaming UX regression is real.** ≤ 2 s p95 chunk visibility is a noticeable
  downgrade from token-by-token for chat UIs; "we preserved event *names*" doesn't
  fully preserve the *feel*. This is an accepted experimental-v1 cost but a genuine
  product hit.
- **180 s is a hard wall inside a bigger budget.** The 180 s must cover
  create/resume/package-verify *and* execution. The setup sub-budget (30 s
  fast-fail) now guarantees a ≥ 150 s execution floor and surfaces cold-start
  stalls early, but the wall is still real: a turn needing ~160 s of thinking after
  25 s of setup exceeds 180 s and returns a (typed) `504`.
- **504-not-async can surprise callers.** *(Mitigated — see 504 handling.)* A
  client that didn't set `respond-async` still gets a hard 504, but it now carries
  a typed `reason` + "use async" hint, and first-party SDKs surface a typed error
  with an opt-in async-retry helper. Non-SDK callers must still read the hint.
- **Idempotency-Key semantics.** *(Resolved — see Resolved refinements.)* Scope is
  per-session with a bounded TTL; a same-key retry replays the existing run, a
  distinct submission earns the flat `409`, and a same-key/different-payload
  mismatch is a typed `422` — composed with 0008.2's Finalized one-active-run rule.

**Reconsider triggers.** Revisit if: the streaming downgrade proves unacceptable
for target chat UIs (accelerates the authenticated-transport upgrade in 0008.5);
cold-start + verification regularly pushes normal turns past 180 s (may force a
larger sync budget or faster create/resume); or callers frequently hit 504 because
they didn't opt into async (may need clearer client guidance or an opt-in
auto-async).

## Resolved refinements (sibling-aligned)

### Streaming replay depth & `snapshot-restart` (resolves OQ#2)

`GET /agents/{slug}/sessions/{session_id}/runs/{run_id}/events` accepts
`Last-Event-ID`. Replay is
guaranteed within the transport's retained window — the **last 16 × 1 MiB event
segments per run** (deletion-based compaction; bound and tunability owned by
[0008.5](0008.5-controller-sandbox-transport-and-protocol.md)). When a caller's
`Last-Event-ID` predates that window, the transport returns a typed
`snapshot-restart` control record (`reason: "last-event-id-evicted"`,
`earliest_available_event_id`, `authoritative: ["status.json","result.json"]`).
0008.11 surfaces it as a **named SSE event** (`event: snapshot-restart`) so an
`EventSource` client can `addEventListener('snapshot-restart', …)` and never
confuse it with a normal `message` frame. **Client contract:** on
`snapshot-restart`, reconcile from the run's status/result, then **reconnect with
`Last-Event-ID: E-1` when `earliest_available_event_id = E`** — **never a silent
gap and never skipping event `E`**. This is a cursor-eviction
condition on the streaming path *only*: the cursorless status/result reads never
emit it, so a **poll-only async caller is inherently safe**.

**Bounded connection lease.** The SSE endpoint is a **bounded connection lease**,
not an unbounded Function host request. Each event frame carries an `id:` equal to
its monotonic event sequence, and the stream emits heartbeat comments often enough
for clients and intermediaries to observe liveness. The controller gracefully
closes the stream before the Azure Functions HTTP ceiling (target before ~230 s),
after flushing any available event and heartbeat state; clients resume by
reconnecting with `Last-Event-ID`. A normal lease close is **not** cancellation and
does **not** change run state.

**Disconnect never cancels the run.** A client disconnect — whether the graceful
lease close above or an abrupt drop — **does not cancel the run**; the run keeps
executing and journaling, and the client re-attaches by reconnecting with
`Last-Event-ID` (cursor re-attach; `snapshot-restart` if the cursor rotated out).
The **only** things that cancel a run are an **explicit** `POST …/cancel` and the
controller's cancellation when the **180 s sync-wait cap** elapses (→ `504`,
terminal `canceled`). This is the canonical rule coordinated with
[0008.1](0008.1-execution-backend-and-controller.md): run liveness is decoupled
from connection liveness, so a dropped SSE stream or a closed sync socket never
kills in-flight work — it is resumable via the cursor or the async management
routes.

**Cross-layer mapping.** This SSE rendering is the HTTP surfacing of a single
lower-layer condition. On the `AgentExecutionBackend` seam
([0008.1](0008.1-execution-backend-and-controller.md)), the discrete
`read_events` call signals an evicted cursor as a typed error (0008.1's
`read_events` contract names it `EventCursorExpiredError` — see 0008.1
§"Event replay & cursor semantics"), recovered by re-reading authoritative state
via `get_run`. 0008.11 renders that **same**
condition on the streaming wire as the named `snapshot-restart` event
(`reason: "last-event-id-evicted"`); both resolve identically — reconcile from
`status.json` / `result.json`, then resume. They are one contract seen at two
layers, not two mechanisms.

### Result eviction → `410` (folds in the 0008.5 cross-cut)

A run's answer is durable only for a bounded post-terminal grace window; after
0008.5's reap, `get_result` returns `result-evicted`. 0008.11 surfaces this as
**HTTP `410 Gone`** on the result read, while the run's **terminal status remains
resolvable** via `GET /agents/{slug}/sessions/{session_id}/runs/{run_id}` (backed
by the cursorless
`get_status`, which never evicts). `410` is the **result-read** analogue of
`snapshot-restart` — a typed "the durable answer has moved / is gone" signal, not
a silent miss — while `get_status` remains **always-resolvable** (terminal status
survives in the Tables control record). Of the three read paths, only two can
signal absence: `read_events` → `snapshot-restart`, `get_result` → `410`;
`get_status` never does. **Result availability is a separate axis from terminal
status:** a run can be `succeeded` with `result_available=false` once its content
is reaped — the status read still returns `succeeded` while the result read returns
`410`. In the deep-post-reap corner these compose cleanly: a
`snapshot-restart` whose `authoritative` list points at `result.json` can coincide
with that result already evicted — the client still gets a coherent answer (status
resolves from Tables; the result read returns `410`). The status route surfaces
the transport/reconciler's terminal label **verbatim**, using the unified lowercase
status enum (`accepted` / `running` / `succeeded` / `failed` / `canceled` /
`timed_out` / `abandoned`) — including `abandoned` for
a run whose sandbox was lost and reconciled by
[0008.12](0008.12-lifecycle-failure-and-reconciler.md); 0008.11 does **not** rename
terminal states.

### Idempotency-Key contract (resolves OQ#3)

Aligned with [0008.2](0008.2-session-identity-ownership-concurrency.md) (Finalized)
so idempotency and the one-active-run `409` compose cleanly:

1. **Same submission, same key → replay, never `409`.** A retry carrying the same
   `Idempotency-Key` attaches to the existing run (idempotent replay). Sync returns
   the same in-flight/terminal result; async returns `202` with the same `run_id`
   and management URLs. This rides 0008.2's **fast-path resubmit reconciliation** —
   a resubmit whose sandbox is already dead clears the phantom slot rather than
   hitting a stale `409`.
2. **Distinct submission while a run is active → flat `409`.** A genuinely
   different submission returns the flat `409 Conflict` (typed error
   `active_run_exists`, naming the active `run_id`). The v1 escape hatch is explicit
   **cancel-then-submit** — no supersede/interrupt (Decision 6).
3. **Same key, different payload → conflict, not replay.** Returns **`422`**
   (`idempotency_key_conflict`). If `409` is ever reused for this case it **must**
   carry a distinct typed discriminator, so a client can tell "your key collides
   with a different request" apart from "a run is already active"; a **bare `409`
   for both is disallowed**.

Order of checks: **dedupe on `Idempotency-Key` first** (→ existing run); only a
distinct new submission reaches the one-active-run check (→ `409`). Key scope is
**per session** (`session_id` + key) for submissions to an existing session; a
session-creating submission scopes the key to the resolved **owner** for the dedupe
window. TTL is bounded. The sandbox-side idempotency boundary remains the
controller-generated `run_id` in the run envelope
([0008.5](0008.5-controller-sandbox-transport-and-protocol.md)).

**A key identifies one logical attempt (retry-after-abandon rotates the key).**
If a same-key resubmit targets a run that is non-terminal but whose sandbox is
dead, 0008.2's fast-path reconciles that run to terminal `abandoned` **first**,
then the idempotent replay returns that terminal outcome — the caller gets "your
run was abandoned," never a resurrected live run and never a stale `409`. So a
same key **always maps to the same attempt** and replays its terminal outcome once
resolved; **starting a fresh turn after an `abandoned` requires a new
`Idempotency-Key`**. Reusing the old key would only replay the `abandoned`
terminal, so retry-after-abandon is a client-side key rotation. This keeps
"dedupe-first, then one-active-run" unambiguous and stops replay from masking a
legitimate retry.

### Streaming conformance framing (resolves OQ#5)

The `/chatstream` event *vocabulary* is preserved; only *timing* degrades.
[0008.7](0008.7-harness-compatibility-and-conformance.md) conformance is
**normalized/semantic** — it asserts event **type + ordering + key-field presence
+ terminal status** and **explicitly does not assert token-by-token timing or
wording**. So chunked streaming (Decision 25) *passes* conformance: nothing in the
semantic vocabulary is lost over the polled journal. The only additions callers see
are the typed control signals above (`snapshot-restart` on the events path, `410`
result-eviction on the result path) — new signals, not missing events.
