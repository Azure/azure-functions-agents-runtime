## What this is and why it matters

An agent runs partly untrusted code (model-generated tool calls, author-supplied
tools) inside an **ACA Sandbox** (an isolated Azure Container Apps container). If
that code could freely reach the internet, it could exfiltrate prompts, secrets,
or data. **Egress** is the sandbox's outbound network traffic, and an **egress
proxy** is a gateway all outbound traffic must pass through — it can *block*
destinations by default and *inject* credentials into allowed requests so the
secret never sits in the sandbox's own memory.

This area sets the network and credential posture: **deny-by-default egress with
full traffic inspection, applied at sandbox creation** (there is no "open now,
lock down later" window); a preference order for how the sandbox authenticates to
allowed destinations — in v1 the sandbox is **identity-less** (no managed identity, no token
inside), so the **egress proxy injects credentials** into allowed requests and the **controller
delivers the content package** (the v1 model set by the 2026-07-24 Tier-A decision, superseding
the earlier Decision 56 mechanism); and a careful, much-misunderstood distinction — **a managed
identity is not user On-Behalf-Of (OBO)**. **OBO** is the OAuth flow where a
service calls a downstream API *as the actual signed-in user* (delegated), not as
itself. True OBO is deferred (to a follow-up FRD); the design only *reserves* a seam
for an external credential broker to do it safely later.

## Decisions this sub-FRD owns

- **Decision 10 — Egress posture.** Full-inspection, **default-deny** policy is
  **active before the harness executes**. "Allow then tighten" and "deny only after
  bootstrap" are rejected.
- **Decision 11 — OBO interpretation.** A managed identity is **not** OBO; do
  **not** pass a user token into the sandbox; reserve an **external broker** that
  keeps delegated user tokens *outside* the sandbox.
- **Decision 16 — OBO milestone scope.** *Reserve* the broker seam and **defer**
  its implementation until the base sandbox transport is proven; do not claim
  managed-identity-as-OBO, and do not build the broker in v1.
- **Decision 56 — Sandbox identity model.** *(Owned here; v1 mechanism set by a Human Tier-A
  decision on 2026-07-24, parent master log **row 66** "supersedes #56/#57 v1 mechanism". Earlier
  rows #56/#57 (2026-07-23) proposed carrying the app's MI into the sandbox; that is now deferred —
  see below.)* **v1: the sandbox is identity-less.** No managed identity is assigned to the sandbox
  and **no AAD token ever exists inside it**; outbound auth is performed by **egress-proxy credential
  injection** (MI `Transform`, then static secret) as the **primary** path, and the **controller
  delivers the content package** so the sandbox needs no storage/identity of its own. Carrying the
  app's **user-assigned managed identity** into the sandbox (the earlier #56/#57 mechanism) **and**
  ADC **HOBOv2** cross-resource delegation are **both deferred** to a future version — an in-sandbox
  token would let untrusted code inherit state-write RBAC, conflicting with **0008.3**'s sole-writer
  trust model. This **reinforces** Decisions 10, 11 and 16 (deny-by-default egress; managed-identity
  ≠ user OBO; the broker stays deferred) and realizes the original ADC goal that *no secret ever
  enters the sandbox*.

### The network and credential model (parent §4.10)

Every production sandbox starts with: full traffic inspection; default egress
action **Deny**; no general-purpose non-HTTP egress; ordered transform rules ahead
of broader host-allow rules; only explicit model / MCP / artifact / telemetry /
broker destinations; and, in v1, an **identity-less sandbox** (no managed identity exposed to
in-sandbox code — outbound auth is injected by the proxy). Because the **controller delivers the
content package** and packaging requires *no* internet install at create time (sibling 0008.6),
the deny policy can be enforced from the very first instant — there is no bootstrap window to
protect, and the sandbox needs no storage or identity of its own.

**v1 constraint — egress is one group-wide *mutable* policy, not epoch-pinned per session.** The
egress allow-list is a single ADC policy scoped to the Sandbox Group (§ delegation cross-reference
below), and ACA policies are **mutable on running sandboxes** (updates apply to subsequent
requests). In v1 this means an **operator egress-policy change (an egress-only change, without a
content redeploy) applies to *all* live sessions immediately** — egress is **not** pinned to a
session's content epoch. This deliberately differs
from *validation*, which **is** epoch-pinned to the session's content version (0008.7): a session
keeps validating against the package it started with, but it does **not** keep its own frozen egress
policy. Consequence (documented v1 edge, operator-initiated and rare): a **narrowing** change that
removes a destination a live session was previously allowed will start denying that destination
mid-session. *(Scope: this immediate-apply behavior concerns **egress-only** changes; a genuine
**content redeploy drains live sessions** so they never span a content-deploy boundary — parent
Decision 70.)* Per-session / per-content-epoch egress pinning is **future hardening**, aligned with the
per-`delegate_<slug>` egress scoping noted below (see the per-specialist egress resolution).

### Cross-reference: egress under multi-agent delegation (0008.13)

When a coordinator uses **subagents** (multi-agent delegation, FRD 0007), every
specialist runs *in the same session sandbox* (sibling 0008.13). Two consequences
for the model above: (1) the deny-by-default allow-list is deployed as **one
group-wide superset**, computed once from the app-wide catalog — the union of the
coordinator's and every reachable specialist's destinations — *not* a
per-session-recomputed set (consistent with the per-Sandbox-Group provisioning in
0008.4); and (2) those co-located specialists **share one egress proxy and
identity**, so a specialist can in principle reach a peer's allowed destinations
within the session. That is the **"one app = one trust domain"** posture (FRD 0007's
delegation Decision #10 — distinct from this file's Decision 10) and is *strictly
tighter* than today's in-process model, which shares the worker's network with no
per-agent egress isolation at all. Per-specialist egress isolation inside a shared
sandbox is **accepted as the group-wide union for v1**, with identity-scoped rules named
as a future hardening (see the resolution under *Open questions & resolutions* below) —
co-owned with 0008.13 (Decision 44).

**Identity & outbound-authentication model** for allowed destinations. *(v1 model per the
2026-07-24 Tier-A decision; supersedes the earlier "carry the app's MI into the sandbox"
mechanism.)* The v1 sandbox is **identity-less**: no managed identity is assigned to it and
**no AAD token ever exists inside it**. Outbound auth to allowed destinations is therefore
performed **by the egress proxy**, which injects credentials into requests *after* they leave
the sandbox — so the workload never holds a token or secret. In preference order:

1. **Proxy-injected managed-identity token (primary).** An egress-proxy `Transform` mints a
   host/path/method/resource-scoped MI token on demand — using an identity held on the *proxy /
   sandbox-group infrastructure* side, **never exposed to the workload** — and injects it into the
   allowed request. This promoted primary path realizes the original ADC motivation that **no
   secret ever enters the sandbox**.
2. **Proxy-injected static customer secret (fallback).** Where the destination can't use Entra,
   an operator-provisioned `Transform` injects a static secret from the **Sandbox Group Secrets
   store** (prefer a Key Vault reference; see the static-secret resolution below).

**Harness configuration (required).** Because the sandbox is identity-less, the in-sandbox harness
**must not attempt its own AAD token acquisition** — `DefaultAzureCredential`, a direct IMDS call,
or an in-sandbox Identity-Proxy lookup will find no identity endpoint and must not be relied on.
Outbound authentication is entirely the egress proxy's job.

*Deferred to a future version (both).* (a) Assigning the app's **user-assigned managed identity**
to the Sandbox Group so in-sandbox code acquires tokens directly (the earlier Decision 56/57 v1
mechanism, served by an ADC **Identity Proxy**), and (b) ADC **HOBOv2** cross-resource
`delegatedResources` delegation (with mixed-mode `lifecycle none/main/all` gating). Both give the
sandbox an in-workload identity; both are deferred because an in-sandbox token conflicts with
0008.3's sole-writer trust model (untrusted code could inherit state-write RBAC and rewrite session
state) and is unnecessary once the controller delivers the package.

*(ADC platform design for the deferred delegated-identity paths: `coreai-microsoft/adc` —
`docs/arch-design/ManagedIdentity.md` and `docs/arch-design/ManagedIdentityDelegation.md`.)*

**Identity-less ⇒ the sandbox cannot write state, and needs no storage.** Because no identity is
provided to the sandbox, in-sandbox code holds **no AAD token** and can reach only what the
**egress policy** allows (plus any proxy-injected credential). This directly satisfies **0008.3**'s
sole-writer trust model — the sandbox **cannot write session state** (the sandbox identity gets no
state access; only the controller writes state) — and removes any need for sandbox storage access,
because the **controller delivers the content package** into the sandbox (0008.6). This is the v1
posture for *every* session, including `function_app`-owned / function-key sessions
(cross-ref 0008.2), which never had a user identity to begin with.

**How the egress proxy governs everything.** Even though the v1 sandbox is identity-less, the
egress proxy is what makes outbound calls *both possible and safe*: it decides *what destinations
are reachable at all* (deny-by-default) **and** *injects* the credentials for allowed requests.
Every outbound request crosses the proxy, so it is simultaneously the **reachability gate** and the
**credential-injection point** — and no token or secret is ever handled by the workload.

**Can customers specify secrets for the proxy to substitute?** Yes — the static-secret `Transform` —
but the declaration/enforcement split matters:
- **Destination *intent*** (which hosts need reaching) is *authored*, derived from existing
  capability config (MCP server URL, `web_request` `allowed_hosts`, the model endpoint); the
  controller computes the group-wide **union**. A first-class egress field, if ever added,
  belongs to the **authoring surface (0008.10)** — not here.
- **The secret value + the `Transform`** are **operator-provisioned into the egress policy /
  Sandbox Group Secrets store** (sourced from Key Vault at deploy). They are **not** Function
  App **app settings**: the egress proxy is a separate resource (Sandbox Group data plane) that
  cannot read the controller's app settings, and the sandbox identity gets no Key Vault/state
  access (0008.3). So **enforcement + credential injection = this FRD (0008.9); authoring =
  0008.10.**
- *Backend nuance:* authored `$VAR`/`%VAR%` **app-setting** references (what the in-process MCP
  `header_provider` uses today) resolve only on the **local backend**, where the harness runs in
  the Functions worker. On the **sandbox backend** they can't reach the proxy — outbound auth must
  instead be **proxy-injected** (a proxy-side MI `Transform`, or a secret **mirrored** into the
  Sandbox Group Secrets store).

Secret values are never logged or round-tripped through config. Two hazards remain: egress-policy
*read* APIs can reveal static `Transform` values, and static secrets don't self-rotate — so
SandboxGroup Data Owner operations are privileged (another reason the sandbox identity gets *no*
state/Key Vault access, 0008.3).

**Why managed identity — and HOBO — are still *not* user OBO.** Any managed identity (the proxy-side
sandbox-group identity used for injection, or one a *future version* delegates into the sandbox via
plain assignment or HOBOv2) represents the **workload/resource**, not the
signed-in **user**. **HOBO ("Hosted on Behalf Of") is *resource*-identity delegation and must not
be confused with OAuth *OBO* ("On-Behalf-Of"), which is *user* delegation** — HOBOv2 carries no
user assertion and mints no user-delegated token. True delegated-*user* access still needs a token
exchange the proxy can't do by itself. The safe extension remains an **external credential
broker**: Easy Auth validates the inbound user → the sandbox calls only a narrow broker API (the
proxy injects a *workload* token for the broker audience) → the broker performs OBO *outside* the
sandbox, calls an allow-listed downstream, and returns the result → the user assertion, refresh
token, confidential-client credential, and delegated downstream token **never enter sandbox memory
or disk**. The broker is a *separate* trust boundary; FRD 0008 reserves the seam and defers it
(Decisions 11, 16). OBO also presupposes **`entra_user` ownership** — `function_app`-owned sessions
have no user to act for, so OBO is *inapplicable* there, not merely deferred (cross-ref 0008.2).

## Alternatives considered & why the choice won

- **Egress posture (Decision 10).** Considered: default-allow then tighten;
  default-deny *after* bootstrap; or default-deny *from create*. Chosen:
  default-deny from create with full inspection — any window of permissive egress
  is an exfiltration window, and the no-internet-install packaging (0008.6) removes
  the only reason such a window seemed necessary. *Agent.*
- **OBO interpretation (Decision 11).** Considered: treat managed identity as OBO;
  pass the user token into the sandbox; or use an external broker. Chosen: managed
  identity is *not* OBO, never inject the user token, reserve a broker that keeps
  delegated tokens outside the sandbox — putting a user's delegated token inside
  partly-untrusted compute is the exact risk to avoid. *Agent.*
- **OBO milestone (Decision 16).** Considered: claim managed-identity-as-OBO now;
  build the broker in v1; or reserve the seam and defer. Chosen: reserve the seam,
  defer implementation until base transport is proven — building a second trust
  boundary before the first is validated is premature. *Agent reviewer.*
- **Sandbox identity model (Decision 56).** Considered: (a) egress-proxy credential injection into
  an **identity-less** sandbox (no token in the workload); (b) give the sandbox its own separate
  identity; (c) **run the sandbox as the *same* MI** the controller uses. Originally chose (c) for
  auth parity; the 2026-07-24 rubber-duck review found (c) breaks 0008.3's sole-writer trust model
  (in-sandbox code would inherit the controller MI's state-write RBAC) and that (c) was unnecessary
  once the controller delivers the package (0008.6). **Revised choice (Human Tier-A, 2026-07-24;
  parent row 66): (a)** — the v1 sandbox is identity-less with egress-proxy injection as primary.
  Options (b)/(c) — plain-UAMI assignment (the earlier #56/#57 mechanism) and HOBOv2 — are **both
  deferred**. *Human.*

## Honest critique

**Strengths.** Deny-from-create (enabled by no-internet packaging) closes the
classic bootstrap-exfiltration window that many sandbox designs leave open.
Proxy-injected credentials that never touch workload memory is a strong pattern.
Most importantly, the FRD *refuses to overclaim OBO* — a very common and dangerous
conflation — and designs a broker that structurally keeps delegated tokens out of
the sandbox.

**Risks / assumptions.**
- **OBO is deferred, so a real user need is unmet in v1.** Any scenario that
  genuinely requires calling a downstream API *as the user* (e.g. reading the
  caller's own mailbox/files) simply cannot be done safely in v1 — only the seam
  exists. That may be a bigger product gap than it appears.
- **Static secret transforms are a weak spot.** They don't rotate and can be
  revealed by policy-read APIs; the design flags this but still allows them as the
  static-secret fallback, so a careless deployment can leak a long-lived secret.
- **Egress allowlist maintenance burden.** Deny-by-default means every legitimate
  destination (model, each MCP server, telemetry, artifacts, broker) must be
  explicitly allowed with ordered rules — operationally fiddly and easy to get
  subtly wrong, and a missing rule surfaces only as a runtime egress fault.
- **Inspection vs. confidentiality.** "Full traffic inspection" implies the proxy
  can see request contents; that's powerful for control but is itself a sensitive
  vantage point that must be secured and not logged (the runtime's never-log-secrets
  rule in `docs/observability.md` applies — credentials and query strings are never
  recorded; see the proxy log/telemetry resolution below).
- **Outbound reach depends entirely on a correct proxy policy (Decision 56, v1 identity-less).**
  With no in-sandbox identity, every authenticated destination must be wired as a proxy `Transform`;
  a missing or mis-scoped injection rule surfaces only as a runtime auth failure. The upside is
  strong: no token or secret ever lives in the workload, so a sandbox compromise leaks no reusable
  credential. The proxy-side injection identity must itself be least-privilege and, critically, must
  **not** have state-write access (0008.3).
- **Some in-sandbox-SDK patterns don't work in v1.** Code that assumes a local managed identity
  (`DefaultAzureCredential`, direct IMDS) finds none — those calls must be avoided in the harness.
  Scenarios that genuinely need the sandbox to hold its own workload identity wait for the deferred
  plain-UAMI-assignment or HOBOv2 paths (each of which must first reconcile an in-sandbox token with
  0008.3's sole-writer trust model).

**Reconsider triggers.** Revisit if: a concrete, common user scenario needs true
OBO (then the broker moves from reserved seam to funded design); static-secret
transforms prove too leaky and must be dropped in favor of Entra-only
destinations; egress-allowlist maintenance becomes a top adoption complaint; or a
scenario genuinely needs the sandbox to hold its own workload identity (then revisit the
deferred plain-UAMI-assignment or HOBOv2 paths — each requires reconciling in-sandbox tokens
with 0008.3's sole-writer trust model).

## Open questions & resolutions

Most items below were **resolved by the user** (marked *Resolved*). The sandbox-identity item
was **revised on 2026-07-24** (Tier-A, parent row 66) to the identity-less v1 model, superseding
the earlier #56/#57 mechanism; the others were resolved 2026-07-23. Decisions 10/11/16 are
reinforced throughout. A couple of narrow implementation-time follow-ups remain, noted inline.

- **User-delegation (OBO) path — deferred to a follow-up FRD.** *Resolved (Human,
  2026-07-23):* user-OBO is **out of scope for 0008.x and deferred to a dedicated
  follow-up FRD**, consistent with Decision 16. The *workload*-identity need is met by
  **proxy-injected managed identity** (the identity-less v1 model, Decision 56 / parent row 66 —
  no token inside the sandbox); calling a downstream *as the signed-in
  user* is the residual gap that follow-up will own. It will scope the options — a
  **controller-performed OBO** (the controller does the exchange and passes the sandbox
  only a short-lived downstream token) vs. an **external broker** (token never enters the
  sandbox) — and first check whether a Microsoft-native service (Easy Auth token store,
  API Management credential manager) can stand in before anything bespoke is built.
  Presupposes `entra_user` ownership (cross-ref 0008.2); inapplicable to `function_app`-owned
  sessions.
- **Sandbox identity mechanism — resolved for v1 (identity-less).** *Resolved (Human Tier-A,
  2026-07-24; parent master log **row 66**, supersedes the #56/#57 v1 mechanism):* the v1 sandbox
  is **identity-less** — no managed identity, no AAD token inside, ever. Outbound auth is via
  **egress-proxy credential injection** (primary), and the **controller delivers the content
  package**, so the sandbox needs no identity or storage access. Assigning the app's user-assigned
  MI to the Sandbox Group (the earlier #56/#57 mechanism) **and** ADC **HOBOv2** are **both deferred**
  to a future version (an in-sandbox token would conflict with 0008.3's sole-writer trust model).
  *Remaining follow-up (implementation-time, not a v1 blocker):* pin down the proxy-side injection
  identity's exact scope (least-privilege, **no** state-write access) and add negative tests that
  no AAD token is obtainable from inside the sandbox.
- **Egress rule authoring — reuse the `web_request` allowlist model.** *Resolved (Human,
  2026-07-23):* authors express egress **the same way the `web_request` system tool works
  today** (FRD 0005): a per-capability **`allowed_hosts`-style destination allowlist** plus
  optional per-host **`auth` profiles** (`headers` with typed secret-refs — `env` today;
  `managed_identity` / `key_vault_ref` forward-compatible). Destinations are **derived, not a
  new field**: the controller computes the deny-by-default policy as the **union** of the
  `web_request` allowlist, each MCP server URL, the model endpoint, telemetry, and the (future)
  broker. The authoring *shape* is owned by 0008.10 (and FRD 0005 for `web_request`); **this FRD
  owns the compile-and-enforce step**: (1) the union is emitted as an **ordered** ACA rule list —
  most-specific rules (exact host/path `Deny`/`Transform`) **before** broad host `Allow`s,
  consistent with ACA's first-match-wins evaluation; (2) a **deploy-time ordering lint** asserts
  no broad `Allow` shadows a narrower `Deny`/`Transform` (for each specific rule, verify no earlier
  rule already matches its match-set); and (3) each `auth` profile **compiles to a proxy
  `Transform`** — `managed_identity` → MI Transform (preferred, no secret), `key_vault_ref` →
  Key-Vault-reference secret in the Sandbox Group store, `env`/static → static-secret Transform
  (discouraged, per the static-secret resolution above). On the **sandbox backend** an `env`-style
  ref can't resolve in-workload, so it **must** map to the KV-reference or MI Transform form.
  Consistent with "one app = one trust domain": per-agent declarations may *widen* the union, and
  the union *is* the allowlist (no operator ceiling in v1).
- **Static-secret rotation — keep, but recommend Entra/MI first.** *Resolved (Human,
  2026-07-23):* the static-secret `Transform` **stays available** (some destinations
  can't use Entra) but is **not** the recommended path — prefer a managed-identity `Transform`
  or an Entra destination wherever possible. When a static secret is unavoidable, provision it
  as a **Key Vault reference** in the Sandbox Group secret store so **rotation is handled by
  Key Vault** (the reference is re-resolved; the sandbox never holds the value). Raw, non-KV
  static values are discouraged precisely because they don't self-rotate and can be surfaced by
  policy-read APIs. *(Not deprecated — the escape hatch remains for non-Entra destinations.)*
- **Non-HTTP egress — hard-blocked in v1; escape hatch deferred to FRD 0009.** *Resolved
  (Human, 2026-07-23):* v1 runs the egress proxy in **`Full` inspection**, which **blocks all
  non-HTTP traffic**. Rationale: the proxy's controls (allow-list by host/path/method,
  credential injection) are HTTP-only, so non-HTTP is an *uninspectable* exfiltration channel
  (raw TCP, DNS tunneling); and the v1 harness's real destinations — model, MCP, telemetry,
  artifacts, broker — are all HTTP(S), so blocking costs no v1 feature. The one realistic
  exception, a **database driver over a native (non-HTTP) wire protocol**, is **out of scope
  for v1 and owned by FRD 0009** (the non-HTTP fast-follow, parent Decision 41), where a
  scoped escape hatch (e.g. ACA `Partial`/`Legacy` inspection for *trusted* destinations, or
  an HTTP-fronted tunnel / Private Link) gets proper security review. *Consequence:* tools that
  need direct non-HTTP DB access are unsupported on the **sandbox** backend in v1 (they still
  work on the local/in-process backend).
- **Proxy log/telemetry safety — no secrets recorded by default; metadata is fine.**
  *Resolved (Human, 2026-07-23):* the egress proxy **never records secret material by default** —
  injected `Transform` credentials, `Authorization` / API-key headers, static-secret and Key Vault
  values, and query-string secrets are **never** logged, extending the runtime's existing
  never-capture-secrets rule (`docs/observability.md`, *Sensitive data*: MCP tokens, connection
  strings and the ACA system key are never captured, and endpoints are reduced to host only).
  Within that constraint the proxy **may capture whatever operational metadata it needs** to
  enforce policy and be audited: egress **decisions** (allow / deny / transform / rewrite),
  destination **host** (not the full URL or query string), method, timestamps, byte sizes, and
  **denied counts** (the ACA-recommended audit signal). Request/response **content** stays behind
  the same `ENABLE_SENSITIVE_DATA` gate as the rest of the runtime (default **off** → metadata
  only); **secrets are never emitted even when that flag is on**. Because full inspection makes the
  proxy a uniquely sensitive vantage point, it gets the strictest treatment: metadata by default,
  content only under the gate, secrets never.
- **Per-specialist egress within a shared sandbox — union accepted for v1.** *Resolved
  (Human, 2026-07-23):* v1 **accepts the one group-wide union** with **no per-specialist
  egress *isolation***. To be precise, specialists still make outbound calls — they are
  simply **not partitioned**: every co-located specialist shares the one egress proxy/identity
  and can reach any destination in the union (the "one app = one trust domain" posture, already
  strictly tighter than today's in-process model). Identity-scoped egress rules per
  `delegate_<slug>` are named as a **future hardening** for high-security deployments, not a v1
  feature. Co-owned with 0008.13 (Decision 44).
- **Egress policy is group-wide and mutable, not epoch-pinned — v1 constraint.** *Resolved (Human,
  2026-07-24, deployment-epoch depth-gap — egress half):* v1 keeps **one group-wide, mutable ADC
  egress policy**; it is **not** epoch-pinned per session. An operator **egress-only** change (no
  content redeploy) applies to **all live sessions immediately** (unlike *validation*, which **is**
  pinned to the session's content epoch per 0008.7; and unlike a genuine **content redeploy**, which
  **drains** live sessions per parent **Decision 70** rather than applying across the boundary).
  Documented v1 edge: an operator-initiated **narrowing** can
  start denying a destination a live session was previously allowed (rare). Per-session /
  per-content-epoch egress pinning is **future hardening**, aligned with the per-`delegate_<slug>`
  egress scoping above. This is a scoping/documentation statement, not a mechanism change. (See also
  the network-model section.)
