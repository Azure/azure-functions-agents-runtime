# FRD 0008.3 — Customer-owned state store & tamper-evident trust model

> Sub-FRD of [FRD 0008](0008-aca-sandbox-session-runtime.md). It re-expresses,
> in plain language, one self-contained decision area from the reviewed parent.
> **Revised 2026-07-22 (Human direction):** the trust model was simplified to
> lean on Function-App platform primitives instead of per-binding Key Vault
> signing and an immutable WORM log (Decisions 32 and 39 revised). **Finalized
> 2026-07-22** with Human sign-off recorded in the
> [Decisions log](#decisions-log-this-sub-frd).

## What this is and why it matters

Because a session's compute (its **ACA Sandbox** — an isolated Azure Container
Apps container) can be suspended, replaced, or lost, the system needs a durable
record that maps *"session X belongs to owner Y and currently lives in sandbox
Z."* This record is the routing pointer for every turn. If an attacker (or a bug,
or a stale replica) could tamper with that pointer, a caller's turn could be
routed to the wrong sandbox — a "confused deputy" attack.

This area decides *where* that record lives and *how it is validated*. The record
lives in a **customer-owned Azure Storage account** (the application owner's Azure
subscription — never a runtime-team service). The **security boundary is the
Function App**: callers are authenticated by whatever the platform already
accepts — **Easy Auth / Entra tokens *or* Function Keys** — and the *owner* of a
session may be an Entra user **or the Function App itself** (the versioned,
discriminated `OwnerContext` from
[0008.2](0008.2-session-identity-ownership-concurrency.md); 0008.3 *consumes* it and
never re-derives identity). Inside that boundary the trust anchor is simple: because
Shared Key is disabled and storage RBAC is scoped to exactly one table and container
(Decision 33), the **only writer of the state row is the controller's managed
identity**. The row is therefore *authoritative by construction* — but every read
still **verifies rather than blindly trusts**, using two platform-native checks: a
**monotonic generation** on the row (bars rollback) and a **live sandbox manifest**
fetched over the ACA data plane (proves the pointer resolves to the right, ready
sandbox — authenticity comes from ACA isolation, because a storage-only or external
principal cannot forge a *live* manifest). No Key Vault key and no immutable log are
required; tampering is *detected and quarantined at read time* rather than proven by
a cryptographic audit trail. End users never get a storage credential.

## Decisions this sub-FRD owns

- **Decision 5 — Session directory ownership.** State lives in *customer* storage,
  never a runtime-team-operated cross-customer service. (Later refined by
  Decision 31.)
- **Decision 20 — Control-state storage type.** Azure **Tables** hold queryable,
  ETag-controlled session/run records; **Blob Storage** holds transcript and
  checkpoint archives.
- **Decision 31 — Production account (revises #5).** Production requires a
  *dedicated* `AzureFunctionsAgentsStateStorage` account; reusing the Functions
  host's `AzureWebJobsStorage` is allowed only for local/dev and explicit preview
  trials.
- **Decision 32 — Session-pointer validation *(revised 2026-07-22, Human)*.**
  ~~Sign routing-critical bindings with a non-exportable Key Vault key.~~ Within the
  Function-App trust boundary the state row is *authoritative by construction*
  (Decision 33 makes the controller managed identity its only writer), so routing is
  validated with **platform-native checks — a monotonic generation (bars rollback)
  plus a live sandbox manifest cross-check (authenticity from ACA data-plane
  isolation)** — no Key Vault key. Per-binding cryptographic signing is dropped as
  inconsistent with a boundary that already accepts Function Keys as authorization.
- **Decision 33 — State authorization.** Disable Shared Key; grant the Functions
  managed identity narrow Entra roles *scoped to the one table and container*; the
  sandbox identity gets *no* state access.
- **Decision 39 — Immutability scope *(revised 2026-07-22, Human)*.** ~~Use a
  dedicated immutable WORM binding-log container.~~ v1 keeps **no WORM log**: the
  monotonic **generation lives on the Table row** (ETag-guarded), and Blob Storage
  holds only the single *deletable* history/checkpoint container. A WORM audit trail
  is **reserved** as a future option if forensic tamper-evidence is ever required —
  and because it never mixed with deletable user content, adding it later stays a
  clean, additive change.

### The layout and the trust sequence (parent §4.7, revised)

```text
table  AzureFunctionsAgentsSessions
  PartitionKey = {owner_hash_version}:{app_hash}:{owner_kind}:{owner_hash}
                 (discriminator-aware: entra_user and function_app owners never collide)
  RowKey       = session:{session_id} | run:{session_id}:{run_id}
  session row  = sandbox pointer, generation (monotonic), digest_kind + digest,
                 owner_hash_version, protocol, status,
                 last_activity_at, expires_at (idle-reclaim deadline), idle_policy_armed
  run row      = status, expires_at (run-timeout deadline), …
                 (both row types written only by the controller MI)

blob container  azure-functions-agents-state   (deletable)
  sandbox-runtime/history/{owner_hash}/{session_id}.jsonl
  sandbox-runtime/checkpoints/{owner_hash}/{session_id}/{generation}.json
```

> **v1 scope note.** Per [0008.8](0008.8-snapshot-suspend-and-durability.md)
> (Finalized), the owner-scoped external Blob mirror is **deferred to v2**, so in v1
> the deletable history/checkpoint container is provisioned but **not populated**. The
> trust sequence below depends only on the authoritative Table row + live manifest,
> never on an external checkpoint, so routing trust is unaffected. (Consequence per the
> canonical generation model below: because a state-preserving generation advance is
> **v2-only**, v1 has **no generation bump** — a backing loss is a **tombstone**, not a
> bump-and-resume. The durability handling lives in 0008.8/0008.5, not here.)

> **Run-row locator note.** Because run rows are keyed `run:{session_id}:{run_id}`,
> any public run-management route or response locator must carry `session_id` (or
> introduce an explicit run-id locator index). v1 chooses **session-scoped run URLs**
> ([0008.11](0008.11-http-api-sync-async-streaming.md)) rather than a run-id locator
> index.

> **Reconciler due-work query (v1).** The lifecycle reconciler
> ([0008.12](0008.12-lifecycle-failure-and-reconciler.md)) finds timeout / idle-reap
> candidates by reading **this single source-of-truth table directly** — a bounded
> server-side filter on `status` + the due-time fields, following continuation tokens.
> The persisted due-time contract (0008.3 persists the fields; 0008.12 owns their
> values/semantics) is a single, identical set across both docs, with **explicit row
> ownership** because the reaper scans **both** row types:
> - **`expires_at`** — one field name, per-row meaning. On the **run row** it is the
>   *run-timeout* deadline; on the **session row** it is the *idle-reclaim* deadline.
>   There is deliberately **no separate `reclaim_at`**.
> - **`last_activity_at`** — on the **session row** (last-activity timestamp).
> - **`idle_policy_armed`** (bool) — on the **session row**; lets the reaper distinguish
>   terminal-not-armed from terminal-armed-idle; the reaper reads/sets it.
>
> The reaper's predicate therefore covers both row types (run rows for timeout of
> accepted+running work, session rows for idle reclaim, CAS-checking no-active-run on
> reclaim — 0008.12). At the v1 target of ~100 concurrent sessions (Decision 29) that
> filter is a cheap table scan. **v1 runs it as a ~1-hour backstop reconcile
> (0008.12); the ~1-minute cadence (Decision 24) is the v2 target.** There is **no
> separate due-work index table** — Azure Table entity-group transactions require a
> shared PartitionKey, so a reaper-view row co-written with the run row would land in
> the *owner* partition and still force a cross-partition scan; a reaper-friendly index
> would need a different PartitionKey and therefore could **not** be co-written
> atomically, reintroducing the cross-table consistency risk this design deliberately
> avoids. The timeout *policy* and due-time values are 0008.12's (Decisions 22/27);
> 0008.3 only persists the fields the scan reads. Revisit the scan (a time-bucketed
> index partition) only if scale grows well beyond the 100-session target.

Every **routing or submit** operation is *fail-closed* and runs this sequence: **(1)** consume the
resolved `OwnerContext` from the identity layer
([0008.2](0008.2-session-identity-ownership-concurrency.md)) — derived from the
*platform-authenticated* caller (Easy Auth / Entra token **or** Function Key; owner
kind `entra_user` **or** `function_app`), never from request-supplied hashes → **(2)**
compute the deterministic, discriminator-aware partition and read only that owner/app
partition → **(3)** read the session/run row, which is *authoritative by construction*
because Decision 33 (Shared Key disabled, RBAC scoped to this one table/container)
makes the **controller managed identity its only writer** → **(4)** enforce the
**monotonic generation** on the row under an ETag-guarded conditional write (a
lower/divergent generation is *rollback*, not a recovery hint) → **(5)** take the
short ETag lease and resolve the sandbox only inside the configured **Sandbox Group**
→ **(6)** fetch the sandbox's **live manifest over the ACA data plane** and require it
to match owner/app/session/group/generation/`(digest_kind, digest)`/protocol →
**(7)** submit only after a real readiness operation succeeds. Any generation or
manifest mismatch returns *not-found* semantics, emits a security event, and
**quarantines** the sandbox rather than deleting state.

**Not every read is a routing operation.** Authorization, status, result-availability,
tombstone, and post-reap reads are **Table-only** after `OwnerContext` partition
resolution. They must **not** require a live manifest — terminal status stays readable
after the sandbox is suspended or reaped, and result eviction is represented as **410
Gone** rather than a routing failure. Only operations that actually route to or submit
against a live sandbox perform steps (5)–(6)'s Sandbox-Group resolution and
live-manifest cross-check. (Consistent with the reaper/status model in
[0008.12](0008.12-lifecycle-failure-and-reconciler.md) and the run-status/result routes
in [0008.11](0008.11-http-api-sync-async-streaming.md).)

**Canonical generation model (authoritative — this is the source of truth siblings
align to).** The `generation` is a per-session, forward-only integer that identifies
the concrete **sandbox backing** (instance + its disk) the session's pointer resolves
to. Its sole purpose is to bar rollback: a read presenting a lower/divergent generation
than the authoritative row is rejected fail-closed.

1. **What it identifies — and what it does NOT.** The generation tracks the *sandbox
   backing*, never the content. A live session's captured content — its
   `(digest_kind, digest)` — is **fixed at session creation and immutable for the
   session's lifetime**; different content is a **different session** (different
   `session_id`), never a content change within a live session. So the generation
   **never encodes a content change**, and the earlier "content-source switch ⇒ new
   generation" phrasing is **retired** for the live-session case: there is no in-session
   content switch. (`digest` is written once at create; the `(digest_kind, digest)` pair
   *shape* is retained only so a *new* session can adopt Path 2 additively.)

   **Epoch stamp & drain-on-deploy (parent Decision 70).** Because it is fixed at
   creation, the session's stamped `digest` is its **epoch stamp** — the content epoch
   the session belongs to (this is the same value 0008.7 pins I/O validation to). A
   redeploy changes the **controller's current** content digest but never a live
   session's *stamped* digest. When the controller's current digest **≠** a session's
   stamped digest (i.e. a redeploy happened since the session started), that session is
   **drained and tombstoned**: in-flight run grace-then-abandon → session tombstoned →
   **410 Gone**, and the caller starts a new session (which stamps the new digest). So
   **digest-mismatch is a tombstone trigger**, alongside backing-loss. This is a
   *content-epoch* transition across sessions, not a generation change within one — it
   does **not** bump the generation (the generation still only tracks the sandbox
   backing per items 2–3). 0008.12 owns the drain mechanism; 0008.3 supplies the
   stamped digest that the comparison reads. No new field — reuse `(digest_kind,
   digest)`.

2. **What ADVANCES it.** Only a **state-preserving rebind to a DIFFERENT sandbox
   backing while the same session continues** — the session's logical state is carried
   onto a new instance. That requires reconstructing state on the new backing, which
   needs the external checkpoint mirror. **The mirror is v2 (deferred, 0008.8), so a
   generation advance is a v2-only event.** The in-flight (incomplete) turn is abandoned
   (never migrated); the session continues from committed state.

3. **v1 behavior (definitive).** v1 has **no external mirror**, so there is **no
   mechanism to preserve state onto a different backing**. Therefore in v1 the
   generation is **effectively fixed at session creation** and only two transitions
   occur:
   - **Same backing ⇒ SAME generation:** ordinary suspend→resume, and crash-restart on
     the same intact disk (the controller's pointer/disk is unchanged; an in-memory
     in-flight turn is lost and resumes from the committed disk). Reattach is always
     *within one generation* in v1.
   - **Backing lost (disk/state unrecoverable) ⇒ TOMBSTONE:** the same `session_id`
     returns **410 Gone** and a new session is required. This is **never** a generation
     bump.

4. **Settled invariants (all versions).**
   - LOSS (state unrecoverable) ⇒ tombstone / 410, **never** a generation bump.
   - A bumped / "superseded" generation is a **state-preserving rebind** (v2), **not** a
     loss/tombstone.
   - suspend/resume + crash-with-disk-intact ⇒ **SAME** generation.
   - Rollback safety holds in v1 and v2: the generation never advances into an
     empty/stateless backing, so a stale-generation read is always safely treated as
     rollback rather than a legitimate fresh start.

Consumer reconciliation: **0008.5** — reattach is within one generation in v1; the
advancing rebind is v2. **0008.7** — epoch pins to the session's *fixed* `digest`, so
the epoch is constant for the session lifetime and is unaffected by any (v2) generation
advance. **0008.8** — correct "state-preserving rebind uncommon in v1" → **"v2-only"**.
**0008.12** — tombstone/deletion semantics unchanged. (Preserved state in v1 is always
the sandbox's own surviving disk; cross-ref 0008.8's v2 mirror.)

Why this is enough — and why no signature is needed:

- **The row is trustworthy without crypto.** With Shared Key disabled and RBAC
  scoped to the one table/container (Decision 33), nothing but the controller's
  managed identity can write it. Signing existed to catch a *rogue storage writer*;
  scoped RBAC already removes that writer.
- **The v1 sandbox is identity-less, which makes sole-writer trivially true.** Per
  parent **Decision 66**, the v1 sandbox carries no managed identity or token — the
  controller delivers its content package and outbound calls use egress-proxy
  credential injection ([0008.9](0008.9-network-egress-and-obo.md)). With *no*
  credential inside the sandbox, it cannot reach the state store at all, so "the
  controller MI is the only writer" holds **by construction, not merely by RBAC
  scoping.** This strengthens the model rather than weakening it.
- **Manifest authenticity comes from *liveness*, not a signature.** The manifest is
  fetched **live from the sandbox over the ACA data plane**, not read from storage,
  so a storage-only or external principal cannot forge it — they have no ACA access.
- **The generation bars rollback** on the row itself, so a separate immutable log is
  not needed to detect a stale/rolled-back pointer during normal operation.

The **threat model** is unchanged and explicit: the **Function App is the security
boundary**, and subscription Owners are trusted admins (defending against a malicious
Owner is out of scope). Cross-customer isolation is the Azure platform's job
(subscription / resource-group / tenant boundaries). The controls here defend against
end users, cross-tenant callers, accidental edits, and storage-only operators —
consistently with a boundary that already accepts Function Keys as authorization. The
one defense-in-depth reduction versus signing is named in the Honest critique.

## Alternatives considered & why the choice won

- **Directory ownership (Decision 5).** Considered: a runtime-team SaaS store,
  customer storage, or sandbox-only state. Chosen: customer storage — the project
  is open-source and must never require a runtime-team-operated cross-customer
  service. *Human.*
- **Storage type (Decision 20).** Considered: block blobs, Azure Tables, or a
  Durable Entity. Chosen: Tables for queryable ETag-controlled records + Blob for
  archives — Tables give cheap conditional writes and lifecycle queries the
  reconciler needs; Durable is avoided (see 0008.12). *Agent.*
- **Production account (Decision 31, revising 5).** Considered: reuse
  `AzureWebJobsStorage`, a dedicated account, or a runtime-team service. Chosen:
  dedicated account in production so control records don't inherit the Functions
  host's storage lifecycle and RBAC boundary; host-storage reuse is dev-only.
  *Agent reviewers.*
- **Session-pointer validation (Decision 32, revised 2026-07-22).** Considered:
  per-binding Key Vault signing + immutable log + live manifest (the original
  choice); trust ETag + RBAC only; or **scoped-RBAC-authoritative row + monotonic
  generation + live manifest** (no crypto). Chosen: the last — inside the Function-App
  trust boundary, disabling Shared Key and scoping RBAC (Decision 33) already makes
  the controller MI the sole writer, and the *live* manifest supplies authenticity
  via ACA isolation. Per-binding signing is inconsistent with a boundary that accepts
  Function Keys as authz, and adds a Key Vault key, per-read verify, and key-rotation
  burden for a threat (a rogue in-sub storage writer) that scoped RBAC already closes.
  *Human.*
- **Authorization (Decision 33).** Considered: Shared Key, account-wide data
  roles, or Entra roles at table/container scope. Chosen: disable Shared Key and
  scope roles to the exact table/container; the sandbox identity gets none.
  *Agent reviewers.*
- **Immutability scope (Decision 39, revised 2026-07-22).** Considered: a dedicated
  immutable WORM binding-log container (the original choice); one mixed container; or
  **no WORM log, with the generation carried on the Table row**. Chosen: the last for
  v1 — once per-binding signing is dropped, the immutable log's only remaining job was
  a forensic audit trail, which the trusted-Owner threat model does not require.
  Rollback detection moves to the ETag-guarded monotonic generation on the row. A WORM
  audit container stays reserved as a clean, additive future option. *Human.*

## Honest critique

**Strengths.** The trust posture is now *consistent with the Function-App boundary*:
authorization is whatever the platform accepts (Easy Auth / Entra **or** Function
Keys), and validation rests on the same platform primitives the rest of the system
already trusts — managed identity + scoped RBAC, ACA data-plane isolation, and Azure
Table ETags. Making the controller MI the *sole* state writer (Decision 33) turns the
row into a construction-time trust anchor, and the *live* manifest gives routing
authenticity with **zero cryptography**. Dropping the Key Vault key and WORM log
removes most of the customer-side setup and eliminates the per-read signature verify
and the append-log round trip.

**Risks / assumptions.**
- **The trust anchor is now operational config.** Everything rests on Shared Key
  being disabled and RBAC being correctly scoped. If a customer re-enables Shared Key
  or over-grants storage roles, the row is no longer authoritative. **Preflight must
  assert Shared Key is disabled and the scoped roles are present** (see open
  questions; coordinate with [0008.10](0008.10-authoring-surface-and-config.md)).
- **One defense-in-depth sliver is given up.** A principal holding **both**
  storage-write **and** ACA data-plane write (but no controller identity) could craft
  a matching sandbox and re-point the row, defeating the manifest check — signing
  would have stopped that. Such a principal is already near-controller-equivalent, and
  the old controller MI held the signing permission anyway, so this is acceptable
  under the trusted-Owner, experimental-v1 model.
- **No forensic audit trail.** Without the WORM log, tamper *evidence* degrades to
  read-time detection (manifest mismatch → quarantine). Routing errors are still
  caught; after-the-fact forensics are not preserved.
- **`function_app` shared-owner semantics.** Sessions owned by the Function App are
  addressable by *any* holder of a valid Function Key; session-level isolation between
  co-holders of the same key is not provided by the state layer (an
  [0008.2](0008.2-session-identity-ownership-concurrency.md) ownership semantics point,
  noted here as a consequence).

**Reconsider triggers.** Revisit if: a customer needs a forensic tamper-evidence
audit trail (re-introduce the reserved WORM container); the trust boundary changes so
that in-sub principals other than the controller must write state (signing regains its
purpose); or preflight cannot reliably assert the Shared-Key/RBAC anchor.

## Open questions — resolved at close (2026-07-22)

*The simplification dissolved three earlier open questions — key-rotation
semantics, immutable-container lifecycle/cost, and the append-log hot-path round
trip — because there is no signing key and no separate log. The three that
remained are resolved for v1 as follows:*

- **Preflight of the trust anchor — REQUIRED for v1.** Because the row is only
  authoritative if Shared Key is disabled and RBAC is scoped, deploy/startup preflight
  **must** assert both and fail closed otherwise. This is the single most load-bearing
  guardrail. The controller-startup assertion is a 0008.3 concern; the
  authoring-surface/config half is locked in
  [0008.10](0008.10-authoring-surface-and-config.md) (Finalized) as validation-matrix
  **row 6** (see cross-cutting note).
- **Multi-region / DR — DEFERRED (v1 non-goal).** v1 is single-region: the state
  account is co-regional with the Sandbox Group and a failover must **preserve that
  co-region invariant** (per
  [0008.4](0008.4-resource-residency-and-provisioning.md)) rather than drift. Detailed
  cross-region failover behaviour (generation/lease continuity) is out of v1 scope and
  reserved for a future revision.
- **`AzureWebJobsStorage` dev-mode guardrail — REQUIRED for v1.** Preflight **must**
  reject the dev-only host-storage mode (Decision 31) in production; it pairs with the
  trust-anchor preflight above, with the precise check locked in
  [0008.10](0008.10-authoring-surface-and-config.md) (Finalized) as validation-matrix
  **row 7**.

  content change is a new session with a new digest ⇒ new epoch, never "same digest,
  different schema.") If/when Path 2 (`aca_image`, deferred) lands, its `digest` is an
  immutable disk-id rather than a content SHA-256, so a captured-content hash would need
  adding then if 0008.7 requires SHA-256 semantics specifically.
- **[0008.9](0008.9-network-egress-and-obo.md)** *(reinforcement, parent Decision

- **[0008.12](0008.12-lifecycle-failure-and-reconciler.md).** The reaper is a trusted
  controller-MI actor, not a routing caller, so it is outside the fail-closed read
  path. Because 39-R removed the WORM evidence container, reaper/lawful deletion of
  session rows is **unconstrained by tamper-evidence** — there is no evidence trail to
  preserve in v1. The "binding" is now the authoritative row itself, so deleting an
  expired session row removes the pointer; rollback-via-recreate at the same
  `session_id` is out of scope (opaque non-reused ids + controller-MI-only writes).
  Per 0008.8, the deletable history/checkpoint container is unpopulated in v1, so the
  reaper's v1 external surface is Table records + reaped sandboxes only. **Due-work
  discovery reads this single source-of-truth table directly** — a bounded server-side
  filter over **both row types** on `status` + the canonical due-time fields
  (`expires_at` = run-timeout deadline on the **run** row / idle-reclaim deadline on the
  **session** row, no separate `reclaim_at`; `last_activity_at` + `idle_policy_armed` on
  the **session** row) at ~100-session scale, run as a **~1-hour v1 backstop** (the
  ~1-minute Decision 24 cadence is the v2 target) — with **no separate due-work index**
  (dropped per larohra's round-3 decision; the EGT same-PartitionKey constraint means
  an atomically co-written index can't be
  reaper-scoped, so it would add cross-table lag risk for no benefit — see "Reconciler
  due-work query" above). **Drain-on-deploy (Decision 70):** a session whose stamped
  `digest` ≠ the controller's current content digest is drained/tombstoned (in-flight
  grace-then-abandon → 410); 0008.12 owns the drain mechanism, 0008.3 supplies the
  stamped digest the comparison reads. So the reaper has **two** tombstone triggers —
  backing-loss and digest-mismatch — plus the due-time timeout/idle-reclaim above.
